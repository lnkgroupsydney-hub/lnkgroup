# 고객 데이터·계약·관리자 접근 설계

작성·갱신: 2026-10-04 · 목표 모델과 첫 계정 구현 경계 · [목차](README.md)

## 관리자 로그인과 권한

초대한 개별 관리자만 ESN에 들어오는 것을 1차 기준으로 한다. 기존 공용 owner 비밀번호는 운영 인증으로 승격하지 않는다. Supabase Auth의 개별 비밀번호 인증과 서버의 현재 관리자 membership을 확인한다. 최초 TOTP안 이후 사용자가 휴대폰 없이 이메일 코드로 진행하도록 선택했으며 현재 구현은 별도 서버 세션에 귀속된 이메일 확인을 추가한다. 공개 회원가입으로 관리자 권한을 받을 수 없고 회사 이메일 도메인 일치만으로 승격하지 않는다. 고객 로그인은 별도 후속이며 관리자 초대 경로와 섞지 않는다.

| 사용자 | 허용 범위 | 서버에서 확인할 조건 |
| --- | --- | --- |
| 비인증·일반 고객 | ESN 데이터 접근 없음 | 고객 작성 권한으로 관리자 API/PDF/사진 요청 거절 |
| 개별 로그인 후 추가 확인 미완료 | 비밀번호 설정·선택된 추가 확인·로그아웃 | 고객 데이터 응답 없이 제한된 설정 흐름만 제공 |
| 활성 관리자 | 같은 회사 고객·계약·예약·구매 조회, 승인된 업무 처리 | 유효 세션 + 활성 membership + 선택된 추가 확인 + 작업별 권한 |
| 관리자 중 권한 관리 책임자 | 초대·회수·역할 변경·회사 연동 설정 | 재인증·감사, 마지막 책임자 접근 상실 방지 |
| 비활성·회수 계정 | 접근 없음 | 이전 토큰이 남아도 서버의 최신 membership으로 즉시 차단 |
| 후속 직원·회계 역할 | 필요한 업무·필드만 | 별도 범위 승인 후 추가. 1차에서 자동 활성화하지 않음 |

최초 관리자는 회사가 지정한 사람을 통제된 절차로 등록한다. MFA 기기 분실·초대 만료·잠금·퇴사 시 복구 담당자와 본인 확인 절차를 인수 항목으로 둔다. ‘전체 고객 조회’ 권한이 계약 원본 수정·무제한 환불·개인정보 내보내기를 자동 허용하지 않도록 조회/수정/내보내기/권한 관리를 구분한다.

추가 확인은 서버/API에서도 매 요청 검사한다. TOTP의 [Supabase MFA 보증 수준](https://supabase.com/docs/guides/auth/auth-mfa)과 애플리케이션의 이메일 검증 증거를 구분한다. 이메일 검증 성공을 Supabase `aal2`로 만들지 않는다. 사용자 수정 가능한 metadata에 관리자 권한을 넣지 않는다. 토큰의 과거 역할 값만 믿지 않고 현재 활성 membership을 조회한다. [Supabase RLS 안내](https://supabase.com/docs/guides/database/postgres/row-level-security)

현재 22개 업무 테이블은 서버 전용 접근 구조다. Auth를 붙였다고 기존 테이블을 `authenticated`에 일괄 공개하지 않는다. 서버 비밀키는 RLS를 우회할 수 있으므로 서버 인가·최소 GRANT·RLS·RPC 실행 권한을 각각 검증한다. 조회용 view도 권한 우회가 없는 방식으로 만들고 브라우저 직접 조회는 별도 설계 없이 추가하지 않는다.

### 첫 관리자 계정의 구현 선택 — 2026-10-04 후속 요청

사용자가 지정한 `lnkgroupsydney@gmail.com`을 승인된 회사 Supabase Auth에 생성했다. 첫 회사 책임자는 `lk-group`의 `owner`로 지정하며 일반 `admin`은 업무 조회/수정만, `owner`는 회사 Google 연동 관리도 수행하는 기존 인가 정책을 적용한다. 계정 생성 자체를 영구 비밀번호 설정·MFA 완료·업무 접근 검증으로 표시하지 않는다.

- **초기 membership:** 서버 관리자가 쓰는 Auth `app_metadata.lk_staff`의 `company_id`, `role`, `status`를 사용한다. 임시 비밀번호 변경 의무는 독립된 `app_metadata.lk_staff_password_change_required` boolean으로 관리한다. 매 요청 Auth 서버의 `getUser`로 최신 값을 읽으며 클라이언트 편집 가능한 `user_metadata`나 JWT에 남은 과거 metadata를 권한의 원본으로 삼지 않는다.
- **세션과 회수:** 검증한 JWT의 사용자·세션·만료·MFA 수준, 실제 `auth.sessions`의 유효 세션, 기존 비공개 `lk_sessions`의 직원 세션 등록을 함께 확인한다. 실제 Auth 세션 조회는 서비스 역할 전용 RPC로 제한한다. 사용자가 신규 migration을 회사 DB에 적용했다. 실제 RPC에서 유효 세션만 허용하고 다른 사용자·로그아웃·null 세션을 거절했으며 anon/authenticated 호출은 `42501`로 차단됐다. 적용/실행 증거는 [온보딩 검증 기록](../verification/2026-10-04-staff-admin-onboarding.md)을 따른다.
- **단계 제한:** 로그인 후 임시 비밀번호 교체와 선택된 추가 확인이 완료돼야 업무 API를 허용한다. 최신 `STAFF_ADMIN_SECOND_STEP=email` 모드에서는 현재 세션의 이메일 검증 증거를 요구하며, 남아 있는 TOTP factor나 `aal2`만으로 이 단계를 우회하지 않는다. `STAFF_ADMIN_AUTH_ENABLED=true`에서는 기존 공용 비밀번호·Google 데모 세션으로 우회하지 않는다. Google 연결은 직원 로그인과 별개이며 `owner` 권한과 현재 직원 세션에 연결된 OAuth 상태를 검사한다.
- **비밀값:** 임시 비밀번호는 최초 생성 시 Git 제외 `.local/admin-onboarding.json`에 소유자 전용 권한 `0600`으로 보관했고, 사용자 영구 비밀번호 변경 완료 후 그 값을 제거했다. 변경 의무 플래그가 `false`인 것을 확인했으며 새 비밀번호 값은 읽지 않았다. 계획·로그·스크린샷에 비밀값을 넣지 않는다. TOTP 등록은 최신 이메일 방식 선택에 따라 현재 필수 단계에서 제외했다. 이메일 코드·TOTP 키를 계획이나 로그에 보관하지 않는다.
- **후속 확장:** 별도 `staff_memberships` 테이블·다중 관리자 초대/회수 UI·변경 감사·기기 분실 복구는 관리자 수와 관리 기능을 확장할 때 구현한다. 현재 단일 계정의 서버 소유 Auth metadata 선택을 일반 사용자에게 관리자 권한을 부여하는 경로로 넓히지 않는다.

위는 초기 계정 생성과 구현 경계다. 자동 검사·브라우저 로그인·회사 DB 적용·사용자 영구 비밀번호·선택된 추가 확인은 각각 별도 완료 조건으로 추적한다.

### 최신 선택 — 비밀번호 + 이메일 코드 확인

초기 수신자는 최신 Auth 사용자 이메일이 `lnkgroupsydney@gmail.com`인 경우로 제한하며 요청 본문의 수신자 값은 사용하지 않는다. 기존 회사 Resend 설정을 재사용한다. 6자리 코드는 10분 유효·60초 재발송 대기·challenge당 오답 5회 제한이며 사용자별 발송/검증 제한도 적용한다. 서버 비밀키로 만든 HMAC만 저장하고 사용자·현재 이메일 해시·Auth 세션·challenge에 귀속한다. 재발송은 이전 코드를 폐기한다.

발송 확인과 코드 검증은 서버 전용 RPC에서 처리한다. 검증 증거는 기존 앱 세션 만료(최대 8시간)를 넘지 않으며 로그아웃·세션 삭제 시 함께 제거한다. 현재 membership·실제 Auth 세션·비밀번호 변경 의무는 계속 확인한다. 이 검증은 Supabase TOTP MFA나 `aal2`가 아니다.

사용자 승인 후 [`20261004031640_staff_email_verification.sql`](../../supabase/migrations/20261004031640_staff_email_verification.sql) 적용 성공, service RPC의 미발급 상태 `null`, anon의 RPC/테이블 접근 `42501`을 확인했다. 로컬 앱에서 실제 발송 요청 후 Resend 수락·서버 `sent`와 코드 입력/카운트를 확인했다. 이후 사용자가 이메일 수신·코드 인증 완료를 확인했다. 실제 DB의 활성 `verified` 기록 1개와 `code_hash=null`, 새 관리자 탭의 업무 화면·기존 제출 비공개 사진 열람·새로고침 복원을 확인했다. PDF 본문은 브라우저 다운로드 제한으로 미확인이다. 이메일 확인을 Supabase `aal2`로 변경하지 않았다. 전체 업무 검사 320/320·lint·타입·격리 production 빌드 결과와 실제 연결 결과는 [이메일 검증 기록](../verification/2026-10-04-staff-email-verification.md)에서 구분한다.

## 고객 한 명으로 이력을 연결하는 방법

현재 고객 정보는 문의, 작성 초안, 제출 snapshot에 흩어져 있다. 이름·이메일이 같아도 동일인으로 자동 합치지 않는다. 고객 마스터가 없다는 사실을 숨기지 않고 **미연결 기록함 → 후보 대조 → 관리자 확인 → 연결** 흐름을 제공한다.

| 논리 데이터 | 새로 필요한 정보 / 원본 | 규칙 |
| --- | --- | --- |
| customers | 내부 고객 ID, 회사 범위, 표시명, 상태, revision | 내부 ID를 식별 기준으로 사용, 사업자/개인 타입은 실제 필요 시 도입 |
| customer_contacts / addresses | 연락처·주소, 출처·확인 여부·변경 이력 | 현재 연락처 변경이 과거 계약 주소·서명을 바꾸지 않음 |
| customer_record_links | 고객 ID, 원본 종류/ID, 연결 근거·행위자·시각 | 같은 원본의 충돌 연결 금지, 해제/재연결 이력 보존 |
| quote/submission | 기존 초안·불변 제출·PDF·서명 hash | 원본 유지, 데모/운영과 버전 표시. 계약 목록은 원본 참조 |
| booking/project | 기존 제안·고객 동의·회사 확정·작업 구간 | 고객 희망일·확정·Google 변경 검토를 별도 상태로 조회 |
| order/payment/invoice | 후속 구매·결제·청구 모듈의 원본 참조 | 견적 총액을 매출로 계산하지 않음, 상태별 금액 분리 |
| staff_memberships | Auth 사용자 ID, 회사·역할·활성 여부 | 후속 논리 모델. 첫 계정은 위 서버 소유 Auth metadata를 사용하며 별도 테이블·권한 관리 UI·감사는 미구현 |
| admin_audit_events | 행위자·대상·작업·결과·이유·시각·request ID | 업무 변경과 감사 기록의 일관성 확보, 일반 관리자 수정 불가 |

테이블 이름은 논리 모델의 제안이다. 기존 schema의 이름·제약과 대조 후 migration을 만든다. 단일 회사부터 시작하며 다른 회사 데이터가 섞이지 않게 회사 범위를 고정한다. 다회사 SaaS·요금제·테넌트 관리 화면은 만들지 않는다.

고객 상세는 요약, 문의/견적·계약, 예약/작업, 구매/결제, 문서/사진, 처리 이력으로 구성한다. 검색 조건은 이름·확인된 연락처·참조번호·상태·기간부터 제공하고 페이지네이션·조회 한도를 둔다. 민감 검색어와 원문 개인정보를 분석 도구·일반 로그로 보내지 않는다. 연결 근거가 약한 Gmail 발신 주소는 확인되지 않은 출처로 표시한다.

중복 병합은 먼저 양쪽 자료·충돌을 미리 보여주고 확인 사유를 기록한다. 자동 삭제/덮어쓰기 대신 대표 고객 ID와 연결 이력을 보존해 잘못 연결한 기록을 분리할 수 있게 한다. 고객 계정과 과거 거래 연결에는 별도의 소유 확인이 필요하며 관리자의 분류만으로 고객 로그인 계정에 거래 접근을 자동 부여하지 않는다.

## 보존할 업무 규칙

- **계약:** 고객이 확인한 가격·범위·약관·날짜·사진 manifest·서명 hash·PDF 버전은 고정한다. 고객 마스터나 운영 메모를 수정해도 과거 제출 원본은 바뀌지 않는다. 조건 변경은 새 revision·고객 재동의/재서명으로 처리한다. 회사 데모를 실제 계약으로 일괄 전환하지 않는다.
- **예약:** 요청 → 회사 기간 제안 → 필요한 재동의 → 전체 구간·자원 충돌 검사 → 원자적 확정 순서를 보존한다. 관리자 달력 드래그나 Google 변경도 동일 사용 사례를 거친다. 운영 근무시간·인원·취소 규칙은 미정값을 채워 넣지 않는다.
- **청구:** 마지막 작업 뒤 권한 있는 사용자의 Complete가 발행 조건이며 일정 종료만으로 실행하지 않는다. 최종 인보이스 중복을 막고 실제 발행일 +3 달력일(Sydney)의 기존 정책을 유지한다. 지급·청구·예약 상태는 독립적으로 기록한다.
- **결제:** 제공자 검증 결과나 증빙이 있는 승인된 수동 입금 절차를 통해 갱신한다. 관리자 표시 버튼만으로 카드 결제 성공을 만들지 않는다. 환불·취소·배송·재고 복귀는 서로 다른 사건이다.
- **자동화:** 회사 DB를 업무 원본으로 유지하고 같은 트랜잭션에 후속 outbox를 기록한다. worker 재시도·응답 유실에도 이메일/Calendar/청구가 중복되지 않도록 기존 중복키·lease를 보존한다. provider 수락은 실제 배달 성공과 다르다.
- **사진:** 비공개·소유/관리자 권한·정규화·제출 참조를 유지한다. 제출에 고정된 사진을 일반 삭제 API로 지우지 않는다. 운영 보관기간·접근 목적·삭제 요청 처리는 회사 정책 확인 후 구현한다.

## 구매와 보고서

‘구매’는 우선 **고객 상품 주문**으로 가정했다. 초기 ESN에는 구매 기능 준비 상태를 정직하게 표시하고 [쇼핑몰·재고 계획](../plans/06-commerce-and-inventory.md)의 상품/주문/결제/배송이 구현되면 같은 고객 ID로 연결한다. 회사 자재 매입까지 원하면 공급업체·발주·입고·원가·매입 증빙을 별도 업무로 추가한다. 고객 주문과 매입을 같은 상태 모델로 섞지 않는다.

보고서는 계약액, 발행액, 입금액, 환불액, 미수액을 분리한다. 각 수치에 기간 기준·통화·세금 처리·취소 제외·자료 출처를 정의한다. 데모·시험 기록은 운영 집계에서 제외하고 미연결/수집 오류를 0으로 집계하지 않는다. 계산 및 회계 처리 정책이 정해지기 전에는 샘플 수치를 실제 매출로 표시하지 않는다.

## 이관·감사·복구

기존 레코드의 ID·건수·hash 기준선을 확보하고 합성/시험 자료로 고객 연결 규칙을 검증한다. 과거 서명 snapshot은 수정하지 않고 별도 링크로 연결한다. 부분 실패는 실패행·원인·재시도 배치로 남기며 재실행에도 중복 고객·링크가 생기지 않게 한다. 미연결 자료는 남겨 두고 연결률을 보고한다.

변경·권한 회수·문서 열람·내보내기 이벤트의 기록 범위를 정한다. 감사 로그에는 비밀번호·토큰·사진 바이트·서명 원본·전체 개인정보 payload를 남기지 않는다. 내보내기는 필드·기간·건수 제한, 추가 확인과 다운로드 만료·감사를 적용한다. CSV 수식 주입도 검증한다. 대량 내보내기와 삭제는 첫 조회 MVP에서 활성화하지 않는다.

DB 복구와 Storage 객체 복구를 각각 시험하고 복구 목표·보관기간·담당자를 회사와 정한다. 개발/Preview에는 실제 고객 정보를 복사하지 않는다. 이 문서는 설계이며 개인정보 보관기간이나 법적 계약 효력을 확정하지 않는다.
