## ESN-01: 자기 세션 관리와 복구 안내

### 서버 계약

- `GET /api/admin-auth/sessions`: 추가 확인을 마친 현재 본인의 유효 `mode='staff'` 세션만 조회한다. 응답에는 현재 세션의 만료 시각, 다른 유효 ESN 세션의 정확한 개수, 제한된 만료 시각 목록만 포함한다. 목록은 최대 50개와 `truncated` 등 잘림 표시를 둔다. 실제 기기 수나 전체 Supabase 로그인 수로 설명하지 않는다.
- `POST /api/admin-auth/sessions/revoke-others`: 같은 출처의 빈 JSON 객체를 받는다. 사용자 ID·대상 세션·회사·역할을 클라이언트에서 선택하지 않는다. 서버가 검증한 본인 ID와 현재 token hash만 사용한다.
- 자기 세션 관리에는 활성 `admin`과 `owner` 모두 접근한다. 미확인·만료·회수·레거시 세션은 거절한다. `staff.manage` 권한을 자기 로그아웃 관리에 추가하지 않는다.
- 응답에 token hash·JWT·Auth session ID·다른 직원 정보를 보내지 않는다. `private, no-store`와 `Vary: Cookie`를 유지한다.

서비스 역할 전용 invoker RPC 하나에 목록/종료 명령을 두어도 된다. 종료는 본인 ID별 트랜잭션 잠금 → 현재 registry 행의 본인 소유·staff 모드·유효성 재검사 → 현재 hash를 제외한 같은 계정의 registry 삭제 순서다. `PUBLIC`/`anon`/`authenticated` 실행을 차단하고 고정 `search_path`를 적용한다. 기존 Auth schema의 세션을 직접 수정하지 않는다.

```text
ready 본인 + same-origin
  → 본인별 DB 잠금
  → 현재 ESN 세션 재검사 ── 실패 → 거절, 제공자 호출 없음
  → 다른 ESN 세션 삭제 + 이메일 증거 cascade
  → Auth signOut(scope=others)
      ├─ 성공 → 현재 세션 유지, 종료 결과 갱신
      └─ 실패 → ESN 접근 종료/제공자 정리 미확인 구분, 재시도
```

두 세션 A/B가 동시에 실행할 때 A가 먼저 B의 registry를 지우면 B는 잠금 이후 재검사에서 실패해야 한다. B가 제공자 `signOut`까지 진행해 A도 종료하는 경합을 막는다. 제공자 호출 전 새 로그인과의 경합은 목록의 시점 한계를 명시하며, DB/제공자를 하나의 원자적 트랜잭션이라고 표현하지 않는다.

DB 삭제 실패 때 제공자 전체 종료를 대신 호출하지 않는다. DB 삭제 성공 후 제공자 실패는 전체 성공으로 표시하지 않는다. 현재 쿠키·registry·이메일 증거·owner membership을 보존한다. 재시도는 이미 삭제된 다른 registry가 0개여도 안전해야 한다.

### 화면과 복구

기존 관리자 업무 화면에 독립 세션 패널을 붙인다. `This session`, 만료 시각, 다른 ESN 세션 개수, `Sign out other sessions`와 현재 세션을 유지한다는 설명을 제공한다. 실행 전 확인과 실행 중 중복 방지, 종료 결과·부분 실패·재시도를 표시한다. 다른 세션이 없으면 정상 빈 상태를 보여준다.

로그인/접근 불가/이메일 확인 화면에는 ESN 비밀번호와 Google 비밀번호가 다름, 기존 코드의 만료/재발송 방법, 계정 접근을 잃으면 회사 계정 관리 책임자와 회사 Supabase 프로젝트 접근 권한을 가진 담당자가 본인 확인 후 복구해야 한다는 안내를 제공한다. 미확정 담당자 연락처·복구 완료 버튼·임의 비밀번호 초기화 메일은 만들지 않는다. 초대·역할/마지막 owner 변경·비밀번호/이메일 분실 복구의 실제 실행은 후속이다.

## ESN-02: 고객 분류와 통합 조회

### 최소 데이터와 경계

`src/modules/customers`에 domain/application/infrastructure/presentation을 필요한 만큼만 둔다. 업무 접근은 기존 `operations.read`/`operations.write`로 확인하고 회사는 서버에서 `lk-group`으로 고정한다. 신규 클라이언트 직접 DB 읽기·다회사 SaaS·독립 DB는 도입하지 않는다.

| 논리 테이블 | 최소 계약 |
| --- | --- |
| `lk_customers` | UUID, 고정 company, name·선택 email/phone/address, revision, 생성/갱신 시각. 이메일/전화의 유일 제약으로 사람을 합치지 않는다 |
| `lk_customer_record_links` | 회사·원본 종류/ID별 하나의 연결 상태, 고객 FK, 변경 행위자/시각. 해제/재연결도 고객 revision과 감사로 추적한다 |
| `lk_customer_audit_events` | 고객/원본 ID, create/link/unlink, 이전·이후 연결, 이유, 검증된 행위자, 시각, request/idempotency key와 요청 hash. 일반 조회 화면/API에서 수정·삭제하지 않는다 |

모든 새 테이블은 RLS를 켜고 공개 역할 권한을 회수한다. 서비스 역할만 필요한 접근을 가지며 새 RPC 실행 권한도 별도 제한한다. 링크 변경과 감사, 중복 요청 기록은 같은 트랜잭션으로 처리한다. 로컬 SQL 파일은 CLI의 `supabase migration new`로 생성하고 전체 기존 migration 체인과 함께 검증한다.

연결 원본은 일반 `enquiry`와 서명된 `submission`이다. 제출에서 생성된 enquiry는 별도의 고객에게 연결하지 않고 제출 묶음으로 표시한다. 원본 목록과 변경 명령 모두 `submission.enquiry_id` 및 기존 `demoSubmissionId` 관계를 확인한다. 제출 관련 문의/예약/PDF/사진은 그 제출의 고객 관계를 따른다. 이메일 전송 worker가 제출의 enquiry를 나중에 생성해도 새 미연결 고객 기록처럼 중복 표시하지 않는다.

미제출 작성 초안의 별도 분류·고객 마스터의 연락처 편집·대량 import·고객 간 병합은 이번 묶음에서 만들지 않는다. 기존 초안과 제출 snapshot은 보존한다. 연락처는 원본의 출처와 함께 표시하고 Gmail 발신 주소나 관리자의 연결을 신원 확인 완료로 표시하지 않는다.

### API와 저장 규칙

확정 외부 경로는 `/api/admin/customers`다. 공통 타입의 원본은 `src/modules/customers/domain/contracts.ts`이며 UI는 이 계약을 사용한다. `GET /`은 `{customers,page,pageSize,total}`, `POST /`는 `{customer}`, `GET /[id]`는 `{customer,records,audit,purchases:{status:'unavailable'},billing:{status:'unavailable'}}`, `GET /unlinked`는 페이지가 있는 원본 목록, `POST /[id]/links`는 연결/해제를 처리한다.

| 행위 | 입력·결과 |
| --- | --- |
| 고객 목록/검색 | `q`, `page`, `pageSize`로 이름·연락처·참조번호 검색과 유한 페이지. 서버 검색/조회 한도와 정렬 기준을 고정한다. 전용 종류/상태/기간 필터는 ESN-02 후속으로 추적한다 |
| 고객 생성 | `name`, 선택 `email/phone/address`, `idempotencyKey`. 원본에서 이름을 제안해도 사용자가 확정한다. 같은 연락처의 다른 고객 생성 허용 |
| 미연결 기록 조회 | 원본 종류·ID·참조번호·연락처 출처·데모 여부. 전체 서명/메일 원문/사진 바이트는 목록에 넣지 않는다 |
| 연결 | `action:'link',sourceType,sourceId,reason,expectedRevision,idempotencyKey`. 기대 revision은 선택한 고객의 현재 revision이며 원본 존재/기존 연결 충돌도 서버/DB에서 재검사 |
| 해제 | 같은 입력의 `action:'unlink'`. 고객 revision·현재 연결 대상 검사, 행위 이력을 보존하고 다른 고객으로 조용히 덮어쓰지 않음 |
| 고객 상세 | 연결된 원본 요약·문의/제출·예약 상태·문서/사진 참조·연결 처리 이력. 구매/청구는 미구현 상태 |

링크 변경은 원본 잠금과 고객 revision 검사·증가를 함께 수행한다. 같은 요청의 재전송은 동일 결과로 복원하며, 같은 key로 내용이 달라지면 충돌로 거절한다. 서로 다른 고객이 같은 원본을 동시에 연결하면 한쪽만 성공해야 한다. 존재하지 않는 원본·다른 회사·잘못된 종류·오래된 revision·과도한 입력·제어 문자를 거절한다. 수정 사유·actor는 링크 감사에 남기되 토큰·사진·서명·전체 개인정보 payload를 감사/일반 로그에 복제하지 않는다.

고객 ID·표시명 변경이나 연결/해제가 제출 snapshot/hash·기존 문의 payload·예약 revision·고정 문서·사진 manifest를 변경해서는 안 된다. 읽기 중 원본이 없거나 조회가 실패하면 항목별 사용 불가/오류를 표시한다. 오류를 빈 이력·0원 매출로 치환하지 않는다.

### 화면 계약과 접근성

- 기존 Operations 흐름을 유지하고 `Customers` 섹션/탭을 추가한다. 고객 UI는 독립 컴포넌트/스타일로 구현한 뒤 주 에이전트가 연결한다. 세션 구현자가 작업 중인 `staff-admin-console.tsx`를 동시에 편집하지 않는다.
- 검색은 명시적 제출과 페이지 이동으로 동작한다. 검색 변경 시 첫 페이지로 이동하며 늦게 도착한 이전 검색/상세 응답이 현재 결과를 덮지 않게 한다. 고객 목록은 모바일 카드, 상세는 모바일에서 세로 흐름으로 제공한다.
- `Create customer`는 입력 검증·저장 중 상태·실패 후 값 보존·성공 후 선택을 제공한다. 자동 고객 생성이나 입력 연락처 자동 병합은 하지 않는다.
- 미연결 기록에서 원본을 선택하면 참조번호·이름/연락처·출처·데모 여부와 대상 고객을 함께 보여준다. 이유 입력 후 명시적으로 확인해 연결한다. 연결 해제도 같은 수준으로 확인한다. 충돌 시 재조회하도록 안내한다.
- 상세의 문의·서명 제출·예약·처리 이력을 읽고 PDF/사진은 기존 보호된 원본 경로를 사용한다. 원본 보기를 위한 기존 API는 계속 독립 인가한다. PDF 다운로드·사진 오류를 연결 성공과 혼동하지 않는다.
- 구매/청구는 `Not available yet` 등 준비 상태로 표시하고 0건 구매·0원 매출로 단정하지 않는다. migration 미적용 등 준비 대기, 실제 빈 고객, 검색 결과 없음, 통신 실패를 구분하고 재시도를 제공한다.
- 폼 label, 키보드 순서, 명확한 확인 버튼, 처리 상태/오류 알림, 상세 진입/복귀 포커스를 제공한다. 320px에서 가로 넘침 없이 긴 이름·이메일·참조번호가 줄바꿈되고 모든 핵심 동작에 접근할 수 있어야 한다.

## 위험·대안과 이번 제외 범위

- **세션 전체 종료 대신 현재 보존:** 단일 owner의 작업 연속성을 지킨다. 이 기능은 탈취된 비밀번호 변경이나 계정 복구를 대신하지 않는다. 본인 재로그인 자체를 차단하는 권한 회수 기능으로 보고하지 않는다.
- **별도 링크 대신 원본에 customer_id를 일괄 쓰는 대안:** 불변 원본과 worker 관계를 건드릴 수 있어 채택하지 않는다. 작은 링크/감사 테이블로 복구 가능하게 유지한다.
- **전체 자료를 받아 브라우저에서 검색하는 대안:** 원문 노출·메모리·응답 크기를 늘리므로 서버에서 필요한 projection과 페이지 한도를 적용한다. 고객 상세에서 파일은 사용자가 요청할 때 읽는다.
- **성능:** 회사/고객과 원본 식별 인덱스, 안정 정렬, 목록 DTO와 상세 분리를 적용한다. 현재 규모에 새 검색 엔진·캐시·이벤트 버스는 필요하지 않다. 민감 응답은 공유 캐시하지 않는다.
- **미포함:** 실제 초대/발송 확대·별도 membership/역할 관리·마지막 owner 강등·분실 계정 복구 실행, 고객 계정/소유 인증·대량 병합/import/export/delete, 운영 가격/계약·예약 정책·인보이스/결제·구매·배포. 각 항목은 기존 ESN 단계/결정 대기로 유지한다.

오늘 코드와 합성 검사가 끝나도 ESN-01 전체와 ESN-02 회사 인수가 자동 완료되는 것은 아니다. 원격 SQL 적용, 실제 고객 분류, PDF/사진 실열람, 추가 관리자·회수/복구의 남은 조건을 분리해 기록한다.
