KCP AI(P4)·실제 정찰제(P5)의 대기를 고객 조회 시스템으로 숨기거나 완료 처리하지 않는다. 사진/서명 관련 남은 실기기 검증은 [35번](../plans/35-mobile-booking-private-photo-plan.md)에서 계속 추적한다. 회사 계정으로 이미 승인된 연결 범위는 유지하고 신규 서비스·유료 자원·운영 전환은 별도 의존성으로 관리한다.

## 첫 구현 묶음

### 2026-10-04 후속 요청 — Google 결제 대기 중 첫 착수

사용자가 ESN 구현 착수를 요청하고 먼저 첫 작업을 정리하도록 했다. Google Places 주소 자동완성의 결제/키 준비는 관리자 접근 기반의 선행 조건이 아니다. 주소 제공자 `src/shared/address/google-places.ts`는 별도 Maps 키를 사용하며 관리자 접근·회사 OAuth 코드는 이 키에 의존하지 않는다. 이번 확인은 코드 조사이며 실제 Google 결제 상태를 조회한 것은 아니다.

**첫 목표: ESN-01 관리자 로그인·접근 권한 기반.** 기존 단일 앱에서 로컬 관리자 경계부터 개발한다. 실제 도메인과 구매 범위의 미확정은 이 작업을 막지 않는다.

| 순서 | 첫 단계 작업 | 결과·완료 기준 |
| --- | --- | --- |
| 01a | 보호 대상·접근 규칙 정리 | `/admin`, `/api/operations/**`, PDF/사진, `/api/google/connect`·`callback`과 고객 API 구분. 로그인 예외와 회사 연동 권한 정의 |
| 01b | 공통 관리자 인가 모듈 | 개별 사용자 ID·활성 membership·추가 확인 규칙과 인증/권한 조회 포트. 합성 계정으로 비인증·고객·미초대·추가 확인 미완료·회수 계정 거절 시험 |
| 01c | 로그인·세션·관리자 화면 연결 | 로그인·로그아웃·세션 만료·권한 없음·추가 확인 안내와 서버 페이지/API 보호. 공용 로컬 세션을 개별 관리자 인증 완료로 변환하지 않음 |
| 01d | 문서/사진·변경 API·권한 회수 | 파일 URL 직접 호출도 인가, 변경 요청의 Origin/CSRF·revision 유지. 회수 뒤 기존 세션 접근 거절 |
| 01e | 회귀 검증·진행 갱신 | 고객 작성/사진/서명/예약·회사 연동 보존. 자동 검사·브라우저·실제 Auth/MFA 연결 결과 구분 |

01a에서 확인한 기존 경로와 적용 경계는 다음과 같다. 신규 로그인/MFA 경로는 구현 시 별도 정의한다.

| 현재 경로 | 적용 경계 |
| --- | --- |
| `/admin` | 현재 로그인/업무 화면 공존. 로그인 진입과 보호된 업무 화면 분리 |
| `POST /api/operations/login`, `GET /api/operations/session` | 로그인 전 정확한 예외. 입력·요청 제한·필요한 세션 상태만 반환 |
| `POST /api/operations/logout` | 현재 세션·Origin 확인. 무인증 예외와 구분 |
| `/api/operations`·일정/문의/Gmail 하위 업무 API | 각 핸들러에서 관리자 인가·변경 요청 검사 |
| `/api/operations/bookings/**`의 조회·제안·확정·PDF·사진 | 관리자 인가와 기존 revision/동의·원본 보호 |
| `/api/google/connect`, `/api/google/callback` | 현재 로그인/회사 연결 겸용. 아래 전환 규칙 적용 |
| `/api/enquiries`, `/quote/start`, `/api/quote/**` | 고객 접수·작성 권한 유지. 관리자 로그인 강제 대상에서 제외 |

접근 정책은 **비인증/일반 고객 → ESN 데이터 없음, 추가 확인 미완료 관리자 → 설정/확인 흐름만, 활성 관리자 → 허용 업무, 회수 관리자 → 기존 세션도 거절**이다. 로그인 전 세션 확인 응답은 필요한 로그인 상태만 제공하고 내부 설정/회사 연결 상세는 인가 뒤 반환하도록 설계한다.

최초 계획 당시 Google connect/callback은 관리자 로그인과 회사 Gmail·Calendar 연결을 겸했다. 로그인 없이 시작한 callback이 관리자 세션을 발급하므로 `/api/google/*`를 일괄 차단하면 기존 로그인이 끊긴다. 새 직원 인증을 먼저 준비하고 **직원 로그인과 회사 연결/재연결을 분리**한다. 전환 후 회사 연결 시작은 별도 관리자 권한을 확인하고 callback은 state/nonce/PKCE·요청 세션을 검증한다. 전환 전 기존 loopback 경로를 유지하되 새 ESN에는 구 세션을 통한 우회가 없어야 한다.

실제 관리자 명단 없이도 로컬 합성 계정으로 01b를 시작할 수 있다. 실제 초대·메일 전달·선택된 추가 확인/복구·운영 세션 검증 전에는 ESN-01 전체를 완료로 표시하지 않는다. 주소 검색은 결제 완료 후 34번 실연동을 병행한다.

### 같은 날 앞선 구현 기록 — 01b 완료, 01c~01e 일부 진행

- **01b:** 순수 TypeScript `admin-access` 모듈에 서버 세션 검증·membership 조회·시계 포트를 만들었다. 매 요청마다 세션 만료와 `aal2`, 동일 사용자/회사의 활성 `admin`/`owner`, 요청 업무 권한을 검사한다. 조회 중 만료도 재검사하며 제공자 오류는 내부 정보를 숨긴 오류로 처리한다. 합성 포트로 미인증·고객·미초대·회수·MFA 미완료·권한 초과를 시험했다.
- **01c~01d 일부:** 기존 SQLite/Supabase 데모 경로는 명시적 로컬 사용 설정·설정된 요청 host·내부 loopback·유효 세션을 확인한 뒤 DB와 업무 데이터에 접근한다. 커스텀 Google 세션에도 같은 조건을 적용한다. 로그인 전 API/UI에서 회사 이메일·내부 설정을 숨기고 업무 JSON 응답을 `private, no-store`·`Vary: Cookie`로 반환한다. 이 당시 구현은 개별 직원 로그인 또는 MFA 인증 제공자를 연결한 것이 아니었다. 이후 연결은 아래 첫 계정 온보딩 기록을 따른다.
- **01e 일부:** 정책·두 저장소의 API 경계·문서/사진 접근과 기존 고객 업무 회귀 검사를 추가하고 CI에 `test:operations`를 연결했다. 정확한 실행 수·브라우저 결과·실패 수정은 [검증 기록](../verification/2026-10-04-esn-admin-access.md)을 따른다. 합성 DB/전송 검증과 회사 실연동 검증을 구분한다.
- **당시 남은 인수 범위:** 실제 관리자 세션 검증 어댑터·membership 스키마/조회, 초대·MFA 등록/복구·권한 회수 UI, 보호된 관리자 화면과 운영 host 전환. 이 앞선 단계에서는 원격 DB·외부 계정·비용·DNS·배포 변경을 수행하지 않았다.

### 같은 날 후속 — 첫 관리자 계정·회사 DB·앱 로그인

지정 계정 `lnkgroupsydney@gmail.com`을 회사 Auth에 생성하고 로그인·비밀번호 교체·MFA 어댑터와 화면을 연결했다. 첫 membership은 서버 소유 Auth `app_metadata`를 매 요청 최신 조회하며 별도 테이블/관리 UI는 후속이다. 직원 모드의 Google 연결은 현재 직원 세션과 owner 권한을 요구한다.

사용자가 세션 검사 migration을 회사 DB에 적용했다. 실제 서비스 RPC는 유효 세션만 허용하고 다른 사용자·로그아웃·null 세션을 거절했으며 anon/authenticated는 `42501`로 차단했다. 기존 로컬 앱(3002)의 직원 인증을 활성화해 재빌드·실행하고 브라우저 로그인 후 `password_change` 화면을 확인했다. 앞선 자동 검사 294개와 새 실제 연결 증거는 [온보딩 검증](../verification/2026-10-04-staff-admin-onboarding.md)에서 구분한다.

사용자가 ESN 전용 영구 비밀번호를 저장했고 서버의 변경 의무 해제를 확인했다. MFA 등록 중 실제 SDK의 SVG 데이터 URI 형식을 처리하지 못해 QR이 표시되지 않는 문제를 수정했다. 회귀 검사 3개를 포함한 관리자 검사 67개·lint·타입·빌드가 통과했으며 로컬 앱에 반영했다. 당시 TOTP 등록은 완료하지 않았으며 이후 휴대폰을 사용할 수 없는 사용자의 요청으로 아래 이메일 방식을 선택했다. 당시 업무 API·PDF·사진·로그아웃/회수 인수는 남아 있었으며 이후 이메일 방식의 실제 업무 접근은 아래 기록을 따른다. 비밀번호 완료나 코드 검증을 실제 TOTP MFA·ESN-01 전체 완료로 표시하지 않는다. 운영 host·초대/분실 복구·다중 관리자 관리는 남아 있다.

### 최신 후속 — 휴대폰 없이 이메일 코드 확인

사용자가 영구 비밀번호 이후 이메일 코드로 진행하도록 선택했다. `STAFF_ADMIN_SECOND_STEP=email`에서 서버의 최신 Auth 사용자·지정 회사 이메일·현재 세션에 귀속된 증거를 확인한다. 기존 TOTP 미완료를 이 방식의 선행 조건으로 두지 않고, 이메일 성공을 Supabase `aal2`/MFA 완료로 표시하지 않는다.

6자리 코드의 10분 만료·60초 재발송 대기·5회 오답 제한·HMAC 저장과 세션별 일회 검증을 구현했다. 전체 업무 검사 320/320·lint·타입·격리 production 빌드가 통과했다. 사용자 승인 후 이메일 검증 migration 적용 성공·service RPC 응답·anon 차단과 로컬 앱의 이메일 확인 화면을 검증했다. 실제 발송 요청 후 Resend 수락·서버 `sent`와 코드 입력/카운트를 확인했다. 이후 사용자가 이메일 수신·코드 인증과 관리자 진입을 확인했다. 실제 DB의 활성 검증 1개·코드 해시 제거와 새 관리자 탭의 문의 7건·서명 데모 요청 4건·Calendar/Gmail 영역을 확인했으며 콘솔 오류·경고는 없었다. 기존 `DEMO-F628C5C6` 상세의 제출 사진 1개가 실제 로드됐고 새로고침 후 인증·업무 화면도 유지됐다. PDF 본문은 브라우저 다운로드 제한으로 확인하지 못했으며 권한 실패로 판정하지 않는다. [이메일 검증 기록](../verification/2026-10-04-staff-email-verification.md)을 기준으로 PDF·로그아웃/회수 인수를 이어간다. 초대·회수/복구 UI 등 ESN-01 전체는 후속이다.

### 전체 구현 묶음과의 연결

1. **접근 계약:** 현재 모든 `/admin`, `/api/operations`, PDF/사진, OAuth 진입점을 목록화하고 허용/거절 표·합성 관리자 계정을 만든다. 기존 loopback 제한을 해제하지 않는다.
2. **관리자 인증:** 기존 커스텀 세션과 새 인증의 전환/만료를 정의한다. 개별 관리자·선택된 추가 확인·membership·회수·초대 실패를 구현한다. 회사 Google 통합 로그인과 혼동하지 않는다.
3. **읽기 단위:** 합성 고객 1명에 기존 문의·불변 제출·예약·사진 참조를 연결하고 고객 상세에서 조회한다. 연락처만 같은 다른 고객, 미연결 기록, 없는 문서·권한 오류를 함께 검증한다.
4. **목록과 검토:** 검색·페이지네이션·상태 필터, 고객 연결 후보와 확인 기록을 붙인다. 고객/운영 UI 320·390px와 데스크톱·키보드·실제 기기를 구분해 확인한다.
5. **회사 검토:** 읽기 MVP의 결과와 남은 운영값을 검토한 뒤 업무 변경·청구·구매를 단계적으로 연결한다.

실제 구현에서는 단계별 작은 PR에 변경한 권한/데이터·검증·롤백을 기록한다. 공용 상태 규칙 변경은 고객 화면과 관리자 화면 양쪽을 회귀 검증한다. 계획 브랜치에 장기간 모든 기능을 쌓아 관리하지 않는다.

## 일정·비용 산정 방식

달력 납기는 아직 확정하지 않는다. ESN-01의 운영 인증 전환, ESN-02의 고객 연결 품질, ESN-03·04의 운영 정책·외부 의존성이 주요 변수다. 첫 구현 묶음의 실제 작업량을 확인한 뒤 단계별 범위·공수·외부 대기·검증 시간을 나눠 산정한다. 기존 ‘메인 3일·Cabinet 약 1주’ 또는 전체 프로젝트 18~24주를 ESN 납기로 재사용하지 않는다.

운영비 검토 항목은 기존 회사 DB/Auth/Storage 사용량, 관리자 배포 방식, 이메일, worker, 로그/백업과 추후 결제 비용이다. 독립 앱을 선택하면 빌드·배포·운영 관리 부담도 재산정한다. 현재 문서는 유료 서비스 신청이나 비용 승인으로 간주하지 않는다.

## 구현 전 확인할 근거

2026-10-04 [Next.js 인증](https://nextjs.org/docs/app/guides/authentication), [Supabase MFA](https://supabase.com/docs/guides/auth/auth-mfa), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)를 확인해 인증 경계의 기준으로 삼았다. 제품 API·배포 설정은 실제 구현 때 다시 확인한다. Supabase changelog Markdown은 읽기 도구의 content-type 제한으로 열리지 않아 [HTML 변경 기록](https://supabase.com/changelog)을 확인했다. 신규 엔진/패키지 도입은 이번 범위가 아니며 원격 DB 버전·확장 호환성 검사도 미실행이다. schema 작업 전에 관련 변경 영향과 수동 migration 이력을 별도로 대조한다.
