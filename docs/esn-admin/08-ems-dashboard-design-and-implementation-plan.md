# L&K Group EMS 대시보드 — 디자인·UX와 적용 계획

2026-10-06 · Australia/Sydney · **설계 제안 / 앱 구현 미착수**
,
사용자의 두 참고 이미지와 현재 관리자 코드를 대조한 계획이다. 이번 요청은 디자인·UX 검토와 기존 admin 적용 계획까지이며, 앱 코드·DB·권한·배포는 변경하지 않는다. 사용자가 이번에 부른 **EMS**를 화면의 작업 명칭으로 사용하되, 기존 `docs/esn-admin`·ESN 요구 ID·DB 명칭은 유지한다. 상표·도메인·저장소를 이름 때문에 바꾸지 않는다.

## 1. 권장 방향

**첫 화면에서 오늘의 업무와 확인할 문제를 파악하고, 숫자·그래프를 눌러 해당 목록과 고객 상세로 이동하는 운영 대시보드**를 만든다. 모든 원본을 한 페이지에 펼치는 대신, 전사 요약 → 업무 목록 → 고객·기록 상세의 3단계로 관리한다.

- 참고 이미지 1의 고정 사이드바, 업무 요약 카드, 그래프 옆 일정, 하단 목록을 기본 골격으로 쓴다.
- 참고 이미지 2의 정돈된 여백, 큰 숫자, 부드러운 카드 모서리를 일부 반영한다. 큰 인사 문구와 위젯 꾸미기는 업무보다 앞세우지 않는다.
- 글로벌 **Slate / Greige + Manrope**를 유지한다. 참고 이미지의 초록·보라 테마로 바꾸지 않는다.
- 기존 로그인·이메일 확인·고객 원장·예약 검토·PDF·사진·세션 관리와 업무 규칙을 재사용한다.
- 현재 없는 Job·재고·주문·회계 데이터는 별도 업무 모델을 연결한 뒤 표시한다. 준비 중을 0건/0원으로 바꾸지 않는다.

[레이아웃 검토용 와이어프레임](design/dashboard-wireframe.html)은 **1차 적용 화면 / 확장 목표 화면**을 비교하는 로컬 문서다. 숫자는 모두 가상 예시이며 회사 실적이 아니다. 실제 저장·예약 확정·외부 연동은 수행하지 않는다. 와이어프레임 완성과 제품 구현 완료를 구분한다.

이미지로도 볼 수 있다: [1차 적용 시안](design/dashboard-initial-desktop.png) · [확장 목표 시안](design/dashboard-target-desktop.png). 와이어프레임의 메뉴 전체 노출은 구조 검토용이며, 제품 모바일 메뉴 서랍·실제 검색·필터·드릴다운 동작은 아래 구현 계획의 후속이다.

사이드바는 Overview / 고객·서비스 업무 / 상품 업무 / 관리 항목으로 가볍게 그룹화한다. 현재 가능한 항목과 준비 중 항목을 텍스트로 구분한다. 준비 중 항목은 필요한 준비사항을 읽을 수 있는 화면으로 연결하며 작동하지 않는 생성·저장 버튼은 두지 않는다. 홈에 모든 메뉴의 카드를 반복하지 않는다.

상품을 고객에게 판매한 **주문**과 회사가 자재를 사는 **매입·발주**는 다른 업무다. 우선 Orders는 고객 주문으로 계획한다. 재고는 판매상품/작업자재 구분을 둘 수 있게 설계하되, 실제 취급 품목·단위·공급사 발주 포함 범위는 구현 전에 확인한다. 식품 재고가 포함되면 기존 식품 관련 계획의 lot·유통기한·배송 조건도 별도 적용한다.

## 4. Overview 화면 구성

1440px 안팎 데스크톱에서 사이드바 약 240px, 본문 여백 24~32px, 12열 그리드를 제안한다. 픽셀값은 구현·반응형 검토에서 조정할 초기 목표이며 전역 마케팅 타이포를 축소 변경하지 않는다.

```text
┌────────────────┬────────────────────────────────────────────────────┐
│ L&K Group      │ Overview                 고객·참조 검색 / 내 계정   │
│ EMS            │ 선택일 · Australia/Sydney · 조회 시각 · 새로고침   │
│                ├────────────────────────────────────────────────────┤
│ Overview       │ 확인 필요: 일정 변경 검토 / 연동 실패 → 해당 목록 │
│ Clients        ├────────────┬────────────┬────────────┬───────────────┤
│ Enquiries      │ 선택일     │ 미확정     │ 최근 7일   │ 고객 연결     │
│ & quotes       │ 확정 일정  │ 예약 요청  │ 접수 문의  │ 필요 원본     │
│ Schedule       ├─────────────────────────┬──────────────────────────┤
│ Jobs           │ 기간별 접수 추이         │ 선택일 일정 · 다음 일정  │
│ Orders         │ 일별 건수 + 상세 목록    │ 시간/종류/고객/상태      │
│ Inventory      ├─────────────────────────┤                          │
│ Reports        │ 현재 제출·예약 상태 분포 │ 전체 일정 보기           │
│                ├─────────────────────────┴──────────────────────────┤
│ Settings       │ 처리 목록: 고객 / 업무 종류 / 날짜 / 상태 / 다음 행동│
│ 내 계정        │ 최근 5~8건 + 전체 보기                            │
└────────────────┴────────────────────────────────────────────────────┘
```

첫 화면은 오늘 일정·확인할 문제·핵심 수치를 읽을 수 있게 한다. 전체 목록을 스크롤 없이 모두 넣는 것을 목표로 하지 않는다. 자료가 많은 큰 표는 전용 화면에서 검색·정렬·페이지 이동으로 관리한다.

### 핵심 상호작용

1. **숫자에서 목록으로:** KPI를 누르면 같은 날짜·상태·데이터 범위로 필터링된 목록을 연다. 차트에서 날짜를 선택해도 동일하다.
2. **목록에서 고객으로:** 행의 참조번호는 업무 상세, 고객명은 고객 상세로 이동한다. 미연결 자료에는 ‘고객 연결 필요’를 표시하고 원본 조회를 허용한다.
3. **요약에서 처리로:** ‘확인 필요’에는 일정 변경 검토·예약 동기화 실패·고객 연결 필요처럼 실제 처리 가능한 항목을 둔다. 통합 점수나 가짜 알림 개수는 만들지 않는다.
4. **상태 변경은 상세에서:** 홈의 그래프 클릭은 조회만 수행한다. 회사 확정·기간 변경·원본 연결/해제는 대상을 확인한 상세 화면에서 기존 확인·사유·revision 규칙을 거친다.
5. **입력 보존:** 상세 편집 중 메뉴를 바꿀 때 미저장 입력을 보호한다. 단순 조회는 방해하지 않는다. 성공 후 해당 카드·목록만 갱신하고 선택/스크롤을 복원한다.
6. **검색 범위 정직하게 표시:** 1차 검색은 ‘고객·원본 참조 검색’이다. 주문·재고가 연결되기 전까지 모든 데이터를 검색한다고 안내하지 않는다. 검색어에 연락처가 포함될 수 있으므로 URL/로그 노출 정책을 먼저 정한다.

### 필터의 범위

- **일정 기준일:** Sydney의 오늘이 기본. 선택일 KPI와 agenda만 변경한다.
- **추이 기간:** 최근 7일 기본, 30일·직접 기간으로 확장. 접수 차트에 적용하며 현재 미처리 건수를 기간으로 숨기지 않는다.
- **현재 상태 카드:** ‘현재 미확정’, ‘현재 고객 연결 필요’처럼 시점 기준임을 적는다. 기간 필터와 다른 기준을 카드에 명시한다.
- **데이터 범위:** 1차 회사 데모 자료에는 지속적으로 ‘회사 데모’ 표시. 향후 운영/데모를 분리하는 신뢰할 수 있는 원본 필드·정책을 먼저 추가한다. 구분할 수 없는 과거 자료는 억지로 운영에 포함하지 않는다.
- 필터 변경·뒤로가기·새로고침에서 같은 조회 조건을 복원한다. 허용된 비민감 상태/날짜/정렬만 URL로 보존한다.

## 5. KPI·그래프 정의와 데이터 준비 수준

### 1차 적용 지표

| 지표 | 집계 정의 | 유의사항 / 다음 이동 |
| --- | --- | --- |
| 선택일 확정 일정 | 확인된 확정 proposal 작업구간과 Sydney 선택일이 겹치는 **고유 booking 수** | 구간/Calendar event 수를 합하지 않음. 회사 데모 표기 → 동일 날짜 예약 목록 |
| 미확정 예약 요청 | 서명 제출과 booking을 LEFT JOIN하고 `COALESCE(status, 'requested')='requested'`인 고유 submission 수 | booking 행이 없는 최초 제출도 포함. 담당자 조치 가능 건수와 같다고 가정하지 않음 → 예약 목록 |
| 최근 7일 접수 문의 | Sydney 오늘 포함 최근 7일의 createdAt 기준 고유 enquiry 수 | 미열람/신규 고객/견적 수와 다름. 접수 채널 중복 처리 정책 유지 → 문의 목록 |
| 고객 연결 필요 | 미연결 canonical 원본 묶음 총수 | submission과 파생 enquiry를 한 묶음으로 계산 → 미연결 원본 목록 |
| 기간별 접수 추이 | 각 Sydney 날짜의 접수 문의 수 | 세로 막대, X=날짜·Y=건. 비어 있는 날짜는 정상 조회 시만 0 |
| 현재 상태 분포 | 서명 제출 모집단을 requested/confirmed로 분류한 고유 건수 | 가로 막대/목록. 재검토·동기화는 별도 축이며 세 번째 booking 상태로 만들지 않음. 과거 전환율처럼 표시하지 않음 |
| 오늘 일정 | 확정 일정과 요청/검토 중 일정을 구분한 agenda | 시간이 없는 자료에 09:00 등 임의 시간 부여 금지. 원래 구간과 변경 제안을 구분 |

**확정과 동기화는 다른 상태다.** 현재 구현에는 회사 확정 직후 `syncStatus=pending`이고 확정 proposal 포인터 갱신이 아직 남아 있는 구간이 있다. `lk_booking_segments`는 변경 동기화 중 이전/신규 구간을 함께 잠정 점유할 수 있다. 따라서 상태 문자열 하나나 점유 테이블 행 수만으로 ‘오늘 작업’을 계산하지 않는다. 확인된 확정 기준과 변경/동기화 대기 제안을 분리해 표시하고, 확정 기준을 결정할 수 없는 자료는 검토 필요 항목으로 분류한다. 기존 예약 충돌 보호 로직은 변경하지 않는다.

구체적으로 `confirmedProposalId`가 가리키는 세그먼트의 `startAt < dayEnd AND endAt > dayStart`를 사용한다. 최초 회사 확정 후 포인터가 아직 null이면 선택일 확정 일정에서 제외하고 ‘Google 확인 대기’ 큐에 둔다. 변경 proposal이 별도로 있어도 기존 확정본은 유지한다. `review_required`의 기존 확정본은 ‘저장된 확정 일정 · 검토 필요 N건’으로 구분하며 Google 현재 상태와 일치한다고 표시하지 않는다. 이 날짜별 분포는 현재 저장된 일정이며 과거 작업 완료 실적이 아니다.

### 작업·재고·주문 연결 후의 목표

| 영역 | 목표 시각화 | 선행 데이터·정책 |
| --- | --- | --- |
| Jobs | 오늘 예정/진행/완료 카드, 일별 작업 건수, 담당자별 일정 | Job ID·상태·시작/완료 시각·담당자·작업 구간. 예약일이 지났다고 자동 완료하지 않음 |
| Quotes | 현재 검토/고객 응답 대기, 기간별 발행·수락 건수 | 독립 견적 ID·버전·유효기간·발행/수락 이벤트. 데모 서명과 실제 계약을 분리 |
| Schedule | 주간 자원별 일정, 충돌·변경 대기 | 작업시간·인원·자원·휴무 규칙. Google busy를 회사 작업 수로 해석하지 않음 |
| Orders | 미출고/처리 필요·취소/반품, 일별 주문 추이 | 고유 주문 ID·주문 상태, 결제/배송 상태 각각, 중복 요청 방지 |
| Inventory | 부족 품목 목록, 재고 변동, 품목 상세 원장 | SKU/단위/위치·입출고·예약/사용 가능 수량·부족 기준. 단위가 다른 품목의 수량을 합하지 않음 |
| Billing | 발행/미수/입금·기한 경과, 매출과 수금의 별도 차트 | Complete·인보이스·결제/환불·통화/세금 기준. 샘플 견적액을 매출로 합하지 않음 |

견적 승인율은 동일한 발행 cohort와 관찰 기간·분모를 정의한 뒤 추가한다. 현재 스냅샷만으로 과거의 승인율·전월 대비 성장률을 역산하지 않는다. 비교 기간의 데이터가 없으면 ‘비교 자료 없음’, 분모 0이면 ‘계산 불가’로 표시한다. 매출 차트는 실제 청구·결제 모델 준비 전 넣지 않는다.

### 차트 선택

- **건수 추이:** 일/주별 막대. 성격이 다른 문의·작업·금액을 한 Y축에 섞지 않는다.
- **현재 상태:** 가로 막대와 직접 표시한 건수. 작은 수치 비교가 어려운 도넛을 기본으로 쓰지 않는다.
- **일정:** Overview는 시간순 agenda, 전용 Schedule은 일/주/월 전환. 첫 화면의 작은 월력보다 오늘 다음 일정과 검토 상태를 우선한다.
- **재고:** 부족 품목과 원장이 우선이다. 모든 품목을 색만 다른 원형 차트로 압축하지 않는다.
- 차트에는 제목·기간·단위·원본 범위·조회 시각·‘표로 보기’를 제공한다. 클릭 가능한 막대에는 키보드 대체 목록을 제공한다.

## 7. 고객 상세와 일정 업무 UX

- 고객 상세 상단: 이름·연락처·주소·고객 참조. 미확정 정보를 임의 채우지 않는다.
- 아래 탭: Overview / Enquiries & quotes / Schedule / Documents / Orders & billing / Activity. 실제 가용 탭만 정상 데이터로 표시한다.
- 계약/PDF/서명은 원본 버전·데모 여부·제출 시각을 함께 표시한다. 고객 연락처를 수정해도 과거 제출 snapshot은 다시 쓰지 않는다.
- 사진은 고객 권한 경로를 통해 읽는 비공개 썸네일과 확대 보기. 공개 링크·장기 유효 파일 URL을 대시보드 응답에 넣지 않는다.
- 고객 연결/해제는 대상 고객+원본 참조+사유+결과 확인을 보여준다. 같은 이메일/전화의 자동 병합을 도입하지 않는다.
- 일정 상세는 기존 확정 일정, 제안된 변경, 고객 수락/재서명, 동기화 상태를 구분한다. 캘린더 끌어놓기로 즉시 회사 확정이나 Google 쓰기를 실행하지 않는다.
- 긴 편집은 전용 페이지로 연다. 짧은 읽기 미리보기만 보조 패널을 고려하며, 모바일에서는 전체 폭으로 전환한다. 상세 URL을 새로 열어도 동일 인증을 통과해야 한다.

- 업무 화면의 반복적 전환·숫자 카운트업·차트 등장 애니메이션은 생략한다. 필요한 패널 전환만 짧게, 키보드·reduced motion에서는 즉시 처리한다.

## 9. 기존 admin 적용 구조

### 화면과 인증

제안 폴더: `src/modules/admin-dashboard/{domain,application,infrastructure,presentation}`는 집계 계약·읽기 포트·서버 어댑터·대시보드 UI만 담당한다. `src/app/admin`은 라우팅과 모듈 조립을 맡는다. 고객 원장·예약·인증 규칙을 대시보드에 복제하지 않는다. 새 경로/폴더는 아직 생성하지 않았다.

현재 `StaffAdminConsole`의 로그인/비밀번호/이메일 확인 상태 머신을 공통 인증 경계로 추출하고, ready 이후 자식 업무 화면을 렌더링한다. 공통 프레임에 sidebar/header/account를 둔다. 기존 `OperationsConsole`, `CustomersConsole`, `SessionSecurity`는 모듈 공개 진입점을 통해 옮긴다.

현재 RootLayout은 html/body·폰트·전역 스타일을 제공하며 공개 Header/Footer를 직접 포함하지 않는다. `/admin/layout.tsx`와 관리자 범위 스타일로 시작하고, 공개 사이트를 대규모 route group으로 이동할 필요는 없다. 설치된 Next.js 16.3.6의 로컬 인증 문서처럼 layout은 이동 시 재검증을 보장하는 경계가 아니므로 아래 개별 데이터 접근 검증을 유지한다.

페이지 프레임에서 인증을 통과한 사실만 믿지 않는다. **각 데이터 읽기/변경 API와 PDF·사진 요청에서 현재 직원 권한·세션·이메일 증거를 재검증**한다. 모든 신규 deep link에도 같은 경계를 적용한다. 새 화면 분기는 기존 직원 인가 뒤에 두며 레거시 데모 인증으로 우회시키지 않는다. 이메일 확인을 Supabase `aal2`로 표시하지 않는다.

`/admin`의 기존 hash 링크와 `?google=connected` 복귀 경로는 이전 대상 메뉴로 안전하게 연결한다. OAuth callback의 검증과 원래 상태 처리는 유지한다. 기존 운영 프레임의 독립 header/min-height를 그대로 중첩해 여러 전체 화면이 붙는 문제를 피한다. 로그인 전 공개 홈페이지 내비게이션/스타일과 관리자 프레임의 충돌을 확인한다.

### 서버 집계와 데이터

현재 Operations 조회는 **문의/변경 최신 500건**, 예약 관리 목록은 **제출 최신 100건** 등의 제한이 있다. 이 목록의 배열 길이로 전체 KPI를 만들지 않는다. 근거: [기존 operations RPC](../../supabase/migrations/20261001100420_operations_supabase.sql), [기존 booking RPC](../../supabase/migrations/20261003111254_admin_booking_confirmation.sql).

- 집계 전용 읽기 계약을 정의한다. 서버가 권한과 허용 필터를 확인한 뒤 DB 전체 대상의 `COUNT`/날짜별 집계를 수행한다. 공개 브라우저 DB 직접 조회를 추가하지 않는다.
- 제안 엔드포인트는 `GET /api/admin/dashboard`다. 기존 업무 mutation API는 보존한다. 회사는 현재 `lk-group` 단일 경계이며 브라우저가 임의로 보낸 companyId로 범위를 결정하지 않는다. 연결 설정은 owner, 나머지는 기존 업무별 서버 권한을 따른다.
- 응답에 `asOf`, `timezone`, `scope`, 기준일/기간, 위젯별 `ready / unavailable / error`와 값·필터 설명을 포함한다. 정상 0과 실패/미연결을 타입으로 구분한다.
- Sydney 날짜의 시작~다음 날 시작을 반열린 구간으로 계산한다. UTC offset을 고정하거나 24시간을 단순 더하지 않는다. 일광절약시간·자정·연속 여러 날·날짜 없는 기록을 검증한다.
- 목록은 서버 pagination을 사용한다. 집계와 드릴다운은 같은 필터/상태/canonical 규칙을 공유한다. 페이지 첫 100/500건만 필터링해 전체라고 표시하지 않는다.
- 서로 다른 원본을 나중에 읽는 경우 위젯별 시각을 표시한다. 가능한 집계는 한 DB snapshot으로 일치시키고, 외부 Google 상태는 별도 최신 시각을 쓴다.
- 새 집계 RPC/인덱스가 필요하면 별도 migration으로 검토·최소 권한 검사 후 적용한다. 프레임/문서 작업을 이유로 운영 스키마를 먼저 바꾸지 않는다.
- 요청별 비공개 응답 및 기존 `private, no-store`·Cookie 구분을 유지한다. 공용 캐시/서비스 워커/localStorage에 고객 원본을 보관하지 않는다. 자동 갱신은 이후 필요성·비용을 검토하고, 1차는 진입·조건 변경·저장 성공·명시적 새로고침으로 갱신한다.

### 보존할 불변 조건

기존 원본 ID·고객 canonical 연결·제출 snapshot·PDF/서명·사진·booking revision·동기화/잠금 규칙을 보존한다. 화면 이동을 DB 복사나 기록 재작성으로 구현하지 않는다. 동일 연락처 자동 병합, 원본 링크 수정 후 과거 계약 변경, 견적금액의 매출 변환은 금지한다. 고객 변경과 감사는 원자성·idempotency를 유지한다.

기존 [07번 다음 작업](07-2026-10-06-main-status-and-next-steps.md)의 실제 고객 연결/해제·본인 다른 세션 종료·사진 포함 재서명·실기기 검증은 삭제하지 않는다. D1/D3 회귀 인수에 결합하며 새 화면을 그렸다는 이유로 완료 처리하지 않는다. 실제 상태/기간 필터는 D2/D3에서 한 번 구현한다.

## 11. 검증·전환·되돌리기

- 인증: 로그인 전/API 직접 접근·직원 확인 전·만료·회수·다른 세션 종료, deep link와 private 문서/사진의 동일 경계. 401/403 시 화면의 PII 제거.
- 집계: 원본 500/100건 초과, 중복 파생 enquiry, 미연결 원본, 복수 작업구간, 변경 동기화 대기, Sydney 자정/DST, 미래 날짜·빈 날짜·부분 실패, 범위별 demo 분리.
- UI: 1440/1280/768/390/320px, 확대·키보드·초점 복귀·긴 이름/주소/메일, 로딩/0/미구현/실패/권한 만료, 차트 대체 표.
- 회귀: 기존 자동 업무 검사 + 변경한 모듈 검사 + lint/typecheck/build. 앞서 통과한 359개는 과거 근거이며 새 프레임 변경 검증을 대신하지 않는다.
- 실제 인수: 지정 시험 자료로 고객 생성/원본 연결/해제·문서/사진·재서명/확정·세션 회수. 실제 고객을 임의 병합하거나 검증 목적으로 예약·메일을 실행하지 않는다.
- 전환: 구현 브랜치의 로컬/검토 환경에서 먼저 확인 → 새 프레임과 기존 동작 동등성 검수 → `/admin` 기본 진입 전환. 독립 앱·도메인·배포는 별도 후속이다.
- 되돌리기: 초기에는 직원 인증 뒤 내부 분기로 기존 UI를 유지한다. 새 화면 문제가 있으면 UI 선택을 되돌리며, 인증을 끄거나 DB 원본을 되돌리는 방식은 사용하지 않는다. 추가 집계 migration은 원본을 수정하지 않는 방식으로 설계한다.

## 12. 남은 결정과 이번 결과의 한계

권장 기본안은 영어 운영 UI, 위 메뉴 구성, 고정된 4 KPI, Slate/Greige, 동일 앱/동일 DB다. 다크 모드·사용자 위젯 편집·자동 수동배치·전사 전체 검색·CSV 내보내기는 1차 필수에서 제외한다. 이후 필요할 때 권한/개인정보/기간 기준을 함께 정한다.

구현 전에 구체화할 항목은 재고가 판매상품/작업자재 중 어디까지인지, 회사 매입·발주 포함 여부, Job 시작/완료·담당자·자원 규칙, 운영 견적/청구 정책이다. 이는 D4/D5의 결정이며 D1 프레임 작업을 막지 않는다.

이번 산출물은 현재 코드·글로벌 토큰·기존 검증 문서의 대조와 설계 검토다. 와이어프레임 가상 값은 실측 KPI가 아니다. 제품의 새 화면·집계 API·migration은 구현하지 않았고 회사 DB·Google 설정을 변경하지 않았다. 기존 작업 중이던 문서 변경은 보존한다.
