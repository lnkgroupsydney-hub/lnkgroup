**후속 요청 — 실제 운영 계획:** 사용자는 회사 검토·실제 금액 확정 방식으로 데모 이후 흐름을 계획하도록 요청했다. 다음 구현 기준은 [37번 실제 Quote·EMS·예약 계획](37-live-quote-ems-booking-implementation.md)이다. 이번 계획 갱신으로 아래 QF-04/05 잔여 실제 인수나 데모 자료를 운영 계약 완료로 바꾸지 않는다. 지정 두 사진의 기존 비공개 데모 사용 범위와 제출 원본은 보존한다.

상태: **사용자 승인 후 순차 실행 중.** 지정 두 사진 저장·서명·제출 `DEMO-3E8E831C`·회사 INBOX/PDF 두 개·확정 대기 Calendar를 확인했다. 재서명 사진 표시와 요청 경합/권한 종료 오류를 보완하고 380/380 검사·lint·타입·빌드를 통과했다. EMS 실제 고객 연결·제안/재서명/확정은 관리자 로그인 대기이며 Mac 잠금으로 일부 화면 검증도 남아 있다. [실행 기록](../verification/2026-10-08-quote-damage-demo.md)에 범위를 구분한다. 가격·약관은 기존 회사 전용 데모를 유지하고 운영 완료와 구분한다.

### 후속 요청: 사용자가 직접 전체 폼 작성 — 완료

- 완료 화면에 새 견적 생성과 새 탭 열기를 연결한다. 기존 탭의 미저장 재서명 입력·진행 중 요청은 유지한다.
- 기본 작성 세션을 교체하지 않는다. 새 `quote` 선택자마다 별도 HttpOnly 세션을 만들고 API·사진·PDF에 선택자를 전달한다. 각 세션은 고정 최대 24시간이며 원본 owner·서명·TTL은 변경하지 않는다. 잘못되거나 만료된 선택자는 원본으로 전환하지 않고 거절한다.
- 같은 생성 요청은 동일 ID로 재시도하고 이미 발급된 유효 쿠키/만료시각을 유지한다. 생성 요청 시 유효 세션 5개 이상이면 추가 발급을 거절한다. 여러 탭의 동시 생성까지 원자적으로 제한하는 DB 계수 기능은 포함하지 않는다.

## 2. 지정 사진과 사용 범위

| 원본 파일 | 확인한 형식·크기 | 사진에서 보이는 내용 | 이번 용도 |
| --- | --- | --- | --- |
| `/Users/jimee/Downloads/damage 1.jpeg` | JPEG · 480×640 · 22,734 bytes | 오른쪽 측판 마감의 큰 벗겨짐과 노출된 가장자리, 열린 문·서랍 | 측판·가장자리 손상 사례 |
| `/Users/jimee/Downloads/damage 2.jpeg` | JPEG · 480×640 · 17,948 bytes | 싱크대 아래 문·프레임 가장자리와 이음부의 마감 벗겨짐 | 문·프레임 마감 손상 사례 |

두 사진의 관찰은 사람이 사진을 읽은 참고 설명이다. **AI 분석 결과가 아니다.** 재질·손상 원인·내부 상태·보수 가능 여부·교체 필요성·가격은 사진만으로 확정하지 않는다. 같은 현장의 사진인지도 확정하지 않으며, 가상 데모 한 건의 참고 사진으로만 묶는다.

- 원본은 Downloads에 보존하고 실행 단계에서 기존 업로드 UI로 선택한다. `public/`, 공개 이미지 갤러리, Git 테스트 자산에 복사하지 않는다. 외부 AI 전송은 이번 범위에 없다.
- 업로드 시 기존 서버가 회전 보정·메타데이터 제거·JPEG 정규화 후 private Storage에 저장한다. 현재 파일은 기존 용량 한도 내지만, 실제 업로드 성공은 아직 확인하지 않았다.
- 실행 기록에는 원본 SHA-256과 `photoId`, 정규화 `contentHash`, `processingVersion`의 대응을 남긴다. 원본 해시와 정규화 해시가 같아야 한다고 판정하지 않는다. 비공개 원본·접근 URL·세션 값은 커밋하지 않는다.
- 최종 제출은 정확히 이 두 장의 manifest를 고정한다. 최초 문서와 회사 제안 문서가 같은 원본 제출/사진을 참조하는지 확인한다. 사진 자체를 이메일·공개 PDF URL에 추가하는 범위로 확대하지 않는다.
- 사진 변경 오류 시험은 제출 전에 수행하고 최종 두 장을 다시 확인한다. 제출 뒤에는 원본 사진·서명·PDF를 덮어쓰지 않는다.

## 3. 구현·인수 순서

```text
QF-00 회사 연결·별도 작성 세션 준비
  -> QF-01 고객/서비스 저장 + 지정 사진 2장 + 복원
  -> QF-02 데모 승인 -> 가용 날짜 -> 최종 확인·서명·제출
  -> QF-03 불변 제출/PDF -> 회사 메일 -> 확정 대기 Calendar
  -> QF-04 EMS 검토·사진/PDF 열람·고객 원장 수동 연결
  -> QF-05 회사 작업 구간 제안 -> 고객 재서명 -> 제안 메일 수락
           -> 전체 구간 충돌 재검사 -> 회사 확정 -> Calendar synced
  -> QF-06 모바일·실패 복구·회귀 확인 -> QF-07 결과·TODO 갱신
```

각 단계는 기존 동작을 먼저 확인하고 발견한 오류만 해당 모듈에서 수정한다. 오류를 재현·수정·재검증한 뒤 의존 단계로 넘어간다. 새 테이블·API·의존성 추가는 기본 계획에 없으며 필요성이 드러나면 영향과 대안을 먼저 정리한다.

### QF-00 — 실행 환경과 작성 권한 준비

1. 착수 시 Git 변경·앱·worker 실행 상태, 회사 Supabase/Google/Resend 설정 여부를 확인한다. 키 값은 출력하지 않는다. 계획 작성 시점의 미검증과 이후 실제 실행 결과를 구분한다.
2. `lnkgroupsydney@gmail.com`으로 확인된 회사 브라우저만 사용한다. EMS 인증이 만료됐다면 사용자가 기존 로그인·이메일 확인을 진행하며 비밀번호·코드를 기록하지 않는다.
3. 기존 초안·제출·쿠키를 보존하며 별도 고객 작성 세션을 준비한다. **새 탭이나 다른 포트만으로는 작성 세션이 분리되지 않는다.** 같은 회사 프로필에서 사용되지 않은 loopback hostname과 일치하는 앱 기준 URL/Origin을 사용한 기존 시험 방식을 우선 검토한다. 예: 기존 `127.0.0.1` 세션을 보존하고 `localhost`에 별도 앱 실행. 대상에도 기존 초안이 있으면 지우지 않는다.
4. 작성 쿠키는 고정 24시간이며 유효 쿠키는 재사용된다. 최초 제출부터 QF-05 고객 재서명까지 같은 유효 세션에서 진행한다. 만료된 이전 제출의 소유자 해시·쿠키·TTL을 바꿔 접근을 복구하지 않는다. 만료 시 해당 인수를 중지하고 기존 자료를 보존한 새 가상 시험 건으로 재계획한다.
5. 고유 시험 참조번호·가상 고객명, 회사 수신 주소, 기존 회사 시험 Calendar를 사용한다. 실제 작업일이나 고객 정보를 임의로 확정하지 않는다.

완료 기준: 회사 인증·연동 대상과 기존 자료 보존이 확인되고, 작성부터 재서명까지 사용할 새 세션이 준비됨.

### QF-01 — 고객·서비스·두 사진 저장

고객 정보와 상세를 저장하고 Kitchen Cabinet Painting을 선택한다. Google 주소 검색 결제/키가 아직 준비되지 않았다면 기존 직접 입력을 사용한다. 두 사진을 업로드한 뒤 각 성공 상태·미리보기·삭제/재시도·새로고침 복원을 확인한다. 업로드 도중에는 미완료 사진을 포함해 제출하지 못해야 한다.

대상: `enquiries/presentation/quote-draft-form.tsx`, `quote-photo-upload.tsx`, `infrastructure/quote-draft-api.ts`, `quote-photo-api.ts`, `quote-photo-image.ts`, `quote-photo-storage.ts`와 기존 사진 테스트. 경로 기준은 `src/modules/`다.

완료 기준: 같은 고객·서비스·사진 ID 두 개가 복원되고, 다른 작성 세션·비로그인 접근은 차단됨. 저장을 누른 상태와 서버 저장 성공을 구분함.

### QF-02 — 데모 승인·날짜·서명·제출

기존 샘플 AUD 1,250·비구속 데모 약관을 명확히 표시한다. 사진을 근거로 산출한 견적처럼 표현하지 않는다. 승인 후 이미 예약된 날짜가 선택되지 않는지 확인하고 빈 희망일을 선택한다. 최종 확인에서 고객·서비스·사진 두 개·금액·희망일을 대조한 뒤 서명·제출한다.

대상: `enquiries/presentation/demo-quote-flow.tsx`, `infrastructure/demo-api.ts`, `demo-availability.ts`, `src/shared/ui/signature-pad.tsx`, `signature-input.ts`.

완료 기준: 사진/서비스/날짜 변경 뒤 필요한 재검토·재승인·재서명이 적용되고, stale 가용성/새 충돌은 서버에서 거절됨. 중복 클릭·응답 유실에도 동일 제출이 유지됨. 화면은 회사 확정 대기로 표시됨.

### QF-03 — 문서·회사 메일·최초 Calendar 확인

불변 제출에서 견적과 서명 약관 PDF 두 개를 생성·보존한 뒤 회사 주소로 발송하는 기존 순서를 확인한다. PDF의 참조번호·데모 표시·서명·사진 참조/개수가 저장된 snapshot과 일치해야 한다. Resend 수락 뒤 확정 대기 Calendar 작업을 진행하고 앱에서 상태를 복원한다.

대상: `enquiries/infrastructure/demo-email.ts`, `demo-pdf.ts`, 기존 전달 작업과 `scripts/integrations-worker.mjs`.

완료 기준: 저장된 PDF 해시와 발송 첨부를 대조하고 회사 Gmail 실제 수신까지 별도로 확인함. `provider_accepted`를 받은편지함 도착으로 간주하지 않음. 같은 버전의 반복 worker 실행으로 메일/이벤트가 중복되지 않음.

### QF-04 — EMS 검토와 고객 원장 연결

`/admin/quotes`에서 새 참조번호로 제출·두 사진·PDF·메일/Calendar 상태를 확인한다. `/admin/customers`에서 가상 고객을 만들고 해당 원본을 명시적으로 연결한다. 회사 데모들은 이메일이 같으므로 이메일 자동 병합을 하지 않으며 source ID·변경 사유·revision으로 연결한다. 고객 연결은 작성 소유권이나 예약 확정을 부여하지 않는다.

대상: `operations/presentation`의 기존 견적 조회, `customers/presentation/customers-console.tsx`, `customers/infrastructure/api.ts`, `store.ts` 및 고객 테스트.

완료 기준: 새로고침 후 고객과 원본 연결·감사가 유지되고 원본 제출·PDF·사진·예약은 바뀌지 않음. 잘못된 연결/해제 경계는 우선 격리 시험으로 확인하고 실제 시험 연결을 변경했다면 올바른 연결로 복구함.

### QF-05 — 회사 기간 제안·재서명·최종 확정

`/admin/schedule`에서 회사가 수동으로 작업 구간을 입력한다. 회사 제안을 원래 작성 세션에서 확인하고 동일 사진·제안 버전·기간·문서에 재동의/재서명한다. 제안 메일 수락과 최신 동의가 충족된 뒤 전체 작업 구간을 다시 검사해 확정한다. Google 쓰기/재조회가 완료돼 `syncStatus=synced`가 될 때까지 동기화 상태를 구분한다.

대상: `bookings/presentation/booking-operations-panel.tsx`, `customer-booking-review.tsx`, `application/confirm.ts`, `infrastructure/api.ts`, `store.ts`, `email.ts`, `calendar.ts`, `calendar-availability.ts`.

완료 기준: 오래된 제안·불충분한 동의·메일 미수락·겹치는 작업 구간은 확정 불가. 최종 문서와 작업 구간이 Calendar와 일치하고 새 작성 세션에서는 점유 날짜가 차단됨. Calendar 이벤트 수는 최초 요청·작업 구간별 이벤트·요약을 구분해 대조하며 전체가 한 개여야 한다고 검사하지 않음. 변경 실패 시 기존 점유를 보존함.

### QF-06 — 실패 복구·모바일·회귀

실제 두 사진의 정상 경로를 회사 연결로 확인하고, 의도적인 공급자 장애·경합·소유권 위반은 기존 격리 시험으로 재현한다. 회사 OAuth 회수나 실제 이벤트 삭제로 장애를 만들지 않는다. 응답을 잃으면 먼저 상태를 읽고 같은 payload/멱등 키로 재시도한다. 메일 `outcome_unknown`을 무조건 재발송하지 않는다.

| 검증 대상 | 검사 방법 | 통과 조건 |
| --- | --- | --- |
| 사진 저장·복원·소유 경계 | 실제 지정 사진 + 기존 사진 DB/API 격리 검사 | 두 사진 대응 유지, 타 세션 접근 차단, 제출 뒤 변경 불가 |
| 변경 후 승인·서명 | 작성 UI + 기존 Quote/서명 테스트 | 이전 승인/검토 토큰 무효화, 오래된 서명 제출 거절 |
| 가용성·전체 기간 충돌·동시 확정 | 실제 busy 읽기 + 예약 격리 검사 | 날짜 선택 및 확정 모두 충돌 차단, 점유 중복 없음 |
| 업로드·메일·Calendar 부분 실패 | 기존 fault fixture·멱등성 검사 | 입력/원본/점유 보존, 실패 단계만 재시도 |
| 회사 고객 연결 | 실제 가상 고객 연결 + 고객 격리 검사 | 동일 이메일 자동 병합 없음, 감사와 원본 보존 |
| EMS 인증·자동 동기화 | 회사 화면 + 기존 관리자/EMS fixture | 401/403 뒤 비공개 데이터 제거, 입력 보존, 중복 요청 없음 |
| 작은 화면·접근성 | 320/390px, 키보드, 확대, 오류/로딩 상태 | 사진·날짜·서명·제출·재서명을 사용할 수 있고 콘솔 오류 없음 |
| 실제 휴대폰 터치 | 보호된 회사 접근 경로와 기기 준비 시 | 지우기·재서명·회전·영역 밖 스크롤; 미실행이면 별도 대기 |

검사 연결: `사진/소유 -> 승인/서명 -> 불변 제출 -> 메일/Calendar -> 제안/재서명 -> 점유/확정`. 기존 사진·Quote·예약·고객·직원/EMS 테스트를 사용하고 실제 결함을 발견한 경계에만 회귀 검사를 추가한다. 사용자 사진 대신 합성 파일을 커밋 가능한 오류 fixture로 사용한다.

코드 변경 후 관련 검사를 먼저 통과하고 최종 `npm run test:operations`, `npm run check`, `git diff --check`를 실행한다. 빌드 환경은 실행 중인 앱과 분리한다. 계획 단계의 문서 검사와 실행 단계의 명령 결과를 구분한다.

### QF-07 — 완료 기록
