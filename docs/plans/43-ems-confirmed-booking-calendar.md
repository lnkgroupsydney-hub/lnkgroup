## 1. 목표와 고객 확인

이 단계의 시작 조건은 **고객의 예상 금액 승인 → 희망일 선택 → 예약 요청 서명·제출**이다. 고객에게 EMS 선행 확정을 요구하지 않는다. 고객 날짜 선택 복구와 수동 예상 견적 검토/예약 제출 구분은 [44번 후속 수정](44-quote-customer-date-first-recovery.md)을 따른다.

**EMS 요청 열기 → 사진/AI 예상본 확인 → 회사 최종 금액·범위·실제 작업 구간 입력 → 충돌 검사 → 회사 제안 발행 → 인증 고객의 해당 버전 확인 → 회사 확정 → DB 기간 점유 → Google 확정 일정 저장·독립 조회 → 고객/EMS 확정 표시·통지 → 다른 고객 날짜 선택 차단.**

기존 서명은 희망 시작일의 예약 요청이다. 회사가 처음 정하는 전체 작업 기간과 최종 금액의 동의로 재사용하지 않는다. 금액이 같아도 고객에게 전체 작업 구간을 보여주고 확인받는다. 회사가 제안을 수정하면 이전 확인으로 확정할 수 없다.

이번 확인은 **회사 제안 금액·범위·일정 확인**이다. 승인된 계약 약관이 아직 없으므로 작업 지시·결제 의무·정식 계약 서명으로 표시하지 않는다. 약관을 받은 뒤의 계약 단계와 운영 일정 확정을 구분한다. 인보이스는 기존 결정대로 **마지막 작업 후 Complete → 실제 발행일 +3일 납기**이며 예약 확정 시 발행하지 않는다.

## 3. 입력·가격·기간 규칙

- **가격:** AI 예상본을 비교 기준으로 표시한다. 회사가 확인 수량·작업 포함/제외·최종 공급가·조정 사유를 입력한다. 기존 승인 GST 설정을 유지하고 서버가 GST/총액을 정수 cents로 계산한다. 음수·NaN·고객 임의 총액·허용 범위 밖 값을 거절하고 수정자·시각·이유를 저장한다.
- **기간:** 회사가 종일 시작일/마지막 작업일 또는 Sydney 시작/종료 날짜·시각을 직접 입력한다. 여러 작업 구간을 지원하고 빈 구간·과거·종료 역전·제안 내부 중복을 거절한다. 구간 사이 날짜는 자동 점유하지 않는다.
- **기간 요약:** 총 작업일/시간은 입력한 구간에서 계산한다. AI 기간 추정·기본 근무시간·주말/공휴일 제외·이동/준비 시간을 임의로 넣지 않는다. 필요한 준비/이동 점유는 회사가 구간에 명시한다.
- **시간 경계:** 종일/시간 구간을 같은 UTC `[start,end)`로 정규화한다. 종일 마지막 작업일은 화면에서 포함하고 저장/Google 종료는 다음 날 exclusive end다. 존재하지 않거나 모호한 Sydney DST 시각은 기존 변환 규칙으로 거절한다.
- **자원:** 첫 구현은 현재 회사 기본 Calendar를 단일 예약 자원으로 사용한다. 직원 수·여러 팀의 병렬 작업 용량은 새로 정하지 않는다.
- **날짜 차단:** 고객은 날짜 단위로 선택하므로 작업 시간이 일부만 겹쳐도 그 Sydney 날짜 전체를 차단한다. 관리자 충돌은 실제 시간 구간 기준이다. 이 차이를 화면에 안내한다.

## 4. 저장·상태·권한

`bookings` 모듈의 domain/application/ports/infrastructure/presentation에 운영 계약을 추가한다. 다른 모듈은 공개 진입점으로 조합하며 데모 자료를 운영 예약으로 변환하지 않는다.

| 저장 단위 | 주요 내용 |
| --- | --- |
| 회사 제안 | 원본 request/submission, version/hash, 최종 공급가/GST/총액, 범위·사유, 모든 구간, Calendar 대상, 작성자/발행자/시각 |
| 고객 확인 | 인증된 고객/요청 관계, 정확한 proposal ID/version/hash, 확인 문구 버전, 서명 또는 확인 기록·시각 |
| 실제 예약 | 수락한 제안, 회사 명령/멱등 key, 버전, `confirming`/`confirmed`/`review_required`, Calendar·메일 처리 상태 |
| 기간 점유 | 예약/제안/자원의 UTC 구간과 고객 차단용 날짜 projection. 처리 중·확정·검토 중 점유 포함 |
| 외부 처리 | 구간별 고정 Google event ID/expected payload/hash/ETag, lease, 시도·오류·독립 조회 결과, 고정 PDF/메일·제공자 ID |

- 흐름은 `초안 → 고객 확인 대기 → 고객 확인 완료 → 확정 처리 중 → 예약 확정`이다. 충돌·외부 변경·불명확 결과는 사유와 함께 `검토 필요`로 표시한다.
- 발행한 제안은 불변이며 수정은 새 버전으로 만든다. 확정 처리를 시작한 버전은 고정하고 수정·다른 버전 발행을 막는다. 과거 동의/서명/PDF 원본을 보존한다.
- 직원 조회는 `operations.read`, 작성/발행/확정은 `operations.write`와 현재 회사 membership/세션을 서버·DB 명령 경계에서 검사한다. 고객 확인은 인증된 요청 소유 관계로만 허용한다.
- `expectedRevision`·proposal hash·명령 payload hash·idempotency key로 오래된 관리자 탭·다른 제안 확인·중복 확정을 거절한다.
- RLS·익명 접근 차단·최소 서버 RPC 권한을 명시한다. secret·내부 event 소유 표식·사진 경로를 공개 API에 노출하지 않는다.

## 5. 순차 구현 단위

### CB-01 — 회사 제안 저장·EMS 입력

1. 운영 회사 제안/확정 DTO·상태·금액/구간 검증과 저장 포트를 만든다.
2. CLI로 새 migration을 생성해 회사 제안·고객 확인·실제 예약/외부 기록과 확정 구간 확장을 추가한다. 기존 migration을 수정하지 않는다.
3. `/admin/quotes` 상세에 예상/최종 금액 비교, 범위·사유, 종일/시간 구간 편집, 초안 저장/복구·버전 충돌을 연결한다.
4. `/admin/schedule`에 같은 운영 예약의 목록/상세를 연결한다. 미저장 초안을 확정 예약으로 표시하지 않는다.

**통과:** 실제 제출에서 초안을 저장·새로고침 복구하고 기존 요청/PDF/사진/분석/서명이 유지된다. 합계·기간·사유 검증과 읽기 권한의 쓰기 차단을 확인한다.

### CB-02 — 전 기간 충돌 검사·고객 확인

1. 관리자 전용 Google 조회에 event ID·ETag·소유 표식을 추가한다. 반복 일정/모든 페이지를 조회하며 계정·Calendar 대상이 도중 바뀌면 실패한다.
2. **모든 작업 구간**을 Google과 DB 처리 중/확정 점유에 대조한다. 충돌 날짜·구간·출처·검사 시각을 EMS에 표시하고 확인 불가 시 확정을 막는다.
3. 충돌 없는 제안을 불변 버전으로 발행한다. 인증 고객 Quote 복구 화면에 금액·범위·전체 일정·이전본 차이를 표시하고 회사 발신으로 접근 안내를 보낸다.
4. 고객 확인은 해당 제안 hash에 묶는다. 새 버전·날짜/금액/범위 변경 후 이전 확인을 거절한다. 확인본/PDF 발송은 기존 제공자 수락 게이트를 유지해 확정 전 준비한다.

**통과:** 시작일이 비어도 뒤의 작업일에 다른 예약이 있으면 충돌한다. 고객이 전체 구간을 확인하지 않으면 회사가 확정할 수 없다. 제안/확인 상태와 메일 상태를 구분한다.

### CB-03 — DB 원자적 확정 준비·기간 점유

1. 확정 버튼에서 최신 제안·고객 확인·확인본 발송 상태와 Google 전 구간을 재검사한다.
2. 같은 회사 자원의 겹친 실제 구간을 거절하는 PostgreSQL exclusion constraint를 둔다. 종일/시간 예약을 동일 기준으로 검사한다.
3. **확정 명령 + 모든 구간 점유 + 외부 manifest/outbox + 감사**를 단일 트랜잭션으로 저장한다. 한 구간이 충돌하면 전체를 거절한다.
4. 상태는 `확정 처리 중`이며 고객 달력에 점유를 바로 반영한다. 실제 서로 다른 DB 연결에서도 겹친 기간을 한 예약만 획득해야 한다.

**통과:** 중복 클릭/재시도는 기존 결과를 반환한다. Google 작업 중에도 이중 점유가 불가능하며 맞닿은 `[start,end)` 경계는 허용한다.

### CB-04 — Google 확정 작업 구간 저장·검증

1. 기존 transparent 희망일 표식은 접수 이력으로 유지한다. 덮어쓰면 불변 요청 outbox와 충돌하므로 **실제 예약/제안 버전/구간별 고정 ID**로 별도 작업 일정을 만든다.
2. 회사 기본 Calendar에 구간별 `private + confirmed + opaque`를 저장한다. 제목은 예약 참조번호·작업 용도를 사용하고 개인정보·사진·서명·attendee를 넣지 않는다.
3. 생성 전 GET으로 존재/소유/payload를 확인한다. 409·응답 유실은 동일 ID 조회로 복구하고 새 ID로 재생성하지 않는다. 자체 event 수정이 필요하면 ETag `If-Match`로 조건부 수행하며 외부 변경을 덮어쓰지 않는다.
4. 구간마다 별도 GET으로 날짜/시간·Calendar·소유·버전/hash·private/opaque를 검증한다. 이후 전 기간을 재조회해 **이번 예약의 검증된 자체 event ID만** 제외하고 다른 충돌을 검사한다.
5. 모든 구간의 독립 읽기·사후 충돌 검사가 성공해야 DB CAS로 `예약 확정`으로 전환한다. 최신 버전/lease를 반복 검사하고 manifest로 외부 결과를 대사한다.

**부분 실패:** 한 구간만 생성되거나 Google 성공 뒤 DB 기록이 실패하면 처리/검토 상태와 점유를 유지한다. timeout·lease 만료만으로 해제하지 않는다. 불명확한 event ID는 대사하고 다른 고객 일정은 수정·삭제하지 않는다.

### CB-05 — 고객 선택 차단·확정 화면·통지

1. 고객 availability에 DB 처리 중/확정/검토 중 점유와 Google opaque 구간을 합친다. UI뿐 아니라 날짜 저장·고객 제출·회사 확정 서버 경계에서 재검사한다.
2. 고객/EMS에 같은 최종 금액·구간·확정 버전·Calendar 검증 상태를 표시하고 새로고침/재인증으로 복구한다. 구간 사이 비점유 날짜는 다른 예약이 없다면 선택 가능하다.
3. DB/Google 확정 뒤에만 회사 발신으로 고정 확정 안내·확인본을 보낸다. 발송 실패로 예약을 해제하지 않고 발송/수신과 예약 상태를 분리한다.

**통과:** 다른 고객 화면과 오래된 화면의 서버 저장에서 모두 차단한다. 두 화면·DB·Google·발송본이 동일 제안을 가리킨다.

### CB-06 — 외부 변경 감지·복구

1. EMS 새로고침·확정 처리·기존 인증 worker/백업에서 자체 event를 읽어 이동·연장·삭제·투명도/상태 변경을 검토 건으로 남긴다. 확정 구간의 전체 점유도 재조회하고 검증된 자체 ID만 제외해, 확정 후 다른 Google event가 같은 기간에 추가된 충돌도 검토로 남긴다.
2. Google 직접 변경을 고객 동의나 자동 취소로 취급하지 않는다. 기존 DB 구간을 유지하고 새 Google busy 날짜도 고객 availability에서 차단한다.
3. 첫 구현은 초기 확정과 변경 감지/검토까지다. 확정 후 재일정/취소의 회사 승인·고객 확인·event 정리·점유 해제는 후속 명령으로 구현한다.
4. 기존 Hobby 일 1회 백업 cron을 실시간 동기화로 표현하지 않는다. 확정 직후 처리·화면 재조회·서버 명령 검사를 함께 사용한다. 더 잦은 자동 동기화 인프라는 별도 선택이다.

### CB-07 — 자동 검사·회사 환경 인수

관련 검사 → lint/타입/빌드 → 회사 DB 적용/기존 데이터 보존·권한 검사 → 회사 배포 → 회사 Chrome 실제 흐름 → DB/Google event/금액·구간/PDF 대조 순서다. 가상 시험 고객을 실제 계약으로 처리하지 않는다.

## 8. 공식 기준

- [PostgreSQL range constraints](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT): 동일 자원의 겹침을 DB 제약으로 거절하는 설계 근거. 회사 DB 버전·extension·기존 구간 중복을 적용 전에 확인한다.
- [Google event update](https://developers.google.com/workspace/calendar/api/v3/reference/events/update)·[ETag 조건부 변경](https://developers.google.com/workspace/calendar/api/guides/version-resources): 이미 읽은 자체 event 버전만 조건부 수정한다.
- [Google 동기화](https://developers.google.com/workspace/calendar/api/guides/sync): 삭제도 변경으로 확인하며 token 만료를 원본 예약 삭제로 취급하지 않는다. 첫 구현은 자체 event 직접 조회·검토를 사용한다.
- [Supabase PostgreSQL minor 변경](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes): changelog의 기존 btree_gist float/NaN index 조건을 검토했다. 새 제약은 시간·식별자 기반으로 설계하고 회사 버전/영향 여부를 적용 전에 확인한다.
