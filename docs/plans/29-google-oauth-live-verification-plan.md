## 0. 실행 환경과 시험 대상 준비

1. Git 변경 상태와 실행 중인 앱/worker를 확인한다. 사용자가 수정한 모델 설정·에이전트 지침은 보존한다. `.env.local`은 값 출력 없이 필수 항목 설정 여부·파일 권한·Git 제외만 확인하고 기존 관리자 비밀번호와 암호화 키를 유지한다.
2. 앱 주소는 `http://127.0.0.1:3002`, 시간대는 `Australia/Sydney`로 맞춘다. 앱/worker의 `OPERATIONS_STORE=supabase`·프로젝트 일치, 기존 문의·전송 대기·이벤트 연결을 확인한다. 이전 `.local/operations.sqlite`는 별도로 보존하며 자동 복사·삭제하지 않는다. 회사 DB를 비우거나 기존 문의를 시험 성공 건수에 포함하지 않는다.
3. 시험 문의에는 식별 가능한 시험 표식을 붙이고 회사가 소유한 Calendar와 사용자 생성 Gmail 라벨을 지정한다. 전용 시험 Calendar(제안 `L&K Integration Test`)는 기존 이벤트 연결·전송 대기가 없는 경우에만 선택한다. 이미 회사 업무 연결이 있으면 그 대상을 임의 변경하지 않고 시험 대상부터 다시 정한다. `L&K/Integration Test` 같은 이름은 시험 제안이며 운영 정책의 확정값이 아니다. 별도 SQLite/PGlite 시험은 오프라인 회귀용이며 회사 Supabase 검증을 대신하지 않는다.
4. 시험용 수신 메일은 회사 계정 외의 사용자가 관리하는 발신 계정에서 준비한다. 제목에는 `[LK-OAUTH-20261001]`을 넣고 실제 고객 정보는 사용하지 않는다. 회사 계정의 자기 자신에게 보낸 메일은 `SENT`로 제외될 수 있어 수신 검증에 사용하지 않는다.
5. Calendar 첫 선택 전에 전송 대기를 확인한다. 희망일만 있는 웹 문의도 종일 요청 이벤트로 전송될 수 있으며, 관리자 화면의 자동 polling도 실제 동기화를 실행한다. 연결 이후에는 `Sync now`만이 전송 계기라고 가정하지 않는다.

현재 코드는 이벤트 연결이 남아 있는 DB에서 다른 Calendar로 바꾸는 것을 막는다. 시험 대상 정리와 실제 사용 대상 선택은 6단계를 따르고, 기존 연결을 DB에서 직접 지워 전환하지 않는다.

## 1. Google Cloud·OAuth 준비

1. 일반 Chrome 등 지원되는 브라우저에서 회사 계정으로 로그인하고 회사가 관리할 Google Cloud 프로젝트를 선택한다. 없으면 회사 계정으로 이번 연동용 프로젝트를 만든다. 프로젝트 ID·소유 계정만 기록하고 결제 계정이나 유료 서비스를 추가하는 단계는 포함하지 않는다.
2. 동일 프로젝트에 **Gmail API**, **Google Calendar API**를 활성화한다.
3. Google Auth Platform에서 Branding의 앱 이름·지원 이메일·연락 이메일을 입력한다. 이름은 `L&K Group Local Operations`를 제안하고 이메일은 회사 연동 계정을 사용한다. Audience는 **External / Testing**, 테스트 사용자는 `Lnkgroupsydney@gmail.com`으로 설정한다. 일반 Gmail 계정에 조직 내부 앱 조건을 가정하지 않는다. [Google 동의 화면 설정](https://developers.google.com/workspace/guides/configure-oauth-consent)
4. Data Access에 현재 코드의 권한만 등록한다.

| Scope | 사용 목적 |
| --- | --- |
| `openid`, `email` | 승인된 회사 Google 계정 확인 |
| `https://www.googleapis.com/auth/gmail.readonly` | 문의 라벨과 수신 메일 읽기 |
| `https://www.googleapis.com/auth/calendar.calendarlist.readonly` | 선택 가능한 Calendar 목록 읽기 |
| `https://www.googleapis.com/auth/calendar.events.owned` | 회사 계정이 소유한 Calendar의 이벤트 읽기·쓰기 |

Gmail OAuth 권한 자체는 특정 라벨로 제한되지 않는다. 선택 라벨만 읽는 것은 앱의 수집 규칙이다. `gmail.readonly`는 restricted scope이고 라벨/필터 작성·메일 전송 권한을 주지 않는다. 라벨과 필터는 Gmail 화면에서 준비한다. Calendar는 단순 공유 편집 권한만 있는 대상이 아니라 **owner인 대상**을 선택한다. [Gmail 권한](https://developers.google.com/workspace/gmail/api/auth/scopes), [Calendar 권한](https://developers.google.com/workspace/calendar/api/auth)

5. OAuth Clients에서 **Web application**을 만들고 Authorized redirect URI에 다음을 그대로 등록한다.

```text
http://127.0.0.1:3002/api/google/callback
```

서버 OAuth 흐름이므로 프런트엔드 Google 로그인 SDK용 JavaScript origin 추가는 현재 코드에 필요하지 않다. Client Secret은 생성 시 안전하게 보관하고 서버 설정에 직접 넣는다. 채팅·문서·Git에 비밀 값을 남기지 않는다. callback의 호스트·포트·경로를 정확히 일치시킨다. [Web server OAuth 설정](https://developers.google.com/identity/protocols/oauth2/web-server)

로그인은 일반 브라우저에서 진행한다. 다른 브라우저로 옮겼다면 그 브라우저의 `/admin`에서 연결을 다시 시작한다. 진행 중인 callback 주소를 복사해 옮기면 앱의 브라우저별 state 검증이 실패할 수 있다. Google은 개발자가 제어하는 내장 브라우저의 OAuth 사용을 제한한다. [Google OAuth 정책](https://developers.google.com/identity/protocols/oauth2/policies)

## 2. 서버 설정과 실제 연결

1. `.env.local`의 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`에 같은 클라이언트의 값을 입력한다. `APP_BASE_URL`, `LOCAL_OPERATIONS_ENABLED=true`, 기존 `GOOGLE_TOKEN_ENCRYPTION_KEY`, `OPERATIONS_STORE=supabase`와 0단계의 회사 프로젝트를 확인한다. 비밀 값을 포함한 파일 전체 출력이나 스크린샷을 남기지 않는다.
2. 환경변수를 읽는 앱과 worker를 재시작한다. 처음에는 worker를 실행하지 않고 관리자 흐름부터 확인한다. 개발 실행은 `npm run dev -- --port 3002`; production 실행을 사용할 경우 최신 build와 `npm run start -- --port 3002`를 사용하며 같은 포트의 중복 서버를 띄우지 않는다.
3. `/admin`에서 로컬 관리자 로그인 → Google 연결 → 회사 계정 선택 → 요청 권한 확인·승인 → 같은 브라우저의 앱으로 복귀한다. Google 비밀번호·2단계 인증은 사용자가 Google 화면에서 직접 입력한다.
4. **연결됨 표시뿐 아니라 실제 Gmail 라벨 목록·소유 Calendar 목록 조회가 성공하는지** 확인한다. 동의 취소·필수 권한 일부 거절은 성공으로 표시하지 않아야 하며, 다시 연결해 정상 상태로 복구한다. 잘못된 계정·state 재사용은 기존 격리 테스트 근거와 구분한다.
5. 시험 라벨과 시험 Calendar를 선택한다. 기존 Google 이벤트 링크가 없고 전송 대기가 의도한 시험 데이터인지 확인한 뒤 수동 동기화를 수행한다. 동기화 중 선택 변경이 409로 거절되면 현재 실행이 끝난 후 재시도한다.

External/Testing 상태의 이번 권한 조합은 refresh token의 **7일 만료** 조건에 해당한다. 오늘 확인할 토큰 자동 갱신은 access token 갱신이며, 7일이 지나도 연결이 영구 유지된다는 뜻은 아니다. 연결일을 기록하고 만료 시 재연결 절차를 남긴다. 운영 전환 심사·공개 상태 변경은 별도다. [Google 토큰 만료 조건](https://developers.google.com/identity/protocols/oauth2#expiration)

## 3. Gmail 수집 검증

Gmail에서 시험 제목과 시험 발신자를 기준으로 필터 검색 결과를 먼저 확인한 뒤 시험 라벨을 자동 부여한다. 기존 전체 메일을 한꺼번에 라벨링하지 않는다. 답장도 필터 조건을 만족해야 분류되므로 **새 답장 자체에 라벨이 있는지** 확인한다. [Gmail 필터·답장 적용 조건](https://support.google.com/mail/answer/6579?hl=en)

| ID | 실제 시험 | 기대 결과 |
| --- | --- | --- |
| G01 | 라벨이 자동 부여된 새 문의 수신 후 동기화 | 발신자·제목·본문·수신 시각을 가진 문의 1개 저장 |
| G02 | 같은 메일을 대상으로 여러 번 동기화 | 메시지·문의 중복 생성 없음 |
| G03 | 같은 Gmail 대화에 수신 답장 추가, 답장에도 라벨 확인 | 기존 문의에 새 수신 이력 추가, 일정과 기존 본문 보존 |
| G04 | 다른 대화의 문의, 날짜 없는 문의 | 대화별 문의 분리, 날짜 없는 문의는 검토 대기이고 일정 자동 확정 없음 |
| G05 | 선택 라벨 없는 메일, 보낸 편지·초안 | 문의 수집 대상에서 제외; 필요시 라벨을 붙인 수신 메일만 후속 수집 |
| G06 | 시험 HTML 본문·일반 첨부 1개 | 본문 텍스트와 첨부 개수·존재 표시, HTML 실행·첨부 자동 다운로드 없음 |
| G07 | 화면 자동 수집이 한 차례 이상 실행될 때 새 메일 수신 | 수동 버튼 없이 수집됨; 시각·건수·접수번호로 확인 |

대량 pagination·과대/손상 MIME·최신 30개 제한은 기존 격리 테스트를 확인한다. 실제 회사 계정에 대량 메일이나 손상 메시지를 만들 필요는 없다. `Lnkpaintingau@gmail.com`의 공개 문의함과 이번 회사 연동 계정은 다르다. 공개 문의함의 메일을 가져오는 전송/통합 규칙은 이번 연결로 자동 생성되지 않는다.

이벤트는 비공개·시간 비차단이어야 하고, 제목·설명은 접수번호·미확정 상태·앱 링크만 포함한다. 고객 이메일·전화·메일 본문·사진·참석자 초대가 없어야 한다. Google 이벤트의 API `status=confirmed`는 이 앱의 고객 예약 확정 상태와 별개다.

현재 양방향 범위는 **앱이 연결한 이벤트의 날짜·시간·삭제/반복 변경 검토**다. Google에서 임의 생성한 모든 이벤트를 문의로 바꾸거나 제목·설명을 고객 데이터로 가져오는 기능은 아니다. Google 변경 승인도 고객의 예약 수락을 대신하지 않는다.

## 5. 자동 수집·실패 복구·재시작

1. 관리자 화면을 닫고 `npm run integrations:worker -- --once`로 한 번 확인한 뒤 `npm run integrations:worker`를 실행한다. 새 시험 수신 메일과 Calendar 수정을 각각 넣어 **관리자 화면 없이** worker가 수집하는지 확인한다. 주기는 작업 완료 후 약 60초이며 Google 처리 시간까지 포함한 실시간 보장은 아니다.
2. worker와 관리자 polling을 함께 한 번 실행해 중복 저장/이벤트 생성이 없는지 확인한다. 동기화 잠금에 따른 일시적인 409와 실제 Google 장애를 구분한다.
3. 앱과 worker를 정상 종료하고 같은 DB·같은 키로 재시작한다. 계정 연결·선택 라벨/Calendar·접수번호·메일 이력·일정·검토 상태가 보존되는지 확인한다. 둘 다 꺼진 동안 들어온 시험 메일도 재시작 후 중복 없이 수집돼야 한다.
4. 최초 OAuth의 access token 만료 시각을 비밀 값 없이 확인한다. 다른 시험을 진행하며 갱신 시점이 지난 후 재동의 없이 API 요청과 만료 시각 갱신이 성공하는지 확인한다. 당일 그 시점까지 확인하지 못하면 **자동 갱신 실검증 대기**로 남긴다. DB 만료값을 바꾼 시험은 자연 만료 검증과 구분한다.
5. 정상 왕복과 자동 갱신 확인 후, 시험용 앱 연결에 한해 Google 계정에서 권한을 회수한다. 동기화 실패·데이터 보존을 확인하고 회사 계정으로 재연결한다. 선택 대상과 기존 문의/이벤트가 유지되고 실패 작업이 중복 없이 회복되는지 확인한다. 앱 로그아웃은 Google 권한 회수가 아니다.
6. `Sync completed`, `connected`, worker 종료 코드 0만으로 통과시키지 않는다. 현재 코드는 부분 오류를 결과로 반환하며, 10월 1일 보강한 관리자 화면/worker는 이를 실패 표시·종료 상태에 반영한다. Gmail/Calendar 오류, 문의별 `calendarStatus`, 수집/실패 건수와 실제 Google 이벤트를 함께 확인한다. 오류가 성공처럼 보이거나 재연결 안내가 부족하면 재현 후 수정 대상으로 기록한다.

Google의 410·429·5xx, 응답 유실·정교한 동시 변경은 격리 테스트로 검증하고 실서버 오류를 일부러 유발하지 않는다. 실제 발생한 오류는 재현 조건과 복구 결과를 추가한다. 컴퓨터 절전·worker 종료 중 상시 수집은 오늘의 완료 기준에 포함하지 않는다.

## 6. 마무리·사용 준비·검증 기록

시험 중 코드 오류를 수정하면 관련 Next.js 가이드를 읽고 작은 범위로 수정한다. 해당 시나리오 재검증 후 `npm run test:operations`와 `npm run check`를 실행한다. 변경 없는 문서 계획 단계에서는 이미 통과한 코드 검사를 반복하지 않는다. 실제 연동 화면은 데스크톱·모바일 문의 상세/변경 검토, 키보드 조작, 오류·콘솔을 확인한다.

검증 완료 후 **시험 이벤트를 연결했던 동일 저장소에서 먼저** 시험 Calendar 이벤트 삭제→앱의 삭제 검토 승인→동기화 확인으로 시험 일정을 정리한다. 문의 이력과 검증 증거는 보존한다. DB 행이나 Calendar 링크를 직접 삭제해 정리하지 않는다.

그다음 회사가 실제 사용할 Gmail 라벨·필터와 **회사 소유 Calendar**를 확인한다. 화면 polling과 worker를 멈추고 남은 이벤트 연결·전송 대기를 점검한다. 전용 시험 Calendar를 썼다면 모든 시험 이벤트의 삭제 검토와 연결 해제가 끝난 경우에만 운영 Calendar 선택을 시도한다. 기존 업무 링크가 남아 있으면 Calendar 변경을 진행하지 않고 별도 이전 검토로 남긴다. 동일 회사 Supabase 프로젝트에서 운영 대상 선택 후 지정 문의 소량으로 수집·일정 1건을 다시 확인한다. 토큰이나 이벤트 연결을 임의 복사하거나 기존 데이터를 삭제하지 않는다. 운영 대상이 정해지지 않았다면 시험 연동 검증 완료와 실제 사용 전환 대기를 따로 보고한다.

종료 시 실행 중인 앱/worker, 사용하는 Supabase 프로젝트·라벨·Calendar, 남은 시험 문의·이벤트를 기록한다. 이전 SQLite와 별도 오프라인 검증 DB는 비공개로 보관하고 Git에 커밋하지 않는다.

실행 후 `docs/verification/2026-10-01-google-oauth-live.md`에 계정·클라이언트 설정 상태, 시험 ID별 통과/실패/미실행, 접수번호·이벤트 참조·Sydney 확인 시각, 재시작/권한 회수/재연결 결과, 수정과 회귀 검사, 운영 전환 여부를 남긴다. 토큰·비밀번호·메일 본문은 기록하지 않는다. 실행 결과 파일은 실제 검증 후 생성했으며 통과·부분 확인·미실행을 구분한다.

**최종 완료 판정:** 회사 OAuth와 G/C 핵심 흐름, 자동 수집·재시작·재연결이 실제 증거로 통과하고, 실패 항목이 해결됐으며, 실제 사용 대상과 실행 조건이 명시돼야 한다. 자동 갱신 또는 운영 전환이 대기라면 해당 항목을 미완료로 남기고 전체 완료라고 표현하지 않는다. AI·Resend는 이 검증 이후 별도 단계에서 시작한다.

## 실행할 때 필요한 사용자 참여

- 회사 Google 로그인·2단계 인증·OAuth 동의 등 계정 소유자 확인.
- Client Secret을 비공개 로컬 설정에 입력하고, 실제 사용할 라벨·Calendar·문의 분류 기준 확인.
- 시험 발신 계정에서 문의와 답장을 발송. 에이전트의 메일 발송은 별도 명시 요청이 없는 한 수행하지 않는다.

나머지 설정 점검·앱 연결·동기화 확인·오류 수정·검증 기록은 위 순서로 진행한다. 계획 문서와 실제 검증 결과를 구분하며, 최신 연결·시험 상태는 결과 기록을 따른다.
