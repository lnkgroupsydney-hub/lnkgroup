**2026-09-30 KCP 실행 기준:** [25번 계획의 KQ01~KQ14](25-kcp-quote-to-booking-implementation.md)를 아래 기존 서비스 시나리오에 추가한다. 고객 AI 관찰 결과·가격 후보·희망일 요청·회사 duration·최종 수락·인보이스/결제가 이번 검증 범위다. 기존 A/B/C의 KCP AI 일정은 P4로 앞당기되 AI 평가와 공개 기준을 생략하지 않는다. 식품·쇼핑몰 검증이 KCP 출시의 선행 조건은 아니다.

Google Calendar 양방향·자동 날짜 설정에는 [27번 GC01~GC14](27-kcp-google-calendar-sync.md)를 추가한다. P0에서는 Coatly 테스트 **소스만 검토**했으며 실행 통과·원격 DB·실제 Google 연결을 확인하지 않았다. etag 충돌·중복 생성·날짜/시간/DST·watch 갱신·Calendar 장애·인보이스 사실 보호와 Complete 중복/권한·실제 발행일 +3 달력일·발행 재시도는 후속 필수 검증이다.

## 검증 원칙

이 파일은 앞으로 수행할 검증 계획이다. 현재 웹앱이 구현되거나 다음 테스트가 통과했다는 의미가 아니다. 핵심 위험은 잘못된 금액, 중복 예약·결제, 재고 음수, 다른 고객 자료 노출, 식품 배치 오출고다. 이 위험을 먼저 검증하고 단순 화면 문구에 과도한 자동 테스트를 만들지 않는다.

계획·원인 분석·테스트 설계·코드 작성·결과 판단·QA 검토의 모델과 effort는 사용자 선택을 따른다. 별도 지정이 없는 에이전트는 현재 채팅 설정을 상속하며, Sol 모델을 명시할 때는 `gpt-6.1-sol`을 사용한다. 실제 모델 선택 방식은 [개발 운영](13-ai-development-workflow.md)을 따른다.

## AI 출시 판단

최소 100건의 대표 사례를 준비하는 목표를 두되 자료가 없으면 달력상 C 단계가 끝나도 자동확정은 켜지 않는다. 작업·고객 단위로 학습용 개선 자료와 평가용 자료를 분리해 같은 집의 사진이 양쪽에 섞이지 않게 한다. 정상·손상 없음·흐린 사진·복잡한 표면·복수 손상·위험 사례·범위 밖을 포함하고 2명의 작업 전문가가 의견 차이를 조정한다.

첫 목표는 고정 평가셋의 규칙 금액 계산 일치 100%, 포함 보수 중복 과금 0건, 정의한 위험 사례의 자동확정 0건이다. 손상 분류 precision·recall과 과대·과소견적을 서비스별로 보고하고 전체 평균만으로 통과시키지 않는다. 작은 표본에서 0건 오류는 실제 오류 확률 0%를 뜻하지 않는다.

추가금 오차 목표의 초안은 전문가 견적 대비 중앙 절대 백분율 오차 15% 이하이나, 정답이 0인 경우 별도 AUD 절대오차를 쓴다. 서비스별 허용 오차·자동화 한도는 실제 마진과 오류 비용으로 조정한다. 모델 자체 confidence 0.9를 90% 정확도로 사용하지 않는다.

최소 2주 shadow 운영 → 모든 건 담당자 승인 → 제한된 저위험 범위만 활성화 순으로 진행한다. 모델·프롬프트·가격표 변경 시 고정 평가셋을 재실행한다. 위험 누락·과금 오류가 나오면 자동발행을 끄고 기존 문의를 수동 처리한다.

## 비기능 목표

모바일 주요 페이지는 실제 이용자 p75 기준 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하를 목표로 하며 출시 전 합성 측정과 출시 후 실측을 구분한다. 초기 실측이 없으면 목표 달성을 선언하지 않는다. API 응답 p95 1초 목표는 외부 AI·결제 처리 시간을 제외하고 측정한다. 접근성은 WCAG 2.2 AA 목표로 폼·견적·결제의 수동 확인을 포함한다.

제안 부하 조건은 동시 사용자 50명과 20건 결제·예약 경합이다. 실제 운영량에 맞게 조정한다. 결제 처리 성공률에는 사용자 카드 거절을 시스템 장애로 섞지 않고 서버 오류·공급자 장애를 별도로 측정한다.

## 단계별 출시 승인

A는 T02~T11, T13, T18~T19, T21~T24와 서비스 UAT를 통과해야 한다. B는 T12·T14·T15·T25 및 주문·환불 UAT를 추가한다. C는 AI 평가와 T16~T17, 식품 운영 승인을 추가한다. 전체 공통 조건은 치명·높음 결함 0건, 담당자 교육, 롤백·복구·수동 처리 확인이다.

결함은 증상·재현 조건·기대값·실제값·원인·수정·회귀 영향·증거를 남긴다. 검증 기록에는 배포 ID, commit, 데이터·가격표·모델 버전, 테스트 명령, 결과, 담당자를 기록한다. UI만 정상인데 Webhook·DB·회계가 틀린 경우 완료로 판단하지 않는다.
