## 1. 이번 결정과 완료 목표

사용자는 2026-10-02 [18번 후속 흐름](18-kcp-page-prototype.md)을 **고객 정보·디테일 입력/저장 → 서비스·사진 → AI 관찰·가격 결과 → 고객 approve → 앱 달력 시작일 → 최종 확인·전자서명 → 제출 → 고객 이메일로 최종 견적·서명 계약서 → 회사 Google Calendar 자동 업로드**로 구체화했다. [32번](32-client-quote-signature-submission.md)이 이 순서와 제출 경계의 최신 기준이다. 작업 완료 이후 인보이스·결제는 이어지는 별도 업무다. 문의 접수나 회사 Calendar 수동 연동만으로 전체 목표를 완료 처리하지 않는다.

최초 요청의 계획·TODO 갱신 후 P0 명세·정적 검토를 수행했다. 이후 KCP 견적 버튼에서 요청 폼·로컬 저장·운영 검토로 이어지는 구현을 시작했다. 아래는 전체 목표이며 이번 제한된 구현을 전체 완료로 보지 않는다. 실제 가격·예약금·취소 조건은 별도 확정이 필요하다. 과거 Cabinet ‘약 1주’는 소개·문의 접수 목표였으며 이 전체 기능의 납기로 사용하지 않는다.

## 2. 고객 화면과 회사 업무 흐름

전용 `/quote/start?service=cabinet-painting` 페이지를 제안한다. KCP 헤더·Hero·하단의 견적 버튼과 사진 버튼은 하나의 작성 흐름을 사용한다. 사진 버튼은 같은 초안의 사진 단계로 안내하고 필요한 앞 단계 정보를 보완한다. 기존 KCP 소개·공정 화면과 디자인 토큰을 유지한다.

| 순서 | 고객 화면 | 저장·회사 처리 기준 |
| --- | --- | --- |
| 1. 고객·디테일 저장 | 이름·이메일·지역·현장 설명 입력, 저장 결과 확인 | 서버 비공개 초안·작성 권한·revision 발급. 기존 고객과 이메일만으로 합치지 않음 |
| 2. 서비스·사진 | Kitchen Cabinet Painting 선택 확인, 대상·수량·재질·사진 보완 | 목적과 대상 범위를 분리하고 같은 초안에 연결. 실제 파일 검사·소유권·사진 처리 안내 선행 |
| 3. AI·가격 결과 | 문제점·불확실성·담당자 확인 필요와 가격 구성 표시 | AI는 관찰/가격 코드 후보, 금액은 승인 가격표로 서버 계산. 미승인 가격은 결과로 만들지 않음 |

| 5. 앱 달력 시작일 | 가능한 시작 후보와 요청/확정 의미 확인 | 예약된 날짜는 선택 불가·서버 재검사. 회사 기간·충돌 확인 전 요청이며 가용성 조회만으로 확보를 약속하지 않음 |
| 6. 최종 확인·서명 | 고객·주소·범위·총액·약관·시작일/기간 확인, 명시 동의·전자서명 | 견적/약관/일정 snapshot hash에 서명을 연결. 관련 변경 시 새 확인·서명 요구 |
| 7. 최종 제출 | 제출 중·저장 완료·후속 처리 상태 표시 | 서버 현재 버전/소유/서명/가용성 재검사, 불변 submission·outbox를 원자적으로 저장 |
| 8. 문서·고객 이메일 | 최종 견적·서명 계약서의 발송 상태 확인 | 비공개 문서를 같은 submission으로 생성. 제공자 수락·실제 배달·반송을 분리하고 중복 발송 방지 |
| 9. 회사 Calendar | 일정 업로드/검토/확정 상태 확인 | 이메일 제공자 수락 후 별도 outbox로 전송. 회사 기간·충돌 확인 전 요청으로 유지; Calendar 성공만으로 확정 안 함 |

초안 저장이 연락처 수집의 첫 단계다. 전화 필수 여부·주소 상세 수집·보관 정책은 회사 결정으로 남긴다. 서비스 URL은 추천값이며 고객이 서비스를 확인하는 2단계를 생략하지 않는다. 수량·재질은 ‘모름’을 허용하고 정보 부족·사진 불가·AI 실패는 담당자 검토로 이어진다. 사진 없이 분석을 만들거나 가격·서명·발송·예약을 완료로 표시하지 않는다. 앱 밖의 Gmail 문의는 별도 접수 경로로 보존하고 인증된 고객 연결 후 같은 작성 흐름으로 이어갈 수 있다.

### 금액·날짜의 의미

- **기본가격:** 회사가 승인한 포함 범위·수량·세금 규칙의 가격이다. 승인 가격표가 없으면 고객용 금액을 공개하지 않는다.
- **예상 견적:** 선택 범위·수량과 AI의 추가 작업 후보를 반영한 검토 전 금액이다. 고객 수락·청구에 사용하는 확정 견적과 구분한다.
- **확정 견적:** 담당자 또는 별도 승인된 제한적 자동발행 규칙이 승인한 버전이다. 초기에는 담당자가 최종 승인한다. 고객의 기존 수락 내용을 덮어쓰지 않는다.
- **희망일:** 접수된 시작일 선호이며 확정 예약이 아니다. 요청만으로 무기한 자원을 막지 않는다.
- **예약 불가:** 대상 자원의 확정 예약·유효 점유·휴무 등 승인된 정책에 따른다. 회사 전체 1팀인지 복수 팀인지 임의 확정하지 않는다. 고객 화면에는 다른 고객의 이름·주소·작업 내용이 노출되지 않는다.
- **작업 기간:** 달력상의 작업·건조 기간과 직원·부스 등 실제 자원 점유를 구분한다. 회사 제공 3~7일을 모든 견적의 고정 기간으로 사용하지 않는다.

회사가 예약금을 불필요로 정하면 `최종 확인·서명 제출 → 견적/계약 이메일 제공자 수락 → 회사 Calendar 요청 업로드 → 회사 기간·충돌 확인·전체 기간 확보·일정 확정 → 마지막 작업 완료·프로젝트 Complete → 최종 인보이스·결제`로 연결한다. 예약금이 필수로 추후 승인되면 같은 서명 제출·문서/메일·Calendar 요청 흐름 뒤에 `회사 검토·전체 기간 임시 점유 → 예약금 청구·결제 확인 → 일정 확정`의 분기를 추가하고, 최종 청구는 같은 Complete 기준을 따른다. **분기 가능성을 명세에 두되 실제 구현·검증은 회사가 선택한 정책에 맞춘다. 정책 미정을 예약금 불필요로 해석하지 않는다.** 결제 성공 시점에 점유가 만료됐으면 강제 확정하지 않고 대체 일정·환불 검토로 보낸다.

### P0–P1: 입력·화면 계약

- 첫 화면의 고객 정보·현장 디테일 저장 계약을 먼저 정하고, 다음 단계의 서비스 목적과 도장 대상, 단위·수량, 사진 요구를 연결한다. ‘모름’ 입력은 추가 확인 상태로 이어진다.
- 모든 진입점과 모바일 메뉴의 견적 접근, 진행 단계·이전 이동·입력 보존·오류 포커스·키보드 조작을 설계한다. 폼은 기존의 무거운 3D 렌더러에 의존하지 않는다.
- 업로드 진행·부분 실패, 분석 대기·실패, 가격 미정, 가능한 날짜 없음, 제출 중·응답 유실·중복 제출의 화면을 먼저 만든다.
- 로컬 모의 AI는 ‘샘플 분석’, 가격은 ‘테스트 예시’, 제출은 ‘회사에 전송되지 않음’을 명시한다. 샘플 결과를 실제 사진 분석으로 표현하지 않는다.
- 프로토타입에서는 사진을 브라우저 메모리에서 미리보고 종료 시 정리한다. 주소·사진을 무조건 localStorage에 넣지 않는다. 새로고침·탭 종료 후 복구 범위도 안내한다.
- Coatly에서 고객·견적 버전·일정·인보이스의 실제 저장/권한/테스트를 점검해 재사용과 수정 대상을 기록한다. 과거 문서나 화면 존재만으로 재사용 완료로 보지 않는다.

### P2–P3: 접수와 운영 기반

- 익명 작성 세션은 서버가 발급한 만료 가능한 작성 권한에 묶고, 해당 초안의 업로드·분석만 허용한다. 임의 사진 키·다른 고객 ID 연결을 차단한다. 비회원 입력 이메일만으로 기존 고객 거래에 연결하지 않는다.
- 동일한 유효 작성 세션에서는 자기 초안을 이어 쓸 수 있다. 다른 기기/세션에서 저장 자료 조회·재개, 최종 견적 수락에는 이메일 소유 확인 등 검증된 고객 세션을 사용한다. 이메일 입력 전 세션을 잃은 초안은 식별자만으로 복구하지 않는다. 토큰은 로그에 남기지 않고 개인정보 응답은 공용 캐시에서 제외한다.
- 사진 원본/변환본은 비공개로 관리한다. 장수·파일/총 용량·픽셀 한도, 실제 형식 검사, EXIF 제거, HEIC 처리와 지원 불가 안내를 구현한다. 기존 8장·10MB는 검증 전 초안이다.
- 업로드 객체 생성과 DB 저장이 하나의 원자적 작업이라고 가정하지 않는다. `대기 → 업로드 → 검사 → 연결` 상태와 실패 재시도·고아 파일 정리를 두고, 유효 사진 연결 후에만 후속 AI가 읽게 한다.
- 초안 저장·일반 문의 접수와 최종 서명 제출은 별도 명령이다. 같은 요청 키·같은 내용은 같은 결과, 다른 내용은 충돌을 반환한다. 초안/Gmail 접수만으로 자동 메일·Calendar를 예약하지 않는다. 최종 제출의 불변 스냅샷과 문서 작업 outbox는 같은 트랜잭션에 기록하며 외부 실패 때문에 제출을 지우지 않는다.
- 관리자 인증·MFA·역할·담당 범위를 적용한다. 최소 문의함과 알림을 AI보다 먼저 구현해 분석 실패·추가 자료 요청을 처리할 담당 경로를 확보한다.
- 사진·개인정보 삭제/보관 정책은 미제출 초안과 계약 자료를 구분한다. 마케팅 활용 동의와 견적·AI 처리 목적 안내를 분리한다.

### P4: AI 분석과 고객 결과

- 모델은 손상 강도·위치·설명·근거 사진·확인 불가·위험 신호·가격 코드 후보만 반환한다. 허용 스키마/enum을 검사하고 모델에게 DB 변경·메일·결제 도구를 주지 않는다.
- P4는 관찰 결과부터 검증하며 P5의 승인 가격 코드 연결 전에는 코드 후보를 실제 고객 금액으로 노출하지 않는다. 가격 코드 계약은 합성 데이터로 검증할 수 있다.
- 같은 주방의 여러 사진에서 같은 보수 대상이 중복되지 않게 연결한다. 불확실한 병합·재질·수량은 담당자 확인으로 보낸다.
- 사진 집합·작성 내용·모델·프롬프트·스키마 버전을 기록한다. 사진을 교체한 뒤 늦게 도착한 이전 분석이 현재 결과·견적을 덮어쓰지 못하게 한다.
- 작업 큐는 중복 안전 처리·시간 제한·재시도 상한·실패 상태를 가진다. 업로드/분석 요청별 제한과 비용 상한을 적용한다. 응답 후 메모리 작업만으로 분석을 이어가지 않는다.
- 운영자 검토 → 고정 사례 평가 → 승인된 고객 관찰 결과 노출 순으로 검증한다. [09 AI 출시 판단](09-test-and-qa.md)의 대표 사례 목표·shadow 검증 기준을 유지하며, 자료 부족은 완료로 처리하지 않는다. 고객에게 금액 후보를 보이는 단계와 자동 확정 견적 발행 승인은 구분한다.
- AI 장애나 판단 불가에서도 동일 문의를 보존한다. 추가 사진 또는 담당자 검토를 제시하고 재시도 시 중복 분석 비용·중복 문의를 방지한다.

### P5: 가격과 견적

- 기본 작업·포함 준비·문/서랍/패널 수량·추가 보수·옵션·출장·세금·유효기간을 버전 있는 승인 가격표로 관리한다. 회사 제공 핸디맨/실내 도장 가격을 Cabinet 가격으로 전용하지 않는다.
- 승인된 가격 코드만 서버 계산에 사용한다. 포함된 퍼티·샌딩, 동일 보수 영역, 중복 카테고리 비용을 합산하지 않는다. AI가 자유 입력한 금액은 사용하지 않는다.
- 기본가격·추가 작업 후보·세금·총액·포함/제외·검토 상태를 구분해 표시한다. 추가금 후보는 담당자 확인과 고객 동의 전 청구하지 않는다.
- 견적 버전에는 품목·수량·단가·세금·범위·약관·가격표·관련 분석 버전을 보존한다. 담당자 승인/발송과 고객 소유 확인/명시적 수락을 구분한다. 이메일 GET 열람으로 수락되지 않게 한다.
- 고객 approve는 현재 가격·범위를 확인하고 날짜 단계로 이동하는 동작이다. 최종 확인·전자서명·제출과 분리한다. 금액·범위·약관·날짜 변경은 새 버전 또는 variation으로 처리하고 종전 서명은 새 조건의 승인으로 사용하지 않는다. P6에서 제출 스냅샷에 서명 hash를 결합한다.

### P6: 앱 달력·최종 서명 제출·문서와 회사 Calendar

- 지역 기준은 [최신 회사 자료](../reference-assets/company-brief.md)의 **Ermington 10km + Inner West + 명시 21개 suburb**다. 자동 판정 경계가 미정인 주소는 검토 대상으로 받고 10km만으로 일괄 거절하지 않는다. 회사 예약 확정 전에는 실제 주소·예외 승인이 필요하다.
- 고객 캘린더는 승인 자원 정책으로 예약된 날짜를 선택 불가로 표시한다. 조작한 입력과 제출 직전의 새 예약을 서버에서 다시 검사하고 날짜별 가용성 응답에 타인 정보를 포함하지 않는다. 시작일의 후보 가능 여부와 전체 작업 기간의 가용성은 구분하고, 달력 조회 결과만으로 자원을 확보했다고 보지 않는다.
- L&K booking calendar는 [27번](27-kcp-google-calendar-sync.md)에 따라 Google Calendar와 필수 양방향 연동한다. 고객 경로는 최종 서명 제출·문서 생성·이메일 제공자 수락 이후 자동 업로드하며, 단순 초안/Gmail 수신은 자동 전송 조건이 아니다. 요청·확정과 날짜·시간·기간을 구분하고 Google 수정은 앱의 권한·충돌·고객 재서명 필요 여부를 검사한 후 반영한다. 앱 DB에 업무 원본을 보존하고 동기화 실패·재시도·정기 대사를 별도 관리한다. Outlook은 범위에 포함하지 않는다.
- 담당자는 기간과 직원/팀·필요한 공방 자원·이동 버퍼를 설정한다. 실제 점유 구간의 모든 날짜를 DB 트랜잭션·제약으로 검사하고, 두 담당자의 동시 확정도 충돌 없이 처리한다.
- 변경·재예약은 기존 예약을 먼저 잃게 하지 않고 새 가용성을 검사한다. 날짜·금액·조건이 바뀌면 고객에게 변경 내용을 제시하고 필요한 수락을 다시 받는다.
- 저장은 UTC, 표시와 영업 규칙은 Australia/Sydney다. 여름시간·자정 경계·주말·휴무·여러 날 작업을 검증한다.
- 최종 확인 화면은 서명 대상을 재구성할 수 있도록 고객·주소·견적 버전·약관 버전·날짜/기간·요청/확정 의미를 고정한다. 제출 시 현재 버전을 재검사하고 불변 스냅샷·서명 증거·idempotency 결과·outbox를 함께 저장한다.
- PDF 생성·고객 이메일·Calendar는 독립 작업으로 재시도한다. 이메일 제공자 수락 뒤 Calendar를 진행하고 실제 배달·반송은 별도 기록한다. 응답 유실이면 공급자 참조로 조회·대사한 뒤 재시도하며 중복 문서·메일·일정을 만들지 않는다. [32번 상세 계약](32-client-quote-signature-submission.md)을 따른다.

### P7–P8: 청구·결제와 공개

- 인보이스 번호·판매자·세금 상태·품목·견적 버전·계약 총액·기입금·잔액을 일관되게 관리한다. 앱과 외부 회계가 같은 거래의 원본 청구서를 중복 발행하지 않는다.
- 마지막 작업 후 소유자 권한 사용자의 프로젝트 Complete를 기록하고 최종 인보이스를 1회 발행한다. 실제 발행일 + 3 달력일(Sydney)을 납기로 저장하고 Google에 비차단 이벤트로 반영한다. 예정 마지막 작업일은 예상 표시일 뿐 발행 조건이 아니다. [27번 계약](27-kcp-google-calendar-sync.md)에 따라 미승인 금액·필수값 부족은 청구 보류, 더블클릭/재완료/재시도는 중복 방지, Google 장애는 동기화만 재시도한다. 발행/입금 사실은 Google 드래그로 덮어쓰지 않는다.
- Stripe는 기존 제안 후보이며 제공자·회사 계정·수수료·결제수단 승인 후 연결한다. Coatly의 SaaS 구독 결제를 고객 공사 대금 기능으로 재사용하지 않는다.
- 결제 성공 URL은 입금 증거가 아니다. 서명·금액·통화·견적/인보이스 연결을 검증한 사건을 저장하고 중복·역순 Webhook을 안전하게 처리한다. 정기 대사로 누락 상태를 복구한다.
- 예약금·잔금·은행이체/현금 지원 여부는 회사 정책을 따른다. 수동 입금은 권한·증빙·감사 이력을 남기고 예약금을 매출에 이중 합산하지 않는다.
- 취소·변경·부분 환불은 원거래와 연결하고 환불 한도·일정 해제·미수 잔액을 함께 검증한다. 자동화 실패를 담당자가 확인·재처리할 수 있게 한다.
- 공개 전 테스트 환경의 전체 거래·실제 브라우저·운영자 UAT와 데이터/파일 복구를 확인한다. 운영 검증의 실제 과금·발송은 별도 승인 범위에서 수행한다. Preview/noindex와 운영 공개를 구분한다.

## 4. 모듈과 데이터 경계

하나의 Next.js + TypeScript 앱을 유지한다. `src/app`은 라우트·메타데이터·조립만 담당한다. 아래 모듈 이름은 제안이며 P0에서 기존 `service-catalog`와 Coatly 경계를 대조한 뒤 확정한다. 해당 단계가 시작될 때 필요한 계층만 만든다.

| 모듈 | 책임 | 도입 단계 |
| --- | --- | --- |
| `service-catalog` | 기존 KCP 설명·서비스 식별자·선택 옵션 공개 | P1에서 기존 모듈 활용 |
| `enquiries` | 작성 초안·입력 검증·사진 연결·접수·처리 상태 | P1 화면, P2 저장 |
| `customers` | 고객 식별·인증 연결·주소·동의 | P2 |
| `assessments` | 분석 요청·관찰·버전·평가·담당자 검토 | P4 |
| `quotes` | 가격표·중복 제거·견적 버전·회사 승인·고객 approve | P5 |
| `agreements` | 약관 버전·최종 확인·서명 증거·불변 제출·비공개 문서·발송 상태 | P6, 제출 경계는 오늘 선행 |
| `bookings` | 요청·가용성·기간·자원·점유·확정 | P6 |
| `billing` | 인보이스·결제·입금 배분·환불·대사 | P7 |
| `calendar-sync` | 회사 연결·이벤트 mapping·양방향 변경·재시도·대사 | P2 데이터, P3 연결, P6 작업, P7 청구 |

업무 규칙은 `domain`, 사용 사례·외부 포트는 `application`, DB·AI·메일·결제 어댑터는 `infrastructure`, 화면은 `presentation`에 둔다. `domain`은 React/Next.js/공급자를 모르고 `application`이 구체 DB 클라이언트를 가져오지 않는다. 다른 모듈은 공개 진입점으로만 사용한다. 직원 인증·outbox·감사는 업무 모듈에서 재사용하되 새 이벤트 버스를 불필요하게 만들지 않는다.

[04 데이터 계획](04-data-model-and-access.md)의 고객·문의·사진·분석·견적·예약·청구·이벤트 후보를 바탕으로 P0에서 매핑한다. 작성 초안/업로드 세션, 예약 요청과 확정 예약의 분리, 참조키·유일성·동시성·권한을 명시한다. 이 표는 목표 계약이며 실제 도입된 테이블·검증 상태는 [30번](30-supabase-storage-integration.md)과 TODO를 따른다. 서명/문서/최종 제출 저장소는 32번의 선행 조건과 오늘 구현 범위를 구분한다.
