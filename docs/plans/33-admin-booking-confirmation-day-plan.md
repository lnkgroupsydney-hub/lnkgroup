**서명 제출된 요청을 회사가 열람 → 작업 구간 입력 → 필요한 고객 재확인·재서명 → 전체 구간 충돌 검사 → 회사 확정 → Google 반영 확인**까지 연결한다. 기존 회사 전용 데모를 확장하며 실제 고객 계약·운영 예약으로 전환하지 않는다. 기능과 오류 처리부터 구현하고 세부 디자인은 후속으로 둔다. 구현과 실행 수준별 증거는 [10월 3일 검증](../verification/2026-10-03-admin-booking-confirmation.md)을 따른다.

현재 제출본/서명 검토·원자적 작업 점유·확정 상태·변경 조건 재동의 연결과 PDF를 구현했다. 회사 Supabase 신규 schema·21테이블/7 RPC·공개 역할 차단과 회사 Chrome의 저장→키보드 서명·PDF 메일→작업 제안·재서명·확정→실제 Google 이동·재검토·재확정을 확인했다. Google 기본 응답 처리 오류를 수정한 뒤 전체 164개 검사·lint·타입·빌드가 통과했다. 아래는 구현에 사용한 순서와 검증 계약이며 실제 실행 수준과 남은 모바일 터치/별도 날짜 선택 UI는 검증 기록을 따른다.

- 회사 Google/Supabase와 기존 시험 Calendar를 유지한다. 실제 고객·다른 수신자로 범위를 확대하지 않는다.
- 가격·약관은 기존 데모를 유지한다. 관리자 입력으로 실제 가격표나 운영 약관을 확정하지 않는다.
- 근무시간·기간 산식은 미정이다. 자동 기본값 없이 담당자가 시험용 시작/종료와 작업 구간을 직접 입력한다. 여러 날의 전체 기간을 인력 점유로 간주하지 않고 실제 작업 구간을 구분한다.
- 시험 Calendar에 연결된 단일 시험 자원만으로 확정 경로를 검증한다. 이 설정은 회사의 실제 인력·공방·버퍼 정책이 아니다. 운영 자원·근무 규칙이 없으면 운영 확정은 차단한다.
- 요청은 비차단 상태로 유지하고, 검증된 시험 작업 구간만 차단한다. 데모 확정도 앱·Google·문서에 DEMO를 유지한다.

## 3. 구현 방법과 데이터 경계

- `operations`의 기존 관리자 인증·공개 진입점·Calendar 연동을 확장한다. `enquiries`의 불변 제출을 읽되 서명 원본을 기존 문의 수정 API로 바꾸지 못하게 한다. 업무 규칙은 domain, 사용 사례/포트는 application, DB/Google/PDF/메일은 infrastructure에 둔다.
- 회사 검토·작업 구간 제안·고객 재확인·업무 확정과 외부 동기화 상태를 분리한다. 같은 브라우저 작성 권한은 데모 재확인에만 사용하고 운영 고객 인증으로 승격하지 않는다. 새 제안의 확인은 명시적 동작으로 받고 이메일 열람만으로 승인하지 않는다. 기존 관리자 일정 저장·Google `Approve change`도 새 충돌/재동의 절차를 우회하지 못하게 한다.
- 회사가 제안한 정확한 날짜/시간/기간이 기존 서명에 없으면 그 조건을 담은 새 확인본을 받는다. 변경 승인본의 문서·회사 시험 메일 제공자 수락 뒤에 해당 Calendar 변경을 처리한다. 기존 서명/메일 결과는 감사 기록으로 보존한다.
- 확정 직전 앱 점유와 최신 Google busy를 전체 작업 구간에 대해 검사한다. 자기 요청/관리 이벤트만 검증된 연결 ID로 제외하며 다른 busy는 제외하지 않는다. 조회 실패·누락·오래된 결과는 확정을 차단한다.
- DB 트랜잭션과 제약/잠금으로 동시 점유·중복 확정을 막고 같은 트랜잭션에서 outbox를 기록한다. 공급자 호출은 트랜잭션 밖에서 수행하며 기존 lease·중복키·조건부 갱신을 재사용한다.
- 재예약 확정 명령에서는 기존·신규 구간을 함께 점유한다. 새 Google 작업 이벤트의 생성·재조회·busy 검증이 끝나면 `calendar_ready`에서 새 확정 제안/점유로 전환하고 이전 Google 이벤트를 정리한다. 삭제 실패는 과차단으로 남겨 재시도하며 최종 검증/정리가 끝난 `synced`만 화면의 완료 상태다. 삭제 전 의도를 저장하여 응답 유실·삭제 tombstone도 복구한다.
- DB와 Google 외부 편집을 하나의 원자적 트랜잭션으로 잠글 수는 없다. 최신 조회·조건부 이벤트 갱신·반영 후 대사로 경합을 확인한다. 충돌/실패는 검토·동기화 대기로 남기고 무조건 성공 처리하지 않는다. 확정된 기존 예약은 외부 장애나 삭제만으로 해제하지 않는다.
- 확정 시험 작업은 실제 점유 구간만 `opaque`, 요청/전체 요약은 `transparent`로 구분한다. 확정 후 고객 가용성에 DB 점유와 Google busy가 함께 반영돼야 한다.
- PDF는 불변 제출/승인 버전에서 생성하고 source hash·문서 템플릿 버전을 담는다. 새 발송 PDF 바이트는 비공개 DB의 발송 payload에 고정하며 다운로드도 고정된 첨부 바이트를 우선 사용한다. 최초 발송 전/이전 HTML 제출은 같은 불변 자료에서 PDF를 생성한다. 공개 파일 경로나 무인증 다운로드를 만들지 않는다. 이미 고정된 발송 payload는 변경하지 않으며 기존 제출을 자동 재발송하지 않는다.

## 5. 의존성과 오늘 뒤로 두는 작업

- **회사 DB 스키마:** 수동 적용 이력과 실제 schema를 먼저 비교한다. 관리 권한이 복구되지 않으면 기존에 승인된 회사 Dashboard 경로로 필요한 새 SQL만 검토·적용한다. 이력 대조/repair 없이 `db push`, reset, 기존 migration 재적용을 하지 않는다. 계획 작성 후 회사 Chrome Dashboard에서 신규 두 migration만 적용했고 전체 연결/권한 검사를 통과했다. CLI 수동 적용 이력 repair는 아직 남아 있다.
- **Resend 운영 전환:** 회사 발신 도메인·DNS 접근 정보가 없어 실제 고객 발송은 대기다. 현재 회사 수신자 제한을 유지하며 provider accepted와 delivered를 구분한다. 도메인 인증·배달/반송 webhook·운영 환경 설정은 별도 후속 단계다. 시험 메일이 스팸함에 도착한 기존 결과를 받은편지함 배달 성공으로 바꾸지 않는다.
- **운영 예약:** 회사 근무/인력/자원/버퍼·필요 청구 조건과 고객 소유 인증이 준비되기 전에는 실제 예약 확정을 활성화하지 않는다. 담당자 시험 입력을 자동 기간 산식으로 저장하지 않는다.
- **후속:** 사진 업로드·AI 분석·실제 가격/약관·최종 디자인·공개 배포·클라우드 상시 worker는 오늘 확정 흐름과 분리한다.
- **인보이스:** 마지막 작업 후 프로젝트 Complete → 최종 인보이스 발행 → 실제 발행일 +3 달력일(Sydney) 원칙을 유지한다. 오늘 견적/서명 PDF나 예약 확정으로 청구서를 발행하지 않는다.

오늘 목표인 회사 전용 데모의 관리자 검토·변경 동의·Google 반영과 외부 이동 후 재확정은 새 `DEMO-EE6B0405`로 실제 확인했다. 신규 원격 schema·RLS/역할 권한·회사 Gmail PDF·키보드 서명·가용성 API의 점유 변경도 확인했다. A08은 데스크톱 핵심 흐름과 미실행 모바일/터치·별도 작성 세션 날짜 선택 UI를 분리한다. 최종 회사 Gmail 4통/PDF 8개·Google 이벤트 4개·반복 worker 중복 없음·새로고침 복원·320/390px 화면·콘솔 메시지 0까지 확인했다. 실제 동시 확정/제공자 장애 시험을 격리 검사 결과만으로 완료 처리하지 않는다.
