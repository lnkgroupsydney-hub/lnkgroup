## 1B. 예약 날짜 차단과 최종 제출 경계 기반

[32번 CS03~CS07](32-client-quote-signature-submission.md)을 순수 도메인 계약부터 구현한다. 이미 예약된 날짜 판단, 가용성 실패/미정의 검토 상태, 현재 견적/약관/날짜와 서명 hash 일치, 변경 시 재서명, 초안·approve·최종 제출 분리가 대상이다. 가격·근무/기간 규칙은 임의 생성하지 않는다.

오늘의 기반 검증은 **P6의 실제 예약 달력 구현 완료가 아니다.** P6에서 날짜별 개인정보 없는 busy 응답 → UI 선택 차단 → 제출 직전 서버 재검사 → 회사 duration/전체 충돌 확인 → 원자적 자원 점유/확정을 연결하고 실제 브라우저·DB 경합으로 검증한다. 서명 UI·PDF·Resend는 승인 약관·가격·고객 인증·제공자 설정 이후다.

## 1C. OAuth 상태 표시와 복구

### 착수 전 코드 검토에서 확인한 보완 지점

- `supabase-auth.ts`의 `accessToken()`은 만료 직전 토큰 갱신과 비교 후 저장(CAS)을 구현했다. 하지만 refresh HTTP 실패를 모두 재연결 오류로 취급해 일시적인 429/5xx와 구분하지 않는다.
- `supabase-api.ts`의 `syncAll()`은 오류를 일반적인 동기화 실패로 바꾼다. 재연결 필요 원인이 관리자/worker까지 전달되지 않는다.
- Gmail reader의 요청 예외도 네트워크 오류로 바뀔 수 있어 인증 원인을 함께 전달해야 한다. 한 번에 최대 20페이지를 처리한 `partial:true` 결과도 완료와 구분해야 한다.
- 대시보드의 `connected`는 저장된 연결 행과 설정 유무로 계산한다. 권한 회수가 확인된 뒤에도 화면에는 `Connected`가 남을 수 있는 구조다. 이는 소스 검토 결과이며 오늘 실제 권한 회수 시험은 아직 하지 않았다.

### 구현 방법

1. 외부 응답은 인프라에서 해석하고, 도메인/API에는 제한된 오류 코드만 전달한다. `재연결 필요`, `일시적 실패`, `동기화 진행 중`, `대상 미선택`, `일부 처리/다음 페이지 대기`를 구분한다. Google 오류 본문을 그대로 화면·로그에 내보내지 않는다.
2. 갱신의 `invalid_grant` 등 실제 재승인 필요 조건과 시간 초과·429·5xx를 구분한다. 자격 증명 설정 오류·권한 부족·API 설정 오류도 무조건 재연결로 묶지 않는다. 재연결 필요일 때만 회사 재연결 동작을 안내한다.
3. 관리자 화면은 저장된 계정 정보와 마지막 확인 결과를 구분해 표시한다. 최초 연결 저장만으로 정상 사용 가능을 단정하지 않는다. 브라우저 새로고침 뒤에도 확인된 실패가 사라지지 않게 상태 전달/저장을 검토한다.
4. 기존 오류 저장 필드·RPC로 해결 가능한지 먼저 확인한다. 새 상태 필드가 필요하면 최소 migration만 추가하고 4단계 이력 정리를 선행한다. 원래 적용된 migration의 이력을 바꾸거나 토큰을 지워 오류를 숨기지 않는다.
5. 재연결 시 같은 회사 계정만 허용하고 선택 라벨/Calendar·Gmail 중복 기록·문의/일정·변경 검토를 보존한다. 이미 있는 연결 버전 검사와 동기화 잠금을 유지한다.

| R01 | 자연 만료된 access token으로 실제 API 호출 | 재동의 없이 갱신, 저장 만료 시각 증가, Gmail/Calendar 실제 요청 성공. 토큰 값은 출력하지 않음 |
| R02 | 실제 앱/worker 중복 실행의 잠금 확인과 격리된 갱신 CAS 시험 | 실제 중복 실행은 lease에 따라 정상 처리 또는 충돌로 끝남. 늦은 갱신 응답의 덮어쓰기 방지는 별도 지연 응답 격리 시험으로 확인하며 잠금 409만으로 실증했다고 하지 않음 |
| R03 | 별도 시험 제안 일정 1개를 준비한 뒤 회사 Google에서 이 앱의 접근 권한 회수 | 다음 실제 요청에서 실패 확인, 재연결 안내, 문의·일정·전송 대기·검토 원본 유지 |
| R04 | 동일 회사 계정 재연결 후 동기화 | 원래 선택 대상·접수번호·이력이 유지되고 Calendar 중복 생성 없이 복구 |
| R05 | 일시 네트워크 오류/429/5xx를 격리 시험 | 재승인을 강요하지 않고 안전한 재시도, 실패를 성공으로 표시하지 않음 |

R01에서는 DB의 만료 시각을 조작하지 않는다. 아직 유효하다면 관찰한 자연 만료 이후 실행하고 그동안 독립 작업을 진행한다. R03~R04 전에는 반복 worker/polling을 멈추고 진행 중 lease가 해제됐는지 확인한다. 사용자 본인의 Google 권한 회수·로그인·동의가 필요한 시점에 안내한다. 그 준비 전에는 실제 권한을 끊지 않는다.

External/Testing과 현재 Gmail·Calendar 권한 조합에서는 refresh token에도 7일 만료 조건이 적용된다. access token 자동 갱신 성공은 장기 연결 유지 증거가 아니다. 게시 상태 변경·심사·장기 운영 전환은 별도다. [Google 공식 만료 조건](https://developers.google.com/identity/protocols/oauth2#expiration)

## 2. 관리자 화면 없는 worker와 중단 복구

착수 전 `scripts/integrations-worker.mjs`는 `syncAll()`을 호출하고 실행 종료 후 60초 뒤 반복하는 구조다. 실패 종류별 지연/복구를 보강하고 최종 구현 기준으로 검증한다. 별도 HTTP 관리자 세션 없이 서버 환경설정으로 실행하므로 브라우저·Next 서버와 분리해서 시험할 수 있다.

1. 관리자 화면을 닫고 반복 worker만 실행한다. 사용자 시험 메일이 다음 정상 주기에 수집되는지 확인한 뒤 반복 주기에서도 문의/이력이 중복되지 않는지 대조한다.
2. 앱과 worker를 모두 중단한 시각을 기록한다. 중단 중 사용자 시험 메일을 받은 뒤 worker만 재시작해 누락분이 들어오는지 확인한다. 이후 앱을 열어 같은 데이터가 표시되는지 대조한다.
3. 최초 문의, 같은 대화 답장, 별도 대화를 구분한다. 기존 일정이 있는 문의의 답장 수집은 원래 일정·원문을 덮지 않아야 한다.
4. worker 중복 실행·관리자 polling과의 경합에서는 기존 DB lease가 쓰기를 보호해야 한다. 건너뛴 실행을 신규 수집 성공으로 세지 않는다.
5. Gmail 페이지 커서·중복 키·실패 항목의 재시도와 중단 직후 재시작을 확인한다. 현재 저장된 page token이 무효가 되면 같은 커서로 계속 실패할 수 있으므로, 제공자가 무효 커서임을 확인한 경우에만 한 번 초기화 후 재조회하고 기존 중복 키로 보호하는 복구를 격리 테스트부터 구현한다. 일반 400·429·5xx를 무조건 커서 초기화로 처리하지 않는다. 페이지 경계·커서 만료·처리 중 중단 시험과 실제 소량 복구를 구분한다.
6. 필요한 경우 로그에 실행 시각·수집/실패/건너뜀 건수·재시도 이유를 더한다. 일시 오류는 지연 후 재시도하고 재연결 필요 상태에서는 불필요한 요청을 줄이는 동작을 검증한다. 최종 지연 규칙은 API 오류 조건과 기존 60초 주기에 맞춰 명세한다.

정상 종료와 강제 종료를 구분한다. 강제 종료 후 기존 lease는 최대 10분 남을 수 있으므로 즉시 재시작 성공을 가정하지 않는다. lease를 DB에서 임의로 삭제하지 않고 정상 만료 후 획득·이전 실행의 늦은 쓰기 거부를 확인한다. 긴 만료 대기는 격리된 시계 제어 시험과 실제 대기 시험을 구분한다.

| ID | 완료 기준 |
| --- | --- |
| W01 | 브라우저/Next 앱을 사용하지 않은 worker 신규 수집과 반복 중복 0건 |
| W02 | 앱/worker 중단 중 들어온 신규 메일과 같은 대화 답장을 재시작 후 모두 반영 |
| W03 | worker 중복·잠금 만료·진행 중 종료 뒤 중복 저장/이벤트 생성 없이 복구 |
| W04 | 부분 실패·아무 작업도 하지 않은 실행·정상 완료를 로그와 종료 상태에서 구분 |

오늘은 수동 실행한 로컬 반복 worker의 동작을 검증한다. 상시 호스팅·스케줄러·Mac 자동 실행 등록은 실행 환경 결정 이후다. 검증 종료 시 어떤 프로세스를 유지/중단했는지 기록한다.

## 4. Supabase 점검과 migration 이력

1. `xlqyafthsxallostcqfe` 프로젝트 접근 가능한 회사 인증으로 security/performance advisors를 조회한다. 서버 Secret key의 Data API 접근과 CLI/MCP 관리 권한은 별개다. 접근 불가면 필요한 권한만 확인하고 다른 회사 프로젝트로 대신 실행하지 않는다.
2. 적용된 12개 업무 테이블, 인덱스·제약·RLS·역할 권한·RPC 정의를 `20261001100420_operations_supabase.sql`과 비교한다. 데이터 행과 비밀 값을 내보내지 않는다.
3. CLI가 필요하면 설치된 버전과 `--help`로 실제 명령을 확인한다. 프로젝트 연결·관리 인증·DB 접근 준비 상태를 확인한 뒤 로컬/원격 migration 목록을 비교한다.
4. **실제 스키마가 일치할 때만** 수동 적용한 버전 `20261001100420`, `20261002100953`, `20261002101142`를 각각 `migration repair … --status applied`로 이력에 반영한다. 불일치는 먼저 원인을 분류한다. `repair`가 스키마 차이를 고쳐 주는 기능은 아니다. [공식 migration repair](https://supabase.com/docs/reference/cli/supabase-migration-repair)
5. 이력 목록과 스키마·health를 다시 대조하고 이미 적용한 생성 SQL의 재실행이 예정되지 않는지 확인한다. 현재 CLI/MCP 관리 인증과 repair는 대기이므로 이력 복구 전 `db push`하지 않는다. 운영 DB reset·기존 생성 SQL 무조건 재실행은 이 계획에 포함하지 않는다.
6. 새 migration이 필요하면 CLI `migration new`로 파일을 만들고 격리 DB/RLS/RPC 검증 후 적용한다. 기존 문의·메일·토큰·일정 보존을 전후 대조한다. 실행 권한이 없으면 그 변경에 의존하는 단계는 대기한다.

Supabase 변경 기록의 Markdown 주소는 조회 오류여서 [HTML 변경 기록](https://supabase.com/changelog)을 확인했다. 구현 시 설치 버전·해당 기능의 최신 문서를 다시 확인하며 이번 계획만으로 패키지/DB 엔진을 변경하지 않는다.

## 5. 운영 대상 결정과 소량 검증

시험을 마친 뒤 아래 항목의 실제 값을 정한다. 정해지기 전에는 현재 시험 대상에서 계속 검증한다.

| 결정 | 정할 내용 |
| --- | --- |
| 문의 수집 범위 | 회사 Gmail의 문의 전용 라벨과 정확한 필터 조건. 기존 메일까지 수집할지와 답장 포함 방식 |
| 실제 Calendar | 회사가 owner인 Calendar, 팀 공유 범위, 현재 시험 Calendar 재사용 여부 |
| 두 회사 이메일 | 공개 문의 `Lnkpaintingau@gmail.com`과 연동 `Lnkgroupsydney@gmail.com`을 유지할지, 전달할지, 공개 주소를 바꿀지 |
| 상시 실행 | 이후 회사 승인 환경에서 worker를 어디에 실행하고 장애를 누가 확인할지 |

운영 라벨 후보를 제안할 수 있지만 실제 값으로 자동 확정하지 않는다. 전체 Gmail 일괄 수집·메일 자동 전달·공개 이메일 변경·클라우드 배포는 각 결정 후 진행한다.

전환 직전 worker/polling을 멈추고 시험 이벤트를 Google 삭제 → 앱 검토 승인 → 재동기화로 정리한다. 활성 연결·outbox·검토가 남으면 선택 대상을 바꾸지 않는다. 새 대상을 선택한 뒤 가상 문의 소량으로 수신→문의함→일정→Google 검토를 확인한다. 기존 문의는 삭제하지 않고 실제 고객에게 자동 메일·초대장을 보내지 않는다.

현재 채팅의 모델·effort와 [에이전트 상속 정책](13-ai-development-workflow.md)을 따른다. 고객 초안·도메인 기반과 OAuth/worker 수정, 읽기 전용 DB·시험 검토를 파일 소유 범위별로 나누고, 실제 회사 연동 쓰기 시험은 한 실행 주체가 순서대로 수행한다.

의미 있는 실패 조건을 재현하는 자동 테스트를 먼저 보완하고 변경 관련 테스트 → `npm run test:operations` → `npm run check` 순으로 확인한다. DB 변경이 있으면 권한·저장 검증도 수행한다. 마지막으로 고객 첫 저장→서비스 입력/재조회와 관리자 연결/실패 화면·핵심 링크·키보드·모바일·콘솔을 실제 브라우저에서 확인한다. 새 고객 저장 검증과 OAuth 실제 재연결·worker 실수신 시험의 통과 범위를 분리한다. 통과한 검사는 후속 변경이나 새로운 위험이 없으면 반복하지 않는다.
