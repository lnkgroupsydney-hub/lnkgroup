# 자동화와 통합 운영

**2026-10-02 KCP:** [27번 Calendar 계약](27-kcp-google-calendar-sync.md)과 [32번 고객 제출 경계](32-client-quote-signature-submission.md)를 따른다. 회사 OAuth·Gmail/Calendar 핵심 연결은 [10월 1일 기록](../verification/2026-10-01-google-oauth-live.md)에서 확인했고 오늘은 고객 초안 선저장·서비스 정보, OAuth 상태/worker 복구를 구현한다. 고객 자동 경로는 최종 서명 제출 → 비공개 quote/계약서 → 이메일 제공자 수락 → Calendar 요청이며 회사 기간·충돌 확인 후에만 예약 확정한다. 실제 AI·Resend·사진·서명·고객 달력·청구는 후속이다.

## 이벤트 중심 업무

자동화는 상태가 바뀌면 다음 업무를 실행하는 방식이다. 고객의 화면에서 버튼이 눌렸다는 사실보다 서버에 확정된 상태를 기준으로 한다. 관리자는 자동화 성공 여부, 재시도 횟수, 실패 사유, 다음 담당자를 확인할 수 있어야 한다.

| 이벤트 | 자동 실행 | 예외 처리와 담당 |
| --- | --- | --- |
| enquiry.submitted / gmail.imported | 일반 문의 접수·담당자 검토 | 고객 최종 계약 제출 아님. 자동 견적/계약 발송·Calendar 생성 금지 |
| quote.approved / scope.approved | 회사 승인 버전 준비 / 고객 날짜 단계 진입 | 만료·대체 버전 재확인. KCP 자동 발송/최종 서명과 분리 |
| quote_submission.submitted | 불변 원본으로 비공개 최종 견적·서명 계약 문서 생성 | 오래된 서명/버전·예약된 날짜 거부, 생성 실패는 동일 제출 재시도 |
| submission_documents.ready | 고객 이메일 작업 생성 | 제공자 미설정/실패/결과 불명은 Calendar 보류 |
| submission_email.provider_accepted | 회사 Calendar에 Pending confirmation 요청 업로드 | 실제 배달/반송은 별도 상태. 중복/응답 유실은 공급자 참조로 대사 |
| booking.confirming / confirmed | Google 작업 이벤트 반영·확정 조건 검사 후 고객·직원 확인 | 최초 연동 실패는 sync_pending/검토, 이미 확정된 예약의 후속 장애는 기존 약속 보존·재시도 |
| calendar.change_received | 앱/Google revision 비교·변경 요청·가용성 검증 | 충돌·고객 재동의·청구 권한 필요 시 검토 큐 |
| invoice.plan_changed / issued / payment_recorded | 승인 규칙으로 미발행 계획 날짜 계산, 발행/납기/입금 이벤트 자동 갱신 | 이미 발행된 사실 보존, Calendar 편집은 입금 증거 아님 |
| booking.upcoming | 24시간 전 안내 기본안 | 재예약·취소 시 예약된 안내 취소 |
| project.completed (KCP Complete) | 마지막 작업 후 소유자 권한 사용자의 완료 처리 → 최종 인보이스 발행 → 실제 발행일 + 3 달력일 납기 → Google 자동 표시 | 개별 job/task 완료는 발행 조건 아님. 미승인 추가금/필수값 누락은 청구 보류, 중복/재완료는 같은 인보이스 반환 |
| payment.succeeded | 입금 배분·영수증·진행 상태 | 금액 불일치 → 출고·확정 보류 |
| order.paid | 출고 또는 제작 작업 생성 | 재고 경합 → 담당자 알림·환불 경로 |
| order.dispatched | 추적·보관 안내 | 식품 배송 사고 → 품질 사건 연결 |
| invoice.overdue | 정해진 일정의 리마인더 | 분쟁·환불·유예 상태 → 발송 중단 |
| automation.failed | 운영 대시보드·경고 | 담당자 수정 후 재실행·감사 기록 |

위 KCP 자동 경로는 일반 문의 접수·관리자의 명시적 검토용 제안과 구분한다. 문서·메일·Calendar는 별도 outbox/중복키·실패 상태를 갖고 같은 제출로 복구한다. 반송 때문에 서명 원본이나 일정을 자동 삭제하지 않는다.

이메일은 최초 승인된 템플릿을 사용한다. 서비스·키트·김치별 발신 이름과 reply-to를 정하되 실제 소유 도메인을 확인한다. 발신 도메인 SPF·DKIM·DMARC와 반송·수신거부 처리를 구성한다. 견적 수락은 이메일 링크를 통한 고객 행동이고 이메일을 보냈다는 사실만으로 성립하지 않는다.

각 서비스 상세의 문의는 service_id와 담당 사업 단위를 포함해 접수한다. KCP는 선택한 회사 Gmail 라벨의 문의와 답장을 메시지 ID·대화 연결로 수집한다. 일반 서비스의 다른 수신함·자동 전달·첨부 다운로드를 함께 활성화하지 않는다. 실제 AI 입력 사진은 고객 업로드 소유/검사를 거쳐야 하며 수신 첨부를 무조건 처리하지 않는다. 대표 이메일 주소의 소유·발신 권한은 착수 때 확인한다.

## 인보이스와 입금

KCP 최종 청구는 사용자 지정 2026-09-30에 따라 **마지막 작업 후 프로젝트 Complete 버튼**이 발행 조건이다. 납기는 Sydney 기준 실제 발행 날짜에서 **달력일 3일 후**로 명세한다. 예정 종료일이나 Calendar 편집으로 자동 발행하지 않는다. 발행 재시도가 늦어지면 실제 발행일을 사용하고, Calendar/PDF/메일 실패는 동일 인보이스의 후속 작업만 재시도한다. [27번 Complete 처리·날짜 계약](27-kcp-google-calendar-sync.md)을 따른다. 예약금/중도금·발송 채널은 별도 미결정이며 현재는 명세만 작성했다.

기본안은 앱이 invoice를 발행하고 회계 시스템으로 내보내는 구조다. 기존 Xero 등에서 반드시 번호를 발급해야 한다면 외부 회계가 번호 원본이 되고 앱은 해당 ID와 문서를 참조하도록 전환한다. 두 시스템이 독립적으로 같은 거래의 법정 인보이스를 발행하지 않는다.

인보이스에는 발행 사업자, ABN, 고객, 날짜, 문서번호, 품목·수량·금액·세금·합계, 결제 조건, 예약금 반영, 잔액을 담는다. GST 미등록이면 Tax Invoice 표기를 쓰지 않는 등 상태별 템플릿을 구분한다. ATO의 [세금 인보이스 자료](https://www.ato.gov.au/api/public/content/0-1e92db95-a75c-4f4e-a3d4-39f43b1a3b25)를 회계 담당자가 검토한다.

예를 들어 계약 총액 A$1,100과 예약금 A$110이면 잔액은 A$990이다. 최종 인보이스에 총액 A$1,100과 기입금 A$110을 보여주거나 회계가 승인한 분할 청구를 쓰되, 매출을 A$1,210으로 계산하지 않는다. 청구 발행·결제 완료·은행 정산은 다른 사건이다.

Stripe 정산 수수료와 환불·분쟁은 원 결제에 연결한다. 현금·은행이체는 관리자 수동 입금 등록과 증빙으로 시작하고, 실제 은행 연결은 별도 범위로 둔다. 카드 영수증을 자동으로 세금 인보이스와 동일시하지 않는다.

## API 계약 초안

| 경로 | 요청·선행 조건 | 응답·중복 방지 |
| --- | --- | --- |
| POST /api/service-area/check | 주소와 서비스 ID, rate limit | eligible/review/outside, 정책 버전, 만료 |
| POST /api/enquiries | 입력·사진키·연락처·동의 | enquiry_id, idempotency_key |
| POST /api/quotes/{id}/accept | 일반 견적 수락: 소유 확인, version, hash | acceptance_id, 이미 수락이면 동일 결과. KCP 단계 계약은 26·32번 |
| POST /api/quote-submissions | KCP 고객 소유·현재 견적/약관/날짜·서명·중복키 | 불변 submission·pending_confirmation, outbox 원자 저장·다른 내용 충돌 |
| POST /api/booking-holds | accepted quote, 희망 slot, resource | hold_id, expires_at, 409 충돌 |
| POST /api/checkout | hold 또는 cart, 서버 계산 | Checkout URL, 동일 키 재호출 동일 세션 |
| POST /api/webhooks/stripe | raw body, signature | 영속 수신 후 빠른 2xx, 중복 무해 |
| POST /api/admin/refunds | 권한, 사유, 금액, 결제 version | refund_request_id, 비동기 완료 |
| POST /api/admin/stock-adjustments | SKU·수량·사유·권한 | movement_id, 감사 이벤트 |

모든 변경은 요청 스키마 검증, 서버 인증·권한, 상태 선행 조건, 금액 검증을 갖는다. 사용자에게는 안전한 오류 코드와 재시도 방법을 보여주고 내부 로그에만 원인·correlation_id를 남긴다. 원본 카드·주소·사진·서명 토큰을 로그로 출력하지 않는다.

## 관리자 업무 절차

매일 아침 운영자는 신규 문의·견적 승인 대기·당일 배정·결제 확인 대기·미출고·실패 자동화를 확인한다. 업무가 미처리되면 대표에게 전달되는 시간과 책임자를 설정한다. 제안 대응 목표는 영업시간 내 문의 1영업일, 금액·중복 결제 문제 즉시 확인, 식품 품질 사건 즉시 판매 보류다.

현장 직원은 출발 전 작업 범위와 주소를 확인하고, 도착·시작·완료를 기록한다. 추가 작업 발견 시 variation을 요청하며 고객 승인 없이 범위를 확대하지 않는다. 김치 출고 담당자는 배치·기한·수량·포장·온도 관리 기준을 확인한 뒤 출고한다.

주 1회 대표는 유효 문의→견적→수락→실제 완료, 주문→출고→환불, 매출→원가→기여이익을 본다. 월 1회 권한·백업 복구·보류 고객·세금 보고·재고 실사와 외부 공급자 비용을 검토한다.

## 장애와 복구

| 상황 | 고객에게 보여줄 상태 | 운영 조치 |
| --- | --- | --- |
| AI 장애 | 접수 완료, 담당자 검토 예정 | 자동견적만 끄고 수동 큐 처리 |
| 이메일 장애 | 앱에서 접수·견적 확인 가능 | 실패 재시도, 반송 연락처 확인 |
| 결제 확인 지연 | 중복 결제 없이 확인 중 | Stripe 조회와 DB 대조 |
| DB 장애 | 신규 결제 진입 보류 | 복구 후 Webhook 재처리와 대사 |
| 재고 불일치 | 해당 SKU 판매 보류 | 실사·조정·이미 결제된 주문 처리 |
| 식품 배치 문제 | 해당 상품 주문 일시 중단 | 배치 격리·대상 조회·승인된 회수 절차 |

복구 목표 초안은 핵심 거래 RPO 1시간·RTO 4시간이다. 목표를 만족하려면 선택한 PITR·백업 옵션과 실제 복구 시험이 필요하며 기본 일일 백업만으로 1시간 RPO를 주장하지 않는다. 예산상 일일 백업만 사용하면 RPO를 24시간으로 조정하고 대표가 수용해야 한다. Storage 객체는 DB 백업에 포함되지 않으므로 사진·문서 파일의 별도 백업·복원을 설계한다. [Supabase 백업](https://supabase.com/docs/guides/platform/backups)

## 인수인계

도메인·Git·Supabase·Vercel·Stripe·이메일 계정은 고객 소유로 개설한다. 계정 목록, 역할, 비상 연락처, 환경 변수 이름 목록, 배포·복구·환불·재고 조정·식품 회수 SOP를 제공한다. 비밀 값은 문서에 쓰지 않는다. 운영자 2회 교육과 고객이 직접 실행하는 UAT 후 인수한다.
