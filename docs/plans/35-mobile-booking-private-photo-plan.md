## 3. 1번 — 예약·서명 검증과 필요한 수정

### 현재 구현

- 공통 `src/shared/ui/signature-pad.tsx`는 Pointer Events, pointer capture, 정규화 좌표, 지우기·키보드 서명을 지원한다. 최초 서명과 회사 일정 재서명이 이를 공유한다.
- `demo-quote-flow.tsx`는 예약된 날짜 비활성화, 조회 만료, 날짜 변경 시 서명 초기화, 제출 충돌 시 재선택을 처리한다.
- `infrastructure/demo-availability.ts`는 Google busy와 DB 점유를 합친다. `infrastructure/demo-api.ts`는 검토와 제출 직전에 최신 상태·초안 버전을 재검사한다.
- 별도 고객 세션의 날짜 화면 차단(M01)과 서명 에뮬레이션을 추가 확인했다. 에뮬레이션·키보드·API 결과는 실제 휴대폰 손가락 서명 완료를 대신하지 않는다.

### 시험 세션·실제 기기 준비

1. 회사 브라우저에서 현재 확정된 시험 작업 구간을 읽어 차단 대상일을 정한다. 이전 기록의 10월 22·23일을 오늘도 같은 상태라고 가정하지 않는다. 오늘과 날짜 경계 계산은 Sydney 기준이다.
2. 기존 작성 세션을 보존한 별도 고객 세션을 만든다. 우선 같은 회사 Chrome에서 `127.0.0.1`과 `localhost`의 host-only 쿠키 분리를 확인한 뒤, 별도 로컬 서버에 맞는 `APP_BASE_URL`을 적용하는 방법을 사용한다. **포트만 변경하면 쿠키가 분리되지 않는다.** 기존 localhost 자료에 영향이 있으면 별도 방법을 마련하고 쿠키를 삭제·복사하지 않는다.
3. 실제 휴대폰은 Mac의 loopback URL에 곧바로 접근할 수 없으므로, 회사 계정 기기와 USB localhost 전달 등 기존 보호를 유지할 수 있는 연결 방법을 먼저 확인한다. 이 검증을 위해 Origin·loopback 보호를 해제하거나 공개 터널을 만들지 않는다.
4. 실제 기기가 없으면 터치 에뮬레이션과 코드 검증을 먼저 기록한다. 실제 기기 확인 항목은 미완료로 남긴다. 시험 후 임시 앱/탭을 정리하며 확인용 스크린샷은 저장하지 않는다.

## 4. 2번 — 사진 업로드의 사용자 흐름

**고객 정보 저장 → 서비스 상세 저장 → 사진 선택·업로드 → 저장 완료/복원 → 데모 견적 확인 → 승인·날짜·서명·제출**로 연결한다.

- 서비스 저장 후 바로 데모 견적으로 넘어가던 위치에 사진 영역을 넣는다. 카메라/앨범 선택, 복수 파일, 썸네일, 개별 진행·실패·재시도·삭제 상태를 제공한다.
- 저장된 사진과 기기에서만 선택된 미저장 파일을 구분한다. 성공한 파일은 부분 실패 때문에 사라지지 않으며, 새로고침 후에는 서버에 연결 완료된 사진만 복원한다. 브라우저 메모리 파일 자체의 재개를 약속하지 않는다.
- 사진 업로드 목적·비공개 보관 안내 확인과 문구 버전을 기록한다. AI 처리·마케팅 동의로 확대 해석하지 않는다. 이번 단계에서 AI에는 전송하지 않는다.
- 전체 모습·표면·손상 부위 촬영을 안내한다. 사진이 없어도 기존 담당자 검토/회사 데모 경로를 유지하되 AI 분석 완료로 표시하지 않는다.
- 업로드/삭제 처리 중에는 다음 승인 단계로 진행하지 못하게 한다. 실패한 사진은 재시도하거나 명시적으로 목록에서 제외한 뒤 진행한다.
- 관리자 제출 상세에는 해당 제출에 고정된 사진 목록과 비공개 미리보기를 제공한다. 이메일/PDF에는 사진 개수·참조를 표시할 수 있으나 사진 원본이나 접근 URL을 첨부하지 않는다.
- 고객의 최종 검토 화면에도 서명 대상 사진 개수·썸네일·참조를 표시해 어떤 사진 목록에 동의하는지 확인하게 한다.

### 초기 개발 제한안

기존 P0의 **8장·장당 10MB·총 80MB**를 회사 데모 시험 한도로 재사용한다. 운영 사진 정책 확정은 아니다. 코드 상수 한곳과 화면 안내를 함께 관리한다.

- 1차 허용 형식은 JPEG·PNG·정적 WebP. 확장자·브라우저 MIME뿐 아니라 실제 파일 디코딩을 검사한다. SVG·문서·움직이는 이미지·손상 파일은 거절한다.
- HEIC/HEIF는 이번 1차 지원에서 제외하고 JPG/PNG 변환 안내를 제공한다. 실제 iPhone 선택 결과를 검사하여 미지원 파일을 정상 업로드로 오인하지 않는다. HEIC 지원 추가는 코덱/실기기 검증을 거친 후속이다.
- 임시 기술 한도는 입력 50메가픽셀, 정규화본 긴 변 4096px·최대 6MB다. 방향 보정 후 EXIF/GPS 등 메타데이터를 제거하고 재인코딩한다. 검증용 사진에서 선명도/메모리/처리시간을 확인해 조정하며 실제 분석 적합성을 보장하지 않는다.
- 처음에는 파일을 한 번에 하나씩 처리한다. 서버에서도 요청·바이트·픽셀·처리시간과 세션/전체 동시 처리 한도를 검사한다. 장수/용량 계산은 진행 중 예약까지 포함해 동시 요청 우회를 막는다.

## 5. 저장·접근·버전 계약

### 현재 앱에 맞춘 전송 방식

현 작성 권한은 `/api/quote` 경로의 HttpOnly 쿠키이며 Supabase Auth 사용자 JWT가 아니다. 1차는 **동일 출처 앱 API가 작성 권한 확인→제한된 파일 수신→이미지 검증/정규화→서버 전용 Storage 업로드**를 맡는다. 사용자 파일 원본은 요청 처리 동안만 취급하고, Storage에는 검증된 정규화본을 저장한다.

이 방식은 현 작성 세션을 그대로 사용하고 저장 전 검사를 보장하지만 앱 서버의 파일 처리 부담이 있다. 임시 로컬 데모의 제한된 동시 처리에 적용한다. 공개 배포 전에는 호스팅 요청 크기·실행시간을 재검토하며 필요하면 비공개 임시 버킷의 직접/재개 업로드→검증→연결 방식으로 바꾼다. 기존 P0의 signed upload API는 이 대안이며 이번 단계에서 둘 다 구현하지 않는다. Supabase는 작은 파일의 표준 업로드를 안내하고 6MB 초과 전송에는 재개 업로드를 권장한다. [공식 업로드 문서](https://supabase.com/docs/guides/storage/uploads/standard-uploads)

### 데이터 구조

- 회사 프로젝트에 비공개 버킷 `quote-photos`와 메타데이터 테이블 `lk_quote_photos`를 생성·검증했다. 버킷은 private, 저장 MIME은 정규화된 JPEG만, 객체 한도는 6 MiB다. 기존 업무 테이블을 포함한 22개 테이블과 새 테이블/RPC의 공개 역할 차단을 확인했다.
- 사진 레코드에는 `id`, `draft_id`, 서비스 참조, 서버 생성 객체 경로, 상태, 입력/저장 바이트 수, MIME, 가로/세로, 내용 hash, 처리/안내 버전, 중복 요청 키, lease·만료·오류 정보와 생성/갱신 시각을 둔다. 경로에는 이름·주소·이메일을 넣지 않는다.
- 상태는 `pending → processing → attached`, 실패는 `rejected/retryable_error`, 삭제는 `delete_pending → deleted`로 구분한다. 만료 중단 건은 lease 만료 후 회수하며 오래된 처리 응답은 새 상태를 덮지 못한다.
- 장수/용량 예약과 소유·만료·제출 여부를 DB에서 검사한다. 연결/삭제 확정 시 초안 revision을 원자적으로 증가시키고 서버가 계산한 사진 목록 hash를 갱신한다. 같은 요청 키·같은 파일은 같은 결과, 다른 파일은 충돌이다.
- 원격 객체 저장과 DB 연결을 한 트랜잭션으로 취급하지 않는다. 객체 성공 후 DB 실패 시 저장 완료를 표시하지 않고 기록된 상태로 재대사한다. 임의 전체 버킷 삭제가 아니라 이 앱의 식별된 미연결 객체만 정리한다.
- 연결된 객체는 upsert/덮어쓰기를 금지한다. 교체나 새 처리 시도는 새 식별 경로를 사용하며, 응답 유실 재시도에서는 기존 객체의 내용 hash를 대조해 재사용 여부를 판정한다. 불변 제출의 참조뿐 아니라 해당 이미지 바이트도 보존한다.

### 접근과 삭제

- 버킷은 비공개다. 새 메타데이터/RPC는 기존 서버 전용 권한과 RLS를 따르며 `anon/authenticated` 직접 접근을 열지 않는다. 브라우저에 secret key를 보내지 않는다. 비공개 버킷의 접근 방식은 [Supabase 공식 문서](https://supabase.com/docs/guides/storage/buckets/fundamentals)를 따른다.
- 매번 현재 작성 세션의 자기 초안 또는 인증된 회사 관리자의 해당 제출 접근권한을 검사한다. ID/경로를 아는 것만으로 조회·추가·삭제할 수 없다. Storage 서버 비밀키 사용은 앱 소유 검사 대신이 아니다.
- 고객 미리보기는 같은 `/api/quote` 하위의 인증된 이미지 응답으로 전달하고 관리자 미리보기도 관리자 검증을 거친다. `private, no-store`와 올바른 이미지 MIME을 사용한다. 공개 URL·사진 바이트/base64·쿠키·객체 URL을 로그/분석/localStorage에 남기지 않는다.
- 미제출 사진 삭제는 먼저 접근 불가 상태와 초안 버전을 확정한 뒤 객체 삭제를 수행하고, 실패하면 지속 가능한 삭제 대기 상태로 재시도한다. 이미 제출에 연결된 사진은 이 초안 삭제 경로로 지울 수 없다.
- 기존 작성 권한 유효기간 24시간은 보관정책과 다르다. 현재 데모 worker는 세션 만료 후 24시간 유예가 지난 미제출 사진 중 활성 lease/서명 참조가 없는 것만 회수한다. 제출 사진·계약 자료는 자동 삭제 대상에서 제외한다. 구체적인 운영 보관기간은 아직 미정이며 기존 문서의 90일 초안을 운영값으로 적용하지 않는다.
- 업로드 HTTP 중단은 원격 Storage 쓰기 취소 완료를 보장하지 않는다. 삭제 응답 뒤 늦은 PUT이 완료되는 경우를 위해 삭제된 사진의 row/정확한 객체 경로를 tombstone으로 보존하고 **24시간마다 동일 경로만 재삭제 대사**한다. 어떤 제출 snapshot에도 사진 ID가 참조되지 않은 `deleted` 객체만 대상이며, 이미 제출된 초안이어도 허용되는 DB 변경은 tombstone의 lease·재검사 시각·오류·갱신 시각뿐이다. 사진 내용·식별자·상태 변경 및 행 삭제는 차단한다. 이 24시간은 가벼운 기술 대사 주기이며 고객 사진 운영 보관정책이 아니다. 실제 제공자 지연 장애를 만든 것이 아니라 격리 시험으로 늦은 쓰기→제출→대사·반복 실행 시 불필요한 즉시 재처리 없음과 서명 참조 보존을 확인했다.

### 기존 승인·서명과의 결합

- 사진 추가·삭제·교체가 완료되면 초안/사진 버전이 바뀐다. 이전 approve·날짜 가용성 확인·검토 토큰·미제출 서명을 무효화하고 재확인하도록 한다. 다른 탭의 오래된 서명은 서버에서도 거절한다.
- 서버가 소유·검증 완료 상태를 확인한 `{photoId, contentHash, processingVersion}` 목록을 새 제출 snapshot/hash에 고정한다. 클라이언트가 임의 photoId/hash/경로를 지정해 연결하지 못하게 한다.
- 제출 트랜잭션은 최신 버전·진행 중 변경 없음과 사진 목록을 재검사하고 사진 참조를 고정한다. 제출 후 사진 추가/삭제는 차단하고 기존 서명·PDF·메일·Calendar를 변경하지 않는다.
- 기존 사진 없는 제출과 저장된 PDF/메일은 그대로 읽을 수 있어야 한다. 새 snapshot 형식을 버전 구분하며 기존 `kcp-demo-v1`을 덮어쓰거나 전역 버전 상수만 바꾸어 과거 제출 조회를 깨뜨리지 않는다. 새 고객 데모만 새 버전을 사용한다.

위 계층과 공개 진입점으로 구현했고 `sharp@0.35.4`를 직접 의존성으로 고정하여 lockfile을 갱신했다. `photos.ts`는 worker용 서버 진입점이며 앱 라우트는 모듈 공개 index를 사용한다.

- `GET /api/quote/photos`: 소유 초안의 사진 상태와 안전한 메타데이터.
- `POST /api/quote/photos`: 저장된 서비스·예상 revision·안내 확인·파일 메타데이터로 제한된 업로드 예약 생성.
- `PUT /api/quote/photos/{id}/content`: 바이트 상한을 스트림 수신 중 검사하고 실제 이미지 검증→정규화→저장→원자 연결. 요청의 Content-Length/MIME만 신뢰하지 않음.
- `GET /api/quote/photos/{id}/content`: 권한 있는 작성자의 검증 완료 사진만 반환.
- `DELETE /api/quote/photos/{id}`: 미제출 초안의 기대 revision 확인 후 삭제 예약/상태 반환.
- `GET /api/operations/bookings/{submissionId}/photos/{photoId}`는 기존 관리자 인증과 해당 불변 제출의 사진 참조를 검사한다. 고객 작성 쿠키를 관리자 쿠키로 대체하지 않는다.

DB/RPC·이미지·대체 Storage 시험과 실제 회사 Supabase 저장·권한·삭제·브라우저 복원을 구분해 실행했다. 마지막 DB 보호 조건을 포함한 최종 `test:operations` **229/229**와 lint·타입·빌드·`git diff --check`가 통과했다. 실제 장애·중단·늦은 원격 쓰기 전체를 회사 서비스에서 유발한 검증으로 표시하지 않는다.
