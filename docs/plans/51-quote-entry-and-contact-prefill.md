# 새 견적 작성과 기존 견적·예약 보기

2026-10-13 · Australia/Sydney

**구현·로컬 검증 완료:** 전체 767/767·관련 37/37·fixture 4/4·lint·타입·build와 production 브라우저 40/40을 통과했다. [실행 기록과 제한](../verification/2026-10-13-quote-entry-contact-prefill.md)·[3002 미리보기](http://127.0.0.1:3002/quote/start)를 따른다. 운영 배포·commit/push/merge는 수행하지 않았다.

사용자가 [50번 후속 제안](50-booking-stage-email-verification.md)을 승인했다. 견적 첫 화면을 새 작성과 기존 조회로 나누며 새 견적에는 이름·이메일·전화만 미리 채운다. 기존 견적·사진·분석·서명·예약·접수증은 보존한다. 새 비용·외부 서비스·운영 배포·로그인 유지 정책 변경은 포함하지 않는다.

## 화면과 전환

첫 화면은 **Start a new quote / View quotes & bookings** 두 카드다. 사용자 선택 전에는 기존 요청을 자동으로 화면에 채택하거나 사진/예약 workspace를 실행하지 않는다. 기존 복구 링크는 명시적 기존 조회로 들어간다. 목록은 요청을 직접 선택해야 열리며 현재 선택된 요청도 다시 열 수 있다. 요약의 draft/review_requested 값을 확정 예약 상태로 해석하지 않는다.

| Before | After | Why |
| --- | --- | --- |
| 저장 쿠키에 따라 기존 견적이 자동 복원 | 새 작성/기존 조회를 먼저 선택 | 작업 의도를 구분 |
| 새 프로젝트에도 연락처를 다시 입력 | 권한이 확인된 연락처 세 항목만 자동 채움 | 반복 입력을 줄임 |
| 선택된 고객 요청 뒤 미연결 guest 초안이 숨음 | 서버가 실제 guest 초안을 별도로 확인 | 기존 초안 접근을 보존 |

새 작성은 서버 성공 응답의 name/email/phone만 새 객체로 복사한다. 주소·suburb·postcode·설명·동의·캐비넷 선택·사진·분석·날짜/시간·서명·예약 proof는 초기값이다. 미리 채운 이메일은 새 견적의 인증 완료를 의미하지 않으며 방문일 인증 한 번을 유지한다. 첫 저장은 saved=null/expectedRevision=0으로 새 요청 ID를 만든다.

사전 입력값은 freshBaseline으로 관리해 처음 표시된 연락처를 미저장 변경으로 오인하지 않는다. 실제 변경 후에는 미저장으로 관리하고 Discard는 baseline으로 돌아간다. 연락처/서비스뿐 아니라 미저장 날짜·시간·이름/그린 서명/동의도 새 시작 전에 계속 작성 또는 명시적 취소를 요구한다. 전송 중·결과 불명 pending은 취소 대상으로 보지 않고 먼저 재시도/상태 확인을 해결한다.

## 서버 보존 경계

기존 customer/logout에 상호 배타적인 두 intent를 추가한다. 기존 일반 로그아웃과 만료 복구는 유지한다.

- **start-new:** 유효한 고객 세션으로 현재 선택 견적, 없으면 최근 연결 견적을 resolve/read해 연락처 세 항목만 반환한다. 연결본이 없으면 확인된 이메일만 제공할 수 있으며 미인증/만료 자료는 자동 채우지 않는다.
- 선택 고객 A와 별도로 raw guest 쿠키가 가리키는 저장본 B를 검사한다. B가 해당 고객의 연결 목록에 없으면 로그아웃·쿠키 변경 없이 `409 unlinked_browser_draft`와 ID/reference만 반환한다.
- guest가 비어 있으면 쿠키를 보존해 재사용한다. 확인 직후 다른 탭이 첫 저장을 하더라도 접근 수단이 사라지지 않는다. 실제 guest 저장본은 유효 고객의 연결 목록으로 복구 가능한 경우에만 작성 쿠키를 회전한다.
- **resume-browser-draft:** raw guest 저장 ID와 expectedRequestId가 정확히 같을 때 고객 세션만 종료하고 작성 쿠키를 보존한다. 이를 통해 숨은 B를 추가 OTP 없이 계속 작성할 수 있다.

고객 세션의 종료/쿠키 전환만 수행하며 기존 업무 행을 수정/삭제하지 않는다. 기존 resolve RPC의 접근 만료시간 갱신은 업무 데이터 보존과 구분한다. 새 DB schema/RPC는 추가하지 않는다.

## 클라이언트 수명

새 시작 logout → session POST → request GET 전체를 하나의 navigator writing lock으로 실행한다. 내부 customerMutation/loadSaved의 중첩 lock은 피한다. 마지막 GET이 null이어야 새 폼을 확정하며 다른 요청이 나타나면 자동 채택하지 않고 충돌/명시 복구를 표시한다.

전체 성공과 현재 generation을 확인한 뒤에만 기존 UI 상태를 새 폼으로 전환한다. 409·실패·늦은 응답에서 입력을 먼저 비우지 않는다. 결과 불명 새 시작은 자동 logout 반복 없이 명시적인 작성 세션 확인으로 복구한다. 다른 탭의 시작/선택·신원 변경은 현재 입력을 보존하고 전송을 잠그며 오래된 연락처/복원 결과가 새 화면을 덮지 않게 한다.

## 검증 범위

실제 migrations/PGlite API 검사와 로컬 production 브라우저로 새 카드·권한 있는 연락처만 자동 채움·별도 ID·기존 업무 데이터 보존·숨은 guest 차단/복귀·미저장/pending·다른 탭/중복 클릭/응답 유실·방문일 단일 인증을 검사한다. 브라우저 fixture에도 실제 CustomerAuth API와 Set-Cookie를 연결하고 인증 제공자만 합성한다. 실제 회사 DB·메일/Auth·Google/AI·운영 배포와 구분한다. 결과는 별도 검증 기록에 남긴다.
