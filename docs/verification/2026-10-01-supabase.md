## 결과와 적용 대상

사용자가 지정한 회사 프로젝트 `xlqyafthsxallostcqfe`에 업무 스키마를 적용하고 로컬 앱의 활성 저장소를 `OPERATIONS_STORE=supabase`로 전환했다. 실제 클라우드 문의 저장·권한 차단·관리자 처리·서버 재시작 보존을 확인했다. 이 Supabase 검증 시점에는 Google OAuth 클라이언트가 앱에 설정되지 않아 실제 Gmail 수집·메일 송수신·Calendar 왕복은 실행하지 않았다. 이후의 실제 Google 연결·왕복 결과는 [Google 별도 검증](2026-10-01-google-oauth-live.md)에 기록했다.

앱 주소는 `http://127.0.0.1:3002`다. 현재 관리자 로그인은 loopback 제한을 유지한다. Vercel 공개 배포, 직원별 Supabase Auth·MFA·역할, 상시 worker, 가격·기간 산식·확정 예약·인보이스 실행은 이번 완료 범위에 포함하지 않는다.

## 실제 Supabase 적용과 읽기 권한 확인

- 회사 프로젝트 SQL Editor에서 기존 `public`·`supabase_migrations` 스키마의 테이블이 0개인 상태를 먼저 확인했다.
- `supabase/migrations/20261001100420_operations_supabase.sql`을 SQL Editor에서 실행해 업무 테이블 12개와 RPC를 적용했다.
- `npm run test:supabase:connection` 실행 결과, 서버 key의 health RPC `ready=true`, `schemaVersion=1`을 확인했다.
- 서버 역할로 12개 테이블을 각각 `limit(0)` 조회해 테이블 존재·읽기 권한을 확인했다. 이 검사는 업무 행을 출력하지 않는다.
- publishable key가 유효한지 먼저 확인한 후, 12개 업무 테이블에서 모두 `42501` 권한 거부와 비공개 RPC 접근 거부를 확인했다. 잘못된 공개키 때문에 실패한 것을 보안 통과로 처리하지 않았다.
- 마이그레이션의 RLS·역할 권한은 소스와 PGlite 테스트에서도 확인했다. 실제 Supabase의 일반 로그인 사용자 JWT를 만들어 `authenticated` 접근을 시험한 것은 아니며, 해당 역할의 SELECT/DELETE/RPC 거부는 PGlite에서 실행했다.

Secret key, 관리자 비밀번호, OAuth 토큰은 이 기록과 화면 증거에 남기지 않는다.

## 코드·SQL·대체 Google 전송 테스트

`npm run test:operations`는 **39/39 통과**했다. 기존 SQLite/Gmail 23개에 Supabase/PGlite·핸들러 16개를 추가했다. `npm run lint`, `npm run typecheck`, `npm run build`도 통과했다.

추가 테스트는 다음을 확인했다.

- anon/authenticated의 비공개 테이블·RPC 접근 거부와 서버 역할의 저장.
- 문의 재전송·내용 불일치, 일정 revision·시간 검증의 원자성.
- Gmail 중복 방지·최신 30개 이력·계정 분리·검토 중 답장 병합.
- 만료된 동기화 소유권, 최신 일정과 오래된 전송 결과의 경합.
- Calendar 변경 승인/거절·삭제 후 새 이벤트 세대·잘못된 변경 검토.
- 연결 선택/재연결 잠금, 관리자 인증·동일 출처·로그아웃.
- OAuth 리디렉션·브라우저 결합·state 재사용, 회사 계정과 토큰 응답 검증.
- 권한이 줄어든 token refresh 차단과 늦은 refresh가 새 연결을 덮어쓰지 않는지.

Google 요청은 대체 전송 계층으로 검증했다. 이 테스트 통과를 실제 회사 Google 연결 성공으로 표시하지 않는다. Node의 SQLite experimental·직접 TypeScript 실행의 module-type 안내는 기존 실행 경고이며 테스트 실패는 아니다.

## 검토 중 수정한 주요 결함

- Supabase OAuth 리디렉션에서 변경 불가능한 Response 헤더에 쿠키를 추가하던 오류를 수정했다.
- cross-site OAuth 시작, 비활성화된 로컬 로그인 세션 재사용, 잘못된 저장소 선택을 차단했다.
- Google 계정 검증·토큰 형식/권한 확인을 보강하고 token refresh 결과에 비교 후 갱신을 적용했다.
- DB 잠금 획득 후 현재 시각을 계산하고 동기화 오류 기록에도 유효한 소유권을 요구하도록 수정했다.
- Calendar의 오래된 결과가 최신 일정·삭제 후 재등록 상태를 덮어쓰지 않도록 검토했다.

## 데이터 보존과 남은 확인

기존 로컬 SQLite는 문의 0개·Google 연결 0개였으며 파일을 보존했다. 이전할 실제 데이터가 없어서 임의 복사는 하지 않았다. 클라우드 시험 종료 후에는 위 합성 문의와 그 문의의 outbox만 정확히 식별해 삭제했다.

Supabase security/performance advisors는 MCP 프로젝트 접근 권한이 거부되어 실행 결과를 확인하지 못했다. 실제 Data API 접근 거부·SQL/RLS 테스트와 별개인 남은 점검이다.

마이그레이션은 Dashboard SQL Editor로 실행했으므로 CLI의 `supabase_migrations` 이력에는 등록되지 않았다. **다음 CLI `db push` 전에** 적용된 스키마와 로컬 마이그레이션이 일치하는지 확인하고 공식 migration repair 절차로 이력을 맞춰야 한다. 이력 복구는 이번에 수행하지 않았으며 이미 적용한 생성 SQL을 그대로 재실행하지 않는다.

worker의 건너뛰기와 종료 코드 0은 실제 Google 수집 성공을 뜻하지 않는다.

후속 [Google 실제 검증](2026-10-01-google-oauth-live.md)에서 회사 연결·Gmail 수신/답장·Calendar 변경 검토·재시작을 확인했다. 부분 실패 처리 보강 후 전체 테스트는 44/44와 lint·typecheck·build가 통과했다. 자연 토큰 갱신·권한 회수/재연결 등은 그 기록의 미완료 항목을 따른다.
