# 관리자 이메일 코드 인증 구현·검증

날짜: 2026-10-04 · Australia/Sydney · 브랜치: `codex/esn-admin-planning`

사용자가 본인 휴대전화가 없어 인증 앱 대신 이메일 코드로 진행하도록 요청했다. **비밀번호 로그인 → 이메일 코드 → 관리자 업무 화면**으로 변경했다. 영구 비밀번호 저장은 이미 사용자가 완료했으며 새 비밀번호를 읽거나 재설정하지 않았다.

회사 DB 적용과 로컬 앱 반영, 실제 코드 발송·사용자 코드 입력·인증 후 업무 화면까지 완료했다. 사용자가 이메일 인증과 관리자 진입을 확인했고, 서버에서도 유효한 검증 상태 1개와 소비된 코드 해시 삭제를 확인했다. 실제 업무 목록·서명 요청 상세·비공개 사진 열람과 새로고침 후 접근 유지도 확인했다. PDF 본문은 브라우저 도구 제약으로 미확인이며 ESN-01 전체 인수를 완료로 표시하지 않는다.

## 구현과 보안 경계

- `STAFF_ADMIN_SECOND_STEP=email`에서 휴대전화나 인증 앱 없이 이메일을 확인한다. 기존 `totp` 모드는 유지한다. 이메일 방식은 앱에서 관리하는 추가 검증이며 Supabase Auth의 `aal2`를 생성하거나 주장하지 않는다. Supabase의 MFA 제공 방식은 [공식 MFA 문서](https://supabase.com/docs/guides/auth/auth-mfa)를 따른다.
- 최초 관리자 수신자는 `lnkgroupsydney@gmail.com`으로 고정한다. 매 요청 최신 Auth 사용자·확인된 이메일·활성 owner/admin 권한·실제 Auth 세션·앱 직원 세션·만료를 다시 확인한다. 브라우저가 다른 수신자를 지정할 수 없다.
- 인증 코드는 암호학적 난수 6자리이며 10분 안에 한 번만 사용할 수 있다. 60초 뒤 재전송할 수 있고 새 코드는 이전 코드를 대체한다. DB에 코드 원문 대신 서버 비밀키 기반 HMAC을 저장하여 사용자·이메일·세션·발급 건에 결합한다.
- 코드 오답은 DB에 원자적으로 누적하며 다섯 번 실패하면 폐기한다. 발송 6회/시간, 확인 10회/15분의 사용자별 요청 제한도 적용한다. 코드가 잘못된 형식이어도 확인 요청 제한을 적용한다.
- DB의 `lk_staff_email_checks`는 RLS가 활성화된 서버 전용 테이블이며 공개/로그인 브라우저 역할에는 권한이 없다. `lk_staff_email_command`는 `security invoker`와 빈 `search_path`, service role 제한을 사용한다.
- 부모 직원 세션을 잠근 뒤 현재 시간을 읽어 동시 발급·확인·삭제를 직렬화한다. 세션 삭제 시 검증 상태도 함께 삭제한다. 성공 후에는 코드 해시를 지우고 검증 유효 기간을 직원 세션 이내로 제한한다. 실제 요청에서는 JWT 만료도 상한으로 적용한다.
- 제공자 실패나 발송 확인 응답 유실 때 해당 발급 건을 폐기하도록 처리한다. DB가 함께 중단되어 정리까지 실패하면 폐기를 보장할 수 없지만, 코드 검증 없이 업무 접근을 허용하지 않는다. 이전 실패 정리가 새 코드나 이미 완료된 검증을 덮어쓰지 않는다.
- 이메일 모드에서 이전 TOTP `aal2` 토큰만으로 업무 API를 통과할 수 없다. 비밀번호 변경 의무가 남은 상태, 이메일 변경, 권한 회수, 로그아웃 또는 세션 만료도 차단한다.
- 발송은 기존 승인된 Resend 설정과 `onboarding@resend.dev` 발신자를 사용한다. 새 도메인·유료 서비스는 만들지 않았다. [Resend 발송 API](https://resend.com/docs/api-reference/emails/send-email)의 성공 응답은 제공자 수락이며 최종 받은편지함 도착 증거와 구분한다.

코드 원문·비밀키·비밀번호·쿠키·토큰은 문서, 검증 로그, 스크린샷에 보관하지 않는다. 비공개 `.env.local`에 생성한 OTP 해시 비밀키와 환경 설정은 Git에서 제외한다.

## 자동 검증

| 검사 | 결과와 범위 |
| --- | --- |
| 전체 `npm run test:operations` | **320/320 통과** |
| 이메일 SQL 집중 시험 | 16/16. 권한, 세션 결합, 만료, 재발급, 오답 누적, 한 번 사용, 발송 확인 응답 유실 후 폐기 포함 |
| 실제 SDK + 합성 제공자 시험 | 이메일 모드의 aal1 접근, 미검증 aal2 차단, 수신자 고정, 비밀번호/Origin 경계, 발송 실패, 해시 결합 및 비밀키 누락 포함 |
| 도메인 정책 시험 | 다른 사용자/세션의 검증 재사용 거절, 만료·권한 조회 중 만료 거절 |
| lint · typecheck · `git diff --check` | 통과 |
| 격리 production build | 이메일 모드로 통과 |
| 기존 3002 앱 production build | DB 적용 뒤 재빌드 통과, 같은 주소에 재시작 |

PGlite 시험은 단일 연결 기반이며 실제 회사 DB의 여러 연결 경쟁을 실행한 증거가 아니다. 전체 테스트 로그는 `/private/tmp/lk-email-final-tests.log`, 실제 앱 빌드 로그는 `/private/tmp/lk-email-main-build.log`다. 기존 Node 모듈 형식/SQLite 실험 경고가 있지만 테스트 실패는 없다.

## 실제 회사 DB와 앱

신규 migration: [`20261004031640_staff_email_verification.sql`](../../supabase/migrations/20261004031640_staff_email_verification.sql).

사용자가 SQL 적용을 승인한 뒤 기존 회사 Supabase SQL Editor에서 실행하여 `Success. No rows returned`를 확인했다. 기존 고객·계약·예약 데이터를 수정하지 않았다. CLI 연결·원격 migration 이력 동기화는 별도이며 SQL Editor 적용을 CLI 이력 완료로 표시하지 않는다.

DB 적용 증거: [SQL 성공 화면](assets/staff-email-sql-applied.jpg). 보안 결과: [Advisor 화면](assets/staff-email-security-advisor.jpg). 사용자 입력 인계: [이메일 코드 화면](assets/staff-email-code-handoff.jpg). 인증 후 실제 진입: [관리자 업무 화면](assets/staff-email-admin-ready.jpg).

사용자에게 같은 컴퓨터에서 회사 메일의 `L&K Group ESN sign-in code` 제목을 확인하고, 6자리 코드를 관리자 화면에 입력하여 `Verify and continue`를 누르도록 안내했다. 코드가 보이지 않으면 스팸함을 확인하고 만료 시 화면에서 재전송한다. 실제 영구 비밀번호와 인증 코드를 채팅으로 요구하지 않는다.

이후 사용자가 인증 완료를 확인했다. 비공개 온보딩 파일에는 `email_verification_complete`와 확인 시각만 반영했다. 검증용 격리 빌드 사본의 `.env.local`을 삭제하고 실제 3002 앱과 관리자 탭을 남겼다.

사용자가 기존 탭을 Google 로그인/도움말로 이동한 동안 페이지 읽기가 자동 승인 검토에서 거절됐다. 사적 Google 계정 접근 우려가 이유였다. Google 페이지 접근이나 권한 변경을 우회하지 않았고 새 로컬 관리자 탭에서 업무 접근을 확인했다. 이 제한은 ESN 이메일 검증 실패를 뜻하지 않는다.

## 후속 인수

1. 기존 계약/PDF 다운로드를 실제 사용자 브라우저에서 확인한다. 도구의 PDF 열람 제한은 완료로 처리하지 않는다.
2. 초대·권한 회수 UI와 분실 복구 등 ESN-01의 남은 인수 범위는 별도 후속으로 유지한다. 기존 서버 정책·격리 시험과 실제 UI 인수를 구분한다.
3. [ESN 진행표](../esn-admin/05-progress.md)에 인수 증거를 반영하고 ESN-02 고객 통합 조회로 이어간다.

최초 계정·임시 비밀번호 교체·실제 Auth 세션 회수 검증은 [앞선 온보딩 기록](2026-10-04-staff-admin-onboarding.md)에 보존한다. 전화 인증 앱 등록은 최신 사용자 요청으로 현재 필수 단계에서 제외했다.
