## 구현 범위

- 관리자에게 불변 제출의 고객·서비스·샘플 금액·원본 서명·메일/Calendar 상태를 표시한다. 작업 구간은 기본 시간 없이 직접 입력한다.
- 시간·기간이 추가되거나 변경되면 별도 제안 snapshot/hash와 새 고객 동의·서명을 저장한다. 원본 제출/서명/발송 결과를 덮어쓰지 않는다.
- 서명된 새 제안의 회사 시험 메일이 Resend에 수락된 후 관리자 확정을 허용한다. 전체 작업 구간 Google busy와 DB 점유를 재검사하고 단일 시험 자원의 겹치는 확정을 트랜잭션으로 차단한다.
- 확정 요청 시 이전·새 구간의 DB 점유를 함께 보존한다. 새 Google 차단 이벤트 생성·재조회·busy 재검증 후 `calendar_ready`에서 새 제안과 점유로 전환한다. 이후 이전 Google 이벤트를 정리하며, 실패하면 과차단 상태에서 재시도한다. 최종 재조회와 정리까지 끝난 `synced`에서만 화면에 데모 확정 완료를 표시한다.
- Google 이동·삭제·반복 일정 전환은 검토 대상으로 기록한다. 같은 외부 변경의 재조회는 최초 관측 증거를 보존한다. 삭제 의도를 먼저 저장하여 Google 삭제 성공 후 DB 응답 유실도 복구한다. 기존 관리자 일정/승인 API로 서명 제출의 새 절차를 우회할 수 없다.
- 데모 견적·서명 약관 PDF를 생성하고 비공개 다운로드와 회사 전용 발송에 연결한다. 이미 고정된 HTML 발송 payload는 변경하지 않는다. 새 PDF 바이트는 비공개 DB의 발송 payload로 고정된다. 별도 공개 Storage URL은 만들지 않는다.

현재 가격·약관은 기존 샘플이며 시험 자원 1개는 운영 인력 정책이 아니다. 회사 계정 수신자 제한·localhost 실행 제한을 유지한다. 견적 PDF·예약 확정으로 인보이스를 발행하지 않는다.

최초 통합 실행에서 이전 API 시험의 허용 RPC 목록에 새 점유 조회가 누락돼 7개가 실패했다. 실제 SQL 점유 조회를 시험 어댑터에 연결해 관련 12개와 당시 전체 160개를 재검증했다. 최초 빌드에서는 UI와 서버 API를 같은 공개 진입점으로 가져와 Node 모듈이 브라우저 그래프에 들어갔다. `bookings/client` UI 진입점을 분리하고 해당 공개 경로만 lint 규칙에 명시하여 타입·lint·빌드를 재검증했다. 검사를 삭제하거나 비활성화하지 않았다.

실제 Google 연동에서는 확정 작업 이벤트의 조회 응답에 `transparency`가 생략되어 기본값 `opaque`와 다르게 비교되는 오류를 발견했다. 같은 이벤트를 직접 GET하여 생략을 확인했고, 두 비교 경로에서 **undefined만 `opaque`로 정규화**했다. 명시적 `transparent` 등 다른 값은 동일하게 취급하지 않는다. Google Calendar의 기본 `opaque` 계약은 [공식 Events 문서](https://developers.google.com/workspace/calendar/api/v3/reference/events)를 따른다. 회귀 검사 4개를 추가한 뒤 전체 164개와 lint·타입·빌드가 통과했고, 앱/worker를 새 빌드로 재시작한 후 실제 r2 확정이 정상 완료됐다.

예약 DB/API 18개에는 동일 ETag 최초 관측 보존·새 동의 후 정리 승인·stale ETag 정리 차단·정확한 frozen PDF 다운로드를 포함한다. 연결 검사기 자체의 7개 합성 시나리오도 통과했으며 잘못된 프로젝트·공개 RPC 노출·서버 행 반환은 실패 처리한다.

로컬 PDF는 합성 고객 정보로 생성했다. 원본 견적과 서명 약관 각 2페이지, 재동의 일정 약관 2페이지를 렌더링해 한글·영문·서명·페이지 경계·DEMO 표시를 확인했고 원본 두 문서의 텍스트 추출도 확인했다. 처음 발견한 폰트 glyph 정렬 오류를 수정하고 해당 회귀 검사도 추가했다. 임시 렌더 이미지 9개는 제거했다. 이후 실제 회사 제출의 r1 서명 PDF도 2페이지로 열어 정확한 서명 시각·두 작업 구간·가상 서명을 확인했다.

로컬 PostgreSQL 검사는 PGlite 격리 DB에 실제 migration SQL을 적용한다. 동시 요청 시험은 같은 PGlite 인스턴스의 경쟁 요청이며 원격 다중 세션 부하 시험이 아니다. 대체 Google·Resend 포트의 장애/응답 유실 시험을 실제 제공자 장애 시험으로 보고하지 않는다.

## 회사 Chrome의 실제 흐름

새 가상 제출 **`DEMO-EE6B0405`** (`ee6b0405-973a-4698-bc28-ce094fc1f9b5`)를 사용했다. 고객 정보·주소는 합성 자료, 메일 수신자는 회사 주소다. 기존 `DEMO-43915C8F`는 보존했고, 이전 `DEMO-734B…`의 기존 삭제 검토는 이번 검증과 무관하여 수정하지 않았다.

1. 회사 Chrome에서 고객 정보를 저장하고 Kitchen Cabinet Painting 서비스 상세를 문 8개·서랍 4개로 저장했다. 데모 승인 후 10월 20일 희망일을 선택하고 키보드로 새 서명을 그려 제출했다. Resend `provider accepted`와 회사 Calendar 확정 대기 요청 업로드를 확인했다.
2. 회사 관리자로 로그인해 제출 원본·서비스·서명·처리 상태를 열람했다. Google 권한 범위를 확대하지 않았다. 10월 20·22일 각 **09:00~12:00 Australia/Sydney** 두 작업 구간 r1을 제안하고 같은 작성 세션에서 새 서명으로 승인했다. 회사 Gmail에서 원본 및 제안 메일과 PDF 2개씩을 확인했다.
3. r1 확정 중 Google 기본 `opaque` 생략 응답으로 검토 상태가 생겼다. 위 오류 수정·회귀 검사·앱/worker 재시작 뒤 같은 작업 구간의 새 r2 (`0b7a8e93-b173-43da-b237-78daf16f33e2`)를 작성하고 다시 서명했다. 메일 제공자 수락 후 회사 확정이 **`Demo confirmed · Google verified`**로 완료됐다. 최초 제출과 각 제안/서명은 보존했다.
4. 실제 Google Calendar UI에서 이 새 참조의 10월 20일 작업을 23일 09:00~12:00으로 옮겼다. 앱은 `review_required`로 가져오고 기존 20·22일 점유를 유지했다. 회사 Chrome의 작성자 가용성 API에서 **20·22·23일 busy, 21일 요청 가능**을 확인했다.
5. 변경 관측 후 22·23일 각 09:00~12:00의 새 r3 (`98eb2d2d-0951-4b7a-b6a3-be81629e1055`)를 제안했다. 같은 작성 세션의 새 키보드 서명·메일 제공자 수락·회사 확정을 거쳐 다시 **`Demo confirmed · Google verified`**를 확인했다. 최종 작성자 가용성 API는 **22·23일 busy, 20·21일 요청 가능**이었다. 이전 일정 해제와 중간 빈 날짜 허용을 실제 API 결과로 확인한 것이며, 별도 미제출 세션의 날짜 선택 버튼 검증과는 구분한다.

## 남은 작업과 실행 상태

- 실제 모바일/터치와 별도 작성 세션의 차단일 선택 UI를 확인한다. API와 키보드 서명 결과를 해당 시험의 통과로 대신하지 않는다.
- CLI migration history repair는 회사 관리 권한/이력을 대조한 뒤 별도 진행한다. 현재 원격 schema는 적용·검증돼 있다.
- 회사 발신 도메인·실제 가격/약관·고객 소유 인증·근무/자원 규칙·사진/AI·운영 배포/상시 worker는 후속이다. 마지막 작업 Complete 후 인보이스 발행·발행일 +3 달력일 납기 정책은 유지하며 이번 데모에서 청구서를 발행하지 않는다.

회사 schema 검사 이후 로컬 앱 `127.0.0.1:3002`와 반복 worker를 실행했고 Google 응답 수정 후 새 빌드로 재시작했다. 이는 로컬 실행이며 클라우드 상시 운영이 아니다. 확인용 스크린샷은 저장하지 않았고 PDF 임시 렌더 이미지도 제거했다. 검증 종료 당시 변경은 `codex/admin-booking-confirmation` 브랜치에 미커밋 상태였으며, 이후 사용자 요청으로 커밋·main 병합을 진행한다. 최종 통합 상태는 Git 이력을 따른다.
