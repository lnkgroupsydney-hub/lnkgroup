L&K Group

클라이언트 제안서 · 2026년 9월 27일 · 버전 1.1

## 제안의 핵심

L&K Group의 핸디맨, 페인팅, 캐비넷 페인팅, 터치업 키트, 김치 판매를 하나의 고객·운영관리 시스템에 연결합니다. 고객은 서비스 견적과 예약, 상품 구매를 편리하게 진행하고, 운영자는 문의부터 작업·출고·입금까지 같은 기록에서 확인합니다.

먼저 서비스 홈페이지와 견적·예약을 출시하고, 키트 쇼핑몰을 추가한 뒤, 사진 AI 견적과 김치 판매를 확장하는 순서를 제안합니다. AI는 승인된 가격표에 따라 손상 보수 항목을 제안하며, 불확실한 작업은 담당자가 확인합니다.

우선 제작 목표는 메인 3일, Cabinet 약 1주, 이후 Coatly 기반 회사 관리 웹입니다. 관리 웹은 재사용 범위 확인 후 산정합니다. 전체 확장 계획 18~24주·850~1,270시간과 비용은 인력·자료 확보를 전제로 한 미승인 가정이며 첫 공개 목표와 범위가 다릅니다. 단계별 운영 결과로 다음 투자를 결정하고, 보수와 매출배분은 15장을 기준으로 협의합니다.

## 1 사업 범위와 출시 순서

고객이 보는 홈페이지는 각 사업의 구매 이유에 맞게 구성하고, 내부 고객·주문·견적 기록은 통합합니다. 운영관리 범위는 ERP·CRM, 즉 고객과 주문·재고·작업·수금을 관리하는 시스템입니다.

| 사업 | 제공할 기능 | 주요 확인 사항 |
| --- | --- | --- |
| 핸디맨 | 작업 상세, 표준 패키지, 사진 견적, 예약 | 실제 제공 작업과 자격, 포함 범위 |
| 페인팅 | 내부·외부 상세, 사진 접수, 방문 견적 | 면적, 준비 공정, 접근성, 자재 |
| 캐비넷 페인팅 | 기존 캐비넷 재도장 상담과 견적 | 재질, 문·서랍 수량, 탈부착·건조 일정 |
| 터치업 키트 | 옵션 선택, 결제, 제작, 배송 | 병 구성, 색상, 라벨, 재고·납기 |
| 김치 | 상품 구매, 배송일, 배치 추적 | 제조·라벨·기한·알레르겐·냉장 물류 |

**A 단계**에서는 홈페이지, 규칙·담당자 견적, 예약, 고객 관리와 인보이스를 제공합니다. 고객이 온라인으로 신청한 내용을 운영자가 처리하고 실제 매출과 업무 흐름을 검증합니다.

**B 단계**에서는 키트 상품과 재고, 결제·배송·환불을 추가합니다. **C 단계**에서는 사진 AI 검토, 김치 판매, 사업별 보고와 핵심 한국어 콘텐츠를 확장합니다.

초기 산정은 단일 판매 법인, 관리 장소 1개, 운영 사용자 10명 이하, 서비스 상세 8개, 기본 SKU 20개 이하를 전제로 합니다. 월 서비스 문의 300건과 상품 주문 300건은 산정 기준이며 현재 실적은 아닙니다.

급여·근태·세무 신고·전체 회계 시스템, 직원 소셜 게시판, 전국 냉장 배송, 구독 자동결제와 별도 모바일 앱은 초기 범위에서 제외합니다. 캐비넷 제작·설치는 캐비넷 페인팅과 다른 사업 범위입니다.

## 2 홈페이지와 고객 경험

메인은 L&K Group의 사업을 빠르게 이해하는 안내 역할을 합니다. 서비스는 카테고리와 개별 작업 상세로, 상품은 키트와 김치 전용 매장으로 이동합니다. 한 도메인에서 시작하되 화면과 구매 과정은 목적에 맞게 구분합니다.

서비스 고객의 이동은 메인 또는 검색 결과 → 작업 상세 → 주소 확인 → 작업 정보·사진 → 견적 확인 → 수락 → 예약입니다. 상품 고객은 제품 상세 → 옵션·배송 확인 → 장바구니 → 결제 → 주문 확인으로 이동합니다.

| 화면 | 고객이 확인할 내용 |
| --- | --- |
| 메인 | 서비스와 상품 선택, 실제 사례, 문의 방법 |
| 서비스 상세 | 작업 범위, 포함·제외, 가격 조건, 예상 시간, 사진과 FAQ |
| 견적 화면 | 필요한 사진과 수량, 제출 상태, 담당자 검토 여부 |
| 예약 화면 | 작업 또는 현장방문 구분, 가능한 시간, 예약금과 변경 조건 |
| 키트 매장 | 구성·용량·색상·라벨·재고·납기·배송 |
| 김치 매장 | 원재료·알레르겐·중량·보관·배송일·기한 안내 |
| 고객 계정 | 본인 견적, 예약, 주문, 인보이스와 문의 이력 |

기존 시안의 단순한 메뉴와 카테고리 카드 방향을 유지합니다. 서비스별 상세 설명과 실제 작업 사례를 보강하고, 캐비넷 항목은 재도장 중심으로 명확히 표현합니다. 김치 페이지는 식품 사진과 제품 정보를 중심으로 별도 분위기를 갖습니다.

모바일에서는 사진 촬영·업로드, 주소 입력, 단계 이동과 오류 복구가 쉬워야 합니다. 업로드 중 연결이 끊겨도 입력을 보존하고, 마지막 단계에서 지역 불가를 알리지 않도록 주소를 먼저 확인합니다. 로그인 없이 둘러보기·문의·비회원 구매가 가능하며, 민감한 거래 조회와 수락에는 이메일 확인을 적용합니다.

초기에는 영어로 출시하고 한국어 핵심 콘텐츠를 확장합니다. 서비스 약관과 식품 알레르겐 등 중요한 문구는 사람이 검수합니다.

## 3 정찰제와 견적 설계

정찰제는 고객과 운영자가 같은 작업 범위를 이해할 때 효과가 있습니다. 작업명만 정하고 가격을 붙이는 방식 대신 수량·자재·준비 작업·최대 높이·접근 조건·제외 항목을 함께 정의합니다.

표준 소규모 작업은 규칙에 따라 가격을 제시하고, 사진 확인이 필요한 작업은 담당자 검토를 거칩니다. 전체 페인팅이나 복잡한 캐비넷 작업은 현장 측정을 기본 경로로 둡니다.

| 가격 구성 | 의미 |
| --- | --- |
| 기본 패키지 | 승인된 수량과 포함 공정의 기본금액 |
| 추가 수량 | 기본 수량 초과분에 대한 명시 단가 |
| 손상 보수 | 기본 공정에 포함되지 않은 실제 추가 작업 |
| 선택 옵션 | 고객이 선택한 자재·마감·추가 서비스 |
| 접근·출장 항목 | 사전에 정한 조건에만 적용되는 추가 비용 |
| 세금과 할인 | 승인된 세금 분류·할인 규칙의 결과 |

계산 예시는 기본 A$300 + 추가 2개 × A$40 + 보수 A$50 = 세전 A$430입니다. 모든 항목이 과세이고 GST 등록 사업자라면 세금 A$43, 총액 A$473입니다. **이 금액은 산식 설명용이며 실제 판매가격이 아닙니다.**

기본 패키지에 포함된 샌딩·퍼티를 손상 추가금으로 다시 계산하지 않습니다. 같은 손상을 여러 사진에 찍어도 중복 비용을 넣지 않습니다. 손상 위험이 크다고 상한에 맞춰 억지로 가격을 낮추지 않고 별도 검토로 전환합니다.

견적에는 버전·총금액·범위·유효기간·약관을 고정해 보관합니다. 고객이 수락한 뒤 가격표가 바뀌어도 기존 견적을 자동 변경하지 않습니다. 현장에서 추가 작업이 발견되면 사유와 금액·일정 영향을 설명한 변경견적을 고객이 다시 수락하도록 합니다.

실제 정찰제 표는 대표와 운영 담당자가 작업 시간·자재·이동·재작업 비용을 확인한 뒤 승인합니다.

## 4 사진 AI의 역할과 도입 기준

사진 AI는 손상 위치·유형·보수 필요성을 파악하는 보조 기능입니다. 최종 금액은 승인된 가격표와 계산 규칙이 산출합니다. 사진만으로 숨은 손상, 정확한 면적, 위험 물질 여부를 확정하지 않습니다.

고객에게 전체 공간·대상 표면·손상 근접 사진을 요청하고, 크기를 판단할 기준이 필요하면 측정값을 추가로 받습니다. 흐리거나 정보가 부족한 사진은 재촬영을 안내하거나 담당자에게 연결합니다.

| 도입 단계 | 고객과 운영자에게 제공되는 결과 |
| --- | --- |
| 기본 운영 | 사진 접수와 담당자 견적, 실제 작업 자료 축적 |
| 내부 시험 | AI가 보수 항목을 제안하고 담당자가 검토·수정 |
| 제한 적용 | 평가를 통과한 서비스·수량·조건에서만 자동 제안 |
| 확대 | 실제 오류·분쟁·원가를 확인한 뒤 대상 범위를 확대 |

습기·곰팡이·구조 균열·높은 곳·위험 재료 의심과 복잡한 접근 조건은 자동확정을 차단합니다. 분석 장애가 생겨도 고객 문의는 저장하고 수동 견적으로 이어갑니다. AI가 작성한 설명과 고객에게 청구할 항목은 분리해 검증합니다.

최소 100건의 대표 사례 확보를 평가 목표로 두고, 작업 전문가가 손상과 보수 항목을 확인합니다. 같은 작업의 사진이 개선 자료와 평가 자료 양쪽에 섞이지 않도록 분리합니다. 자료가 부족하면 정해진 날짜가 되어도 자동확정은 열지 않습니다.

출시 기준은 규칙 계산 일치, 중복 과금 없음, 평가셋의 위험 사례 자동확정 없음과 서비스별 오차 검토입니다. 작은 시험에서 오류가 없었다고 모든 실제 현장을 보장할 수는 없습니다. 최초 운영은 담당자 승인을 거치며 문제가 발생하면 자동화를 즉시 끄고 수동 운영을 유지합니다.

고객 사진은 견적·작업 목적의 비공개 자료로 관리합니다. 홍보 사진 활용이나 추가적인 모델 개선 이용은 별도의 목적과 동의 조건을 확인합니다.

## 5 예약과 이메일 및 인보이스

고객은 견적을 수락한 뒤 가능한 작업 시간을 선택합니다. 서버가 직원·작업 시간·이동 여유·휴무·기존 예약을 확인하고, 필요한 예약금 결제가 검증되면 예약을 확정합니다. 견적 수락만으로 특정 날짜가 확보되지는 않습니다.

기존 요청인 Ermington 반경 15km를 기준으로 주소를 초기에 확인합니다. 직선거리 15,000m 이하를 기본안으로 두며 기준 주소와 정확한 경계값 포함 여부는 착수 때 확정합니다. 지역 밖 고객은 자동예약 대신 맞춤 문의를 남길 수 있습니다.

| 순서 | 고객 경험 | 내부 처리 |
| --- | --- | --- |
| 1 견적 수락 | 범위·금액·약관 확인 | 해당 견적 버전과 수락 기록 보관 |
| 2 시간 선택 | 가능한 날짜·시간 확인 | 직원·팀·작업시간 임시 점유 |
| 3 결제와 확정 | 예약금·정책 확인 | 실제 결제 확인 후 확정 |
| 4 작업 안내 | 확인·방문 전 알림 | 배정과 일정 관리 |
| 5 작업 완료 | 완료 내역·변경 승인 확인 | 사진·체크리스트·원가 기록 |
| 6 잔금 청구 | 인보이스·입금 내역 확인 | 예약금 차감, 미수금과 회계 연결 |

예약금은 계약 유형에 따라 정합니다. NSW 주거공사에 적용되는 예약금 상한과 계약 요건을 검토하므로 전체 서비스에 일괄 30%나 50%를 설정하지 않습니다. 해당 규정은 최대 10% 조건을 안내합니다. [NSW 계약 안내](https://www.nsw.gov.au/housing-and-construction/building-or-renovating-a-home/preparing/contracts)

계약 총액 A$1,100에 예약금 A$110을 받은 경우 잔액은 A$990입니다. 예약금을 매출에 다시 더하지 않습니다. 청구 발행·결제 완료·은행 정산을 구분하고, 취소·환불·변경견적도 원거래와 연결합니다.

이메일이 실패해도 확정된 예약과 주문은 사라지지 않습니다. 관리자는 실패 목록에서 재전송하거나 연락처를 확인할 수 있습니다. 중복 결제·중복 일정이 발생하지 않도록 서버와 데이터베이스에서 보호합니다.

## 6 터치업 키트 쇼핑몰

터치업 키트는 기성 상품과 맞춤 제작 상품을 구분합니다. 기존 시안의 30병·50병 키트, 회사 스티커, 지정 색상 병, 프로 키트는 초기 상품 후보이며 실제 구성·용량·납기와 판매가격은 확정이 필요합니다.

| 판매 형태 | 필요한 기능 | 고객에게 명확히 안내할 내용 |
| --- | --- | --- |
| 기성 키트 | SKU·재고·구매·배송 | 포함 구성, 용량, 사용법 |
| 지정 색상 | 제품·색상 코드·수량 선택 | 조색 가능 여부, 광택, 납기 |
| 회사 로고 | 파일 업로드·시안 승인 | 사용 권한, 승인 후 제작, 변경 조건 |
| 프로 키트 | 세트 구성·부품 재고·조립 | 전체 구성품과 제작 완료 시점 |

빈 병인지 페인트가 담긴 제품인지 먼저 구분합니다. 도료가 포함되면 실제 제품의 안전자료와 운송사 조건을 확인합니다. 화면이나 사진의 색만으로 정확한 색 일치를 약속하지 않습니다.

고객이 장바구니에 넣었다고 재고가 확보되는 것은 아닙니다. 결제 단계에서 현재 재고·배송·총액을 다시 확인하고 짧은 기간 예약합니다. 결제 성공은 결제사의 검증된 결과로 확정하며, 마지막 재고에 여러 고객이 동시에 결제해도 초과 판매가 발생하지 않도록 처리합니다.

맞춤 라벨은 승인된 시안 버전이 있어야 제작을 시작합니다. 구성품을 조립할 때 재고를 차감하는 방식과 완제품을 출고할 때 차감하는 방식을 맞춰 같은 수량이 두 번 빠지지 않게 합니다.

반품 요청, 부분 환불, 재배송과 재고 복귀는 별도 기록으로 관리합니다. 개인 변심에 대한 정책은 맞춤 제작 특성을 반영하되, 불량이나 설명과 다른 상품에 대한 소비자 권리를 배제하지 않습니다. [ACCC 소비자 보장](https://www.accc.gov.au/consumers/buying-products-and-services/consumer-rights-and-guarantees)

초기에는 키트와 김치를 별도로 결제합니다. 고객 계정에서는 두 사업의 주문을 함께 조회할 수 있습니다.

## 7 김치 온라인 판매

김치는 온라인 결제뿐 아니라 실제 식품 운영이 준비되어야 출시할 수 있습니다. 제조·보관 장소, 직접 제조인지 위탁 또는 재판매인지, 책임 사업자, 라벨과 배송 방법을 확정합니다. 처음에는 승인된 소수 상품과 제한 지역 배송으로 시작하는 안을 제안합니다.

| 영역 | 운영자가 준비할 것 | 시스템이 관리할 것 |
| --- | --- | --- |
| 식품 사업 | 관할기관 절차, 제조·보관 조건 | 승인 자료와 판매 활성화 상태 |
| 상품 정보 | 레시피·중량·성분·알레르겐 | 공개 정보와 라벨 버전 |
| 품질 | 검증된 보관·기한·포장 기준 | 배치별 검수·격리·기한 |
| 배송 | 지역·요일·마감·냉장 물류 | 결제 전 배송 가능 여부와 날짜 |
| 사고 대응 | 회수·환불·고객 응대 절차 | 해당 배치의 주문·구매자 추적 |

가정 기반 판매도 실제 운영 형태에 따른 식품 사업 요건을 확인해야 합니다. 관할 council과 NSW Food Authority에 제조·판매 방법을 설명하고 필요한 절차를 확정합니다. [NSW 식품 사업 안내](https://www.foodauthority.nsw.gov.au/retail/home-based-mixed-businesses)

각 생산 배치에 제조일·로트번호·기한·보관 장소·검수 상태를 연결합니다. 기한이 가까운 판매 가능 배치부터 출고하고, 만료·격리·회수된 배치는 주문 배정과 출고를 막습니다. 문제가 생기면 어떤 고객이 해당 배치 제품을 받았는지 조회할 수 있어야 합니다.

생선 소스·새우젓 등 원재료의 알레르겐 여부를 확인합니다. 비건·유기농·글루텐 프리 등의 표현은 증빙과 실제 레시피가 있어야 사용합니다. 온라인 표시와 포장 라벨을 일치시킵니다. [FSANZ 알레르겐 안내](https://www.foodstandards.gov.au/consumer/labelling/allergen-labelling)

김치의 안전한 보관 온도·유통기한을 개발자가 임의로 정하지 않습니다. 식품 책임자가 검증한 기준을 시스템에 입력합니다. 배송 중 누수·온도 이탈·수령 실패는 품질 사건으로 남기고 일반 반품처럼 자동 재판매하지 않습니다. 서비스 작업 반경 15km와 김치 배송 가능 지역은 별도 정책입니다.

## 8 통합 운영관리와 기술 구성

관리자는 고객 한 명의 문의·견적·예약·작업·주문·입금 이력을 연결해서 봅니다. 고객정보는 공통으로 관리하고, 서비스·키트·식품 담당자의 접근 범위는 업무에 맞게 제한합니다.

| 운영 화면 | 확인하고 처리할 내용 |
| --- | --- |
| 오늘의 업무 | 신규 문의, 견적 승인 대기, 오늘 일정, 미출고 |
| 고객과 견적 | 연락처, 문의, 사진, 견적 버전, 수락, 다음 담당자 |
| 일정과 작업 | 직원 배정, 공정, 진행 사진, 변경 요청, 완료 |
| 상품과 재고 | 입고, 예약, 제작, 출고, 반품, 폐기와 수량 조정 |
| 청구와 입금 | 인보이스, 예약금, 잔액, 환불, 연체와 회계 자료 |
| 사업 보고 | 사업별 순매출, 원가, 미수금, 전환과 기여이익 |
| 예외 처리 | 이메일·결제·AI·회계 연동 실패와 재실행 |

Next.js는 고객과 관리자 화면을, Supabase는 고객·거래 데이터와 로그인·파일 보관을, Vercel은 운영 배포를 담당합니다. 초기 개발은 Supabase Cloud의 테스트·운영 프로젝트를 분리해 진행합니다. Docker는 초기 필수 설치에서 제외하고, 로컬 DB 실행·검증이나 특수 처리가 필요할 때 선택적으로 사용합니다. 결제는 Stripe를 기본안으로 두고 이메일·주소·회계 도구를 연결합니다.

현재 Vercel은 Docker 이미지를 실행하는 배포를 지원합니다. 다만 로컬 Docker Compose 전체를 운영 환경에 그대로 올리는 방식과는 구분합니다. 중요한 상태와 파일은 데이터베이스·파일 저장소에 보관합니다. [Vercel Docker 안내](https://vercel.com/kb/guide/does-vercel-support-docker-deployments)

고객은 본인 거래만, 현장 직원은 배정 작업만, 식품 직원은 식품 출고 정보를 봅니다. 회계 담당자가 집 내부 사진까지 볼 필요는 없습니다. 관리자 주요 변경은 누가 언제 왜 처리했는지 남깁니다.

도메인·배포·결제 등 회사 운영 계정은 회사가 소유·관리하는 방향입니다. 기존 Coatly 코드와 공통 모듈, 회사 전용 결과물의 소유·사용권·양도·재사용 조건은 별도 계약으로 정합니다. 개발 환경과 운영 환경을 분리하고, 테스트에서 실제 고객에게 메일을 보내거나 실제 결제를 만들지 않도록 설정합니다. 소규모 ERP는 세무 신고와 전체 회계 시스템을 대체하지 않고 회계 자료를 연결합니다.

## 9 구축 일정과 담당 역할

전체 계획은 18~24주입니다. 핵심 개발자 1명과 파트타임 개발·QA 지원, PM·디자인·운영 담당의 참여로 주 45~60시간의 총 실투입을 확보하는 조건입니다. 콘텐츠나 사업 승인이 늦어지면 의존 기능의 일정도 바뀝니다.

| 단계 | 목표 시기 | 결과 | 총공수 |
| --- | --- | --- | --- |
| 준비 | 1~2주 | 범위·가격·정책·디자인 | 90~130h |
| A 서비스 | 3~8주 | 홈페이지·견적·예약·청구 | 280~420h |

| 일정 완충 | 최대 6주 | 외부 승인·불확실성 대응 | 실제 영향에 따라 조정 |

총공수 850~1,270시간에는 설계·개발·PM·디자인·QA·교육이 포함됩니다. 한 사람이 모든 역할을 맡고 주 30시간을 투입하면 약 30~44주에 외부 대기 시간을 더하는 계획이 필요합니다. 인력이 정해지면 상세 일정과 비용을 다시 산정합니다.

대표는 사업 범위·가격·정책·예산, 운영자는 실제 업무와 인수 테스트, 개발 리드는 기술·보안·배포를 담당합니다. 회계 담당자는 세금·인보이스·환불, 식품 책임자는 제조·라벨·배송과 식품 출시를 승인합니다.

주 1회 의사결정 회의와 2주 단위 시연을 제안합니다. 시연에서는 화면뿐 아니라 실제 주문·견적·예약·수량·입금이 맞는지 확인합니다. 새로운 기능 요청은 가치·비용·일정 영향을 설명한 뒤 반영합니다.

AI 자동확정은 대표 사례와 평가 결과가 확보되어야 합니다. 김치는 식품 판매 준비가 완료되어야 하므로 일정에 맞추기 위해 이 조건을 생략하지 않습니다. 서비스와 키트는 각 단계의 검증을 통과하면 먼저 운영할 수 있습니다.

서비스별 상세 페이지는 실제 작업 범위·가격 조건·전후 사진·FAQ·관련 작업을 제공합니다. 지역명만 바꾼 대량 페이지를 만들지 않습니다. 실제 사례가 쌓이면 해당 지역에서 무엇을 했는지 보여주는 사례 페이지를 추가합니다. [Google 검색 정책](https://developers.google.com/search/docs/essentials/spam-policies)

Google Business Profile은 실제 사업과 서비스 지역을 기준으로 운영합니다. 가상 주소나 지역별 중복 프로필로 노출을 늘리지 않습니다. 김치 별도 프로필은 독립적인 자격을 확인한 뒤 검토합니다. [Google 사업 프로필 지침](https://support.google.com/business/answer/3038177?hl=en)

검색광고는 주소·견적·예약 흐름이 검증된 뒤 소규모로 시작합니다. 작업 구역 밖 유입과 채용·교육 등 구매와 다른 검색 의도를 줄입니다. 캐비넷은 전후와 공정, 키트는 구성·색상·사용법, 김치는 성분·레시피·배송 안내를 중심으로 콘텐츠를 만듭니다.

서비스 고객에게 김치 광고를 자동으로 보내지 않습니다. 사업별 관심과 마케팅 동의를 확인하며, 실제 작업 사진의 홍보 사용도 별도로 승인받습니다. 광고는 문의 수뿐 아니라 실제 완료·환불·기여이익까지 연결해서 판단합니다.

## 12 출시 후 90일 실행과 성과

기간은 A 유료 출시일부터 계산합니다. 키트나 김치가 미출시 상태라면 해당 광고 예산은 집행하지 않습니다. 첫 4주는 기준 데이터를 만드는 기간으로 보고, 이후 실제 결과로 목표와 예산을 조정합니다.

| 기간 | 주요 실행 | 판단할 결과 |
| --- | --- | --- |
| 출시 전 | 서비스 8개·사례·정책·분석 확인 | 문의·결제·알림 검증 |
| 1~14일 | 기존 관계·소개·지역 검색광고 소규모 시작 | 유효 문의와 응답 속도 |
| 15~30일 | 검색어 정리·모바일 이탈 개선·주 1회 사례 | 단계별 전환과 수락률 |
| 31~60일 | 수익성 좋은 작업 확대·B2B 샘플 접점 | 신규 완료 고객당 획득비 |
| 61~90일 | 재구매·키트 캠페인·조건부 김치 시험 | 반복 구매·환불·배송 사고 |

월 A$3,000의 유료 매체 실험 예산을 가정하면 검색 1,800, Meta 600, 키트 300, 김치 300으로 나눌 수 있습니다. 이는 권장 계약금액이나 성과 보장이 아니며 촬영·대행·샘플·할인 비용은 별도입니다. 실제 수용 가능한 작업량과 이익에 맞춰 조정합니다.

가정 예시로 클릭 1,000회 중 유효 문의 5%, 견적 발행 80%, 수락 35%, 완료 90%이면 약 12.6건의 완료 작업입니다. 광고비 A$1,800일 때 완료당 매체비는 약 A$142.86입니다.

다른 예시에서 GST 제외 매출 A$600에서 노동·자재·이동·수수료·재작업 충당을 빼고 A$220이 남으며 목표 이익이 A$120이라면 고객획득비 한도는 A$100입니다. 위 광고 예시는 이 한도를 넘으므로 예산을 늘리기 전에 전환·가격·원가를 개선해야 합니다. 모든 예시 수치는 실제 L&K 실적이 아닙니다.

매주 유효 문의율, 견적 수락률, 실제 완료당 획득비, 순매출, 미수금과 재작업을 봅니다. 키트·김치는 구매 전환·반복 구매·배송 비용·폐기·환불을 별도로 확인합니다. 서버의 확정된 거래를 기준으로 집계하고, 브라우저 구매 이벤트 중복을 제거합니다.

검색량·클릭비·경쟁사 매출은 아직 검증된 값이 없습니다. 광고 계정과 실제 CRM 데이터를 확보한 후 수요와 성과를 보정합니다.

## 13 품질 검증과 운영 인수

출시는 화면이 완성되었을 때가 아니라 고객과 운영자가 금액·일정·수량·개인정보를 믿고 사용할 수 있을 때 진행합니다. 결제·예약·재고·고객 권한의 핵심 검증은 각 단계 출시 전에 끝냅니다.

| 검증 영역 | 출시 조건 |
| --- | --- |
| 견적과 결제 | 가격 버전 보존, 중복 과금 없음, 환불·잔액 정확 |
| 예약 | 동시 요청에도 중복 배정 없음, 현지 시간 일치 |
| 상품 | 마지막 재고 경합 처리, 출고·반품 원장 일치 |
| 식품 | 만료·격리 배치 차단, 모의 회수 성공 |
| 고객 보호 | 다른 고객 정보·사진 접근 차단, 직원 권한 제한 |
| 장애 | 이메일·AI 실패 후 수동 처리·재시도 가능 |
| 복구 | DB와 파일 복원 및 거래 대사 확인 |
| 실제 업무 | 담당자가 견적·예약·출고·환불을 직접 수행 |

고객 사진은 비공개로 보관하고, 관리자에게는 MFA와 역할별 권한을 적용합니다. 보관기간과 삭제·정정 절차, AI·이메일 등 외부 제공자의 처리 범위를 개인정보 안내에 반영합니다. 법 적용 여부는 실제 사업 형태를 확인합니다. [OAIC 사업 안내](https://www.oaic.gov.au/privacy/privacy-guidance-for-organisations-and-government-agencies/organisations/small-business)

홍보 수신 동의와 철회 기록을 관리하고 거래 안내와 광고를 구분합니다. 수신거부는 내부적으로 즉시 반영하도록 설계하며 ACMA의 관련 요건을 준수합니다. [ACMA 안내](https://www.acma.gov.au/avoid-sending-spam)

복구 목표 초안은 최대 1시간의 데이터 손실 범위와 4시간 내 복구입니다. 실제 유료 복구 옵션과 시험 결과가 필요합니다. 기본 일일 백업만 선택하면 목표를 조정해야 하며, DB 백업과 사진·문서 파일 백업은 별도로 준비합니다.

인수 시 회사 운영 계정, 계약으로 정한 범위의 소스코드·사용권, 개발 문서, 관리자 매뉴얼, 가격 변경·환불·재고 조정·장애 복구·식품 회수 절차를 제공합니다. 운영자 교육 2회와 직접 수행하는 인수 테스트를 제안합니다. 미해결 결함과 운영 책임, 유지보수 범위를 명시한 뒤 인수합니다.

## 14 착수 결정과 근거

첫 착수 회의에서는 다음 내용을 확정해 개발 기준으로 사용합니다. 이미 정한 5개 사업과 기술 방향, ERP·CRM 범위는 유지하고 실제 운영값을 채웁니다.

| --- | --- | --- |
| 판매 주체 | 법인·ABN·GST·계좌·자격·보험 | 대표·회계 |
| 초기 서비스 | 작업 범위·포함/제외·시간·자재·원가 | 대표·운영 |

개발팀에는 분야별 Markdown 명세와 백로그, 데이터·권한 규칙, 자동견적·예약·상품 예외, 테스트 시나리오, 마케팅 측정 사전이 제공됩니다. 모델과 reasoning effort는 사용자 선택을 따르며, 별도 지정이 없는 에이전트는 현재 채팅의 설정을 상속합니다. Sol 모델을 명시할 때는 gpt-6.1-sol을 사용하며, 모델 선택과 실제 검증 증거는 별도로 기록합니다.

## 15 보수와 웹 매출배분 협의

현재 전달된 제안은 웹 유입으로 인정되는 매출의 5%를 배분하는 방식입니다. GST 포함 A$1,100 결제에 대한 배분금은 A$55로 설명되었습니다. 최종 계약 체결 여부는 확인되지 않았으며, 정산 기준과 각 업무의 보수는 추가 협의가 필요합니다.

웹사이트·회사 관리 시스템·AI 견적·자동화의 개발 범위와 보수, 유지관리 시간·지원 범위, 마케팅 산출물과 보수를 정합니다. 초기 구축비와 단계별 개발비, 월 관리비, 웹 매출 성과 보상을 구분하는 안을 협의할 수 있습니다. 분할 지급이나 최소 보수를 선택하면 금액·기한 및 매출배분금과의 관계를 명시합니다.

개발용 AI 비용은 개발자가 부담하고 도메인·서버·사진분석 API 등 회사 운영 실비는 회사에 청구하는 방침을 계약에 반영할 필요가 있습니다. 비용 항목·승인 한도·결제 주체·정산 기한을 확인하고 광고 매체비는 별도 예산으로 협의합니다.

웹 문의 후 전화 계약·계좌이체, 홈페이지를 보고 건 전화, 기존 고객의 온라인 신청, 재구매·추가 공사와 여러 채널을 거친 거래의 인정 범위를 정합니다. 문의 출처와 거래·입금·환불 내역을 연결해 양측이 월별 정산을 확인할 수 있도록 합니다.

GST 포함 매출 기준과 별도로 할인·환불·취소·차지백·예약금·잔금·미수금 처리, 매출 인정 시점과 지급일, 수수료 청구서의 GST 처리를 정합니다. 예약금과 잔금을 중복 집계하지 않으며, 출처 미확인 거래와 정산 이의제기 절차도 합의합니다.

계약 당사자와 대상 사업, 계약 기간, 추가 업무의 변경 절차, 조기 종료 시 개발비·미지급금·후속 입금 정산, 인수 지원 범위를 정합니다. 기존 코드·공통 모듈·회사 전용 결과물의 권리와 지급 조건은 별도 조항으로 명시합니다. 회사의 가격·업무 승인과 AI 검토 책임, 유지관리 책임 범위도 함께 협의합니다.

이 장은 협의할 사항을 정리한 제안이며 합의된 계약 조건이나 법률 문안을 뜻하지 않습니다. 일반적인 계약 작성·협상 항목은 호주 정부의 안내를 참고했습니다. [계약 작성 안내](https://business.gov.au/people/contractors/prepare-a-contract), [계약 협상 안내](https://business.gov.au/people/contractors/negotiate-a-contract). 해당 안내는 2026년 9월 27일 확인했습니다.
