# Current module boundaries

- `service-catalog/domain` owns the four service identifiers and catalogue shape. It is pure TypeScript. `application/list-services` applies the agreed display order to a supplied catalogue; the public entry point supplies local content from `infrastructure`.
- `service-catalog/presentation` renders the supplied catalogue and the static Kitchen Cabinet Painting detail. Service routes, icons and contact anchors are UI concerns, separate from the domain. Cabinet categories, scope, process, example briefs and FAQs live in `service-catalog/content`. Company-provided methods, product family and general timing are distinguished from unconfirmed package inclusions, prices and project-specific arrangements; the page does not sell fixed packages.
- `company-profile` owns company copy, confirmed contact details, business identifiers, service-area content, page navigation and the related sections. Cabinet content reuses company facts through its public entry point. Its shared header and footer use page context to link back to home sections from a detail page. Only the mobile menu is a Client Component. Source and outstanding assets are recorded in [the company brief](../../docs/reference-assets/company-brief.md).
- `showcase` owns the gallery of company-provided cabinet preparation and spray-painting photos. It does not invent project locations or before-and-after pairs. Company promotional artwork is displayed in About; generated Cabinet example images remain explicitly labelled as concepts.
- `src/app` composes public module entry points and owns route metadata. Module internals use relative imports; imports from another module go through its `index.ts`.
- `src/shared/ui` contains content-neutral layout and links. Central image paths, dimensions and alt text are in `src/shared/config/assets.ts`; navigation targets and prototype settings are separate configuration.

## Operations and customer flows — 2026-10-06

- `enquiries` owns the customer quote form, saved contact/service drafts, availability requests, private photos, and immutable demo submissions with signatures and PDF/email delivery. A draft cookie grants access to its draft; it does not establish a verified customer identity. Demo prices and terms are not approved operating values.
- `operations` owns the existing admin console, legacy owner/Google preview access, enquiry review, Google connection and calendar coordination, plus SQLite/Supabase adapters. With staff authentication enabled, its server access boundary delegates to `admin-access`; it does not fall back to a legacy preview cookie. Company Google integration is separate from staff sign-in. The app remains loopback-restricted and is not publicly deployed.
- `admin-access/domain` owns pure staff authorization policy: a verified, unexpired session, matching current company membership, accepted additional verification, and per-operation permissions. `application` composes verification, membership and clock ports. The Supabase adapter checks verified claims, a fresh Auth user, actual Auth-session validity, the ESN session registry and initial password setup. First-account membership comes from server-owned `app_metadata`; user metadata and stale JWT roles never grant access. The selected email verification mode requires a proof bound to the current user/email/session and remains distinct from Supabase `aal2`/TOTP MFA.
- `admin-access/presentation` supplies staff sign-in/onboarding and the session security panel. The new server-only session RPC lists safe expiry summaries and serializes removal of the user's other ESN sessions while preserving the current one; Auth-provider cleanup follows and partial failure stays retryable. New session SQL is prepared but company application is awaiting user approval. Additional invitations, role/membership management and lost-account recovery execution remain pending.
- `customers` owns the customer register, bounded search, manual source classification and append-only classification audit. Its staff-authorized `/api/admin/customers` endpoints use server-owned actor/company fields and one SQL transaction for revision, source uniqueness, idempotency and audit. A signed submission and its derived enquiries remain one canonical source; original snapshots, booking state, PDFs and private photos are not rewritten. Presentation preserves Operations and adds customer creation, detail, link/unlink confirmation and protected document/photo links. Purchases and billing explicitly remain unavailable. The three-table company migration is prepared, not yet applied; synthetic API/SQL checks do not establish real customer writes or production readiness.
- `operations/infrastructure/preview-access` uses the `admin-access` public entry point for the separate legacy preview policy. Local enablement, the configured request host, internal loopback and current local/Google session are checked before business access. Anonymous session responses expose only required login state; authorized business JSON responses use `private, no-store` and `Vary: Cookie`. This boundary does not upgrade a company-demo login to staff authorization.
- `bookings` owns company proposals, customer consent, atomic occupancy and confirmation, and Calendar change review. Preserve its client/server entry-point boundaries and existing revision, consent and idempotency checks.
- `gmail-intake` collects the configured company's labelled enquiries and threads. A mail sender is an unverified contact source, not permission to merge customer identities automatically.
- The shared worker composes public server entry points. DB migrations remain in one root history, and private documents/photos are served only after server authorization.
